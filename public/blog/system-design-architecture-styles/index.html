Моноліт, мікросервіси, SOA та інші архітектурні стилі простими словами

25 Oct, 2026

Моноліт і мікросервіси — це лише два краї довшого спектра архітектурних стилів. Між ними (і трохи збоку від них) є ще кілька підходів, які активно живуть у production, просто про них рідше пишуть простою мовою.

У цій статті розберемо:

  • швидкий рекап моноліту й мікросервісів — як точку відліку;
  • Service-Based Architecture — проміжний варіант, про який мало хто розказує;
  • SOA (Service-Oriented Architecture) — те, що було до мікросервісів, і чому це не одне й те саме;
  • Event-Driven Architecture — інша вісь: питання не “скільки сервісів”, а “як вони спілкуються”;
  • Space-Based Architecture — нішевий, але цікавий стиль для екстремальних навантажень;
  • і наприкінці — порівняльну таблицю й гайд “що обрати”.

Це не ієрархія “гірше → краще”. Це інструменти під різні задачі. Вибір архітектури — завжди trade-off, а не пошук єдиної правильної відповіді.

Моноліт і мікросервіси: швидкий рекап

Моноліт

Один застосунок, один процес (або кілька однакових його копій за балансувальником), один деплой, зазвичай одна база даних. Модулі типу Users, Orders, Billing живуть в одному codebase і звертаються один до одного звичайними викликами функцій, а не через мережу.

┌──────────────────────────────────────┐
│       Один застосунок (1 процес)       │
│                                         │
│    Users   │   Orders   │   Billing    │
│     (усі модулі в одному коді)         │
│                                         │
│         один деплой, одна БД           │
└──────────────────────────────────────┘

Плюси:

  • Просто розробляти й дебажити — усе в одному місці, один стектрейс.
  • Один деплой — не треба координувати релізи кількох сервісів між собою.
  • Транзакції прості: одна БД → звичайний ACID, без складних танців із consistency.
  • Дешевше на старті: менше інфраструктури, менше DevOps-роботи.

Мінуси:

  • Масштабується цілком, а не частинами. Якщо під навантаженням лише модуль “пошук” — доведеться піднімати нові копії всього застосунку, а не тільки пошуку.
  • Великий codebase означає довший build/CI і більше merge-конфліктів, коли над ним працює багато команд одночасно.
  • Один серйозний баг (memory leak, нескінченний цикл) може покласти весь застосунок.
  • Технологічний стек зазвичай один на весь застосунок — важко поступово перейти на іншу мову чи фреймворк лише для одного модуля.

Моноліт — не “легасі” і не ознака поганого інженера. Для стартапу, MVP чи команди до десяти людей це часто найрозумніший вибір.

Мікросервіси

Система розбита на окремі сервіси (Users, Orders, Billing), кожен — свій codebase, свій деплой, своя база даних. Спілкуються через мережу: REST, gRPC або асинхронно через черги повідомлень.

 ┌────────┐      ┌────────┐      ┌────────┐
 │ Users  │◄────►│ Orders │◄────►│Billing │
 │service │      │service │      │service │
 │+ своя БД│     │+ своя БД│     │+ своя БД│
 └────────┘      └────────┘      └────────┘
      окремий деплой, окрема БД, зв'язок
         через мережу (REST / gRPC / черги)

Плюси:

  • Кожен сервіс масштабується і деплоїться незалежно від інших.
  • Команди незалежні: команда Orders не чекає релізу від команди Billing.
  • Можна використовувати різні мови й бази даних під різні сервіси (polyglot).
  • Збій в одному сервісі за правильної архітектури (таймаути, circuit breaker) не обов’язково кладе всю систему.

Мінуси:

  • Мережа ненадійна. Те, що в моноліті було викликом функції (завжди відповідає), стає HTTP- або gRPC-запитом, який може таймаутити, падати чи повертати частковий результат.
  • Транзакція через кілька сервісів і баз — це вже не ACID. Потрібні паттерни типу Saga з компенсаційними кроками замість звичайного rollback.
  • Потрібна зріла DevOps-культура: CI/CD на кожен сервіс, service discovery, централізоване логування й трейсинг (інакше дебаг перетворюється на пекло), API gateway.
  • Більше інфраструктурних витрат: більше баз даних, більше контейнерів, більше moving parts загалом.

Мікросервіси — це обмін простоти коду на складність інфраструктури. Без DevOps-зрілості (CI/CD, моніторинг, трейсинг) вони швидше покарають команду, ніж допоможуть їй.

А що між ними? Service-Based Architecture

Ось тут починається те, про що найчастіше не розказують.

Уяви, що ти ріжеш моноліт на частини, але ще не готовий (або немає реальної потреби) городити повноцінні мікросервіси з окремою базою даних для кожної частини. Service-Based Architecture — це компромісний варіант: кілька великих “доменних” сервісів (Users, Orders, Billing — зазвичай одиниці, а не десятки), кожен деплоїться незалежно, але всі вони використовують одну спільну базу даних.

 ┌────────┐      ┌────────┐      ┌────────┐
 │ Users  │      │ Orders │      │Billing │
 │ domain │      │ domain │      │ domain │
 │service │      │service │      │service │
 └───┬────┘      └───┬────┘      └───┬────┘
     │   незалежний деплой кожного    │
     └───────────────┬─────────────────┘
                      ▼
             одна спільна база даних

Це як переїхати з одноквартирного будинку (моноліт) не в окремі таунхауси (мікросервіси), а у велику комунальну квартиру: у кожного своя кімната зі своїми вхідними дверима (незалежний деплой), але труба з водою й каналізація — одна на всіх (спільна БД).

Плюси:

  • Найпростіший і найдешевший спосіб “розрізати” моноліт — не треба одразу вирішувати, як розносити дані по окремих базах.
  • Незалежний деплой кожного сервісу: можна релізити Orders без ризику зачепити Billing.
  • Транзакції й JOIN-и між доменами лишаються простими, бо база даних одна.
  • Менше інфраструктурної складності, ніж у повних мікросервісах: не потрібні event bus, saga-оркестратори чи десятки окремих баз даних.

Мінуси:

  • Спільна база даних — це спільна точка зв’язаності. Зміна схеми таблиці, яку використовують кілька сервісів, вимагає координації між командами — рівно та проблема, якої мікросервіси намагаються уникнути.
  • Немає повної fault isolation: якщо база даних перевантажена чи лежить, лежать усі сервіси одразу.
  • Масштабування обмежене пропускною здатністю однієї бази даних: можна масштабувати логіку сервісу, але не його дані окремо.
  • Легко непомітно скотитися в “розподілений моноліт” — найгірше з обох світів: складність мережі мікросервісів плюс зв’язаність моноліту.

Нюанс щодо назви: чіткого єдиного стандарту термінології тут немає — різні автори й компанії називають подібні речі по-різному. Цю конкретну назву й опис активно використовують Mark Richards і Neal Ford у книзі Fundamentals of Software Architecture — непогане джерело, якщо захочеш копнути глибше. Але сама ідея — кілька великих сервісів зі спільною базою даних, без повноцінної event-шини — дуже поширена на практиці як перший крок при розпилюванні моноліту, навіть якщо команда ніде вголос не називає це “Service-Based Architecture”.

SOA (Service-Oriented Architecture): дідусь мікросервісів

SOA з’явилась задовго до мікросервісів — у великих enterprise-системах (банки, телеком, страхові компанії). Ідея була правильна: розбити систему на сервіси, які можна повторно використовувати в різних частинах компанії. Проблема — у тому, ЯК це зазвичай реалізовували.

Класична SOA будується навколо ESB (Enterprise Service Bus) — централізованого “диспетчера”, через якого проходить весь трафік між сервісами. ESB робить роутинг запитів, трансформацію форматів повідомлень, а іноді й оркестрацію цілих бізнес-процесів.

     Клієнт 1      Клієнт 2      Клієнт 3
        └──────────────┬──────────────┘
                        ▼
             ┌────────────────────┐
             │     ESB (шина)      │
             │ routing / transform │
             │   / orchestration   │
             └──────────┬──────────┘
      ┌──────────────────┼──────────────────┐
      ▼                   ▼                   ▼
  ┌───────┐          ┌─────────┐         ┌───────────┐
  │   HR  │          │ Billing │         │ Inventory │
  │service│          │ service │         │  service  │
  └───────┘          └─────────┘         └───────────┘
              спільна enterprise-БД

Уяви велику корпорацію з централізованою диспетчерською: кожен дзвінок (запит) спочатку йде на ресепшн (ESB), який вирішує, у який відділ (сервіс) його передати, і за потреби “перекладає” запит на мову цього відділу. Самі відділи (HR, Billing, Inventory) часто користуються однією спільною корпоративною базою даних.

Плюси:

  • Чудово підходить для повторного використання бізнес-сервісів по всій великій компанії, а не лише в одному застосунку.
  • ESB централізує cross-cutting concerns: безпеку, логування, трансформацію протоколів — зручно, коли треба інтегрувати десятки різнорідних legacy-систем (мейнфрейми, різні протоколи, різні епохи розробки).
  • Формальні контракти сервісів (історично — WSDL/SOAP) дають чітку, задокументовану межу між командами у великих організаціях.

Мінуси:

  • ESB — потенційна єдина точка відмови і вузьке горлечко: весь трафік компанії проходить через один компонент.
  • Протоколи класичної SOA (SOAP/XML) помітно важчі й повільніші за сучасний JSON/REST.
  • Централізоване управління означає повільні зміни: будь-яка модифікація спільного сервісу вимагає погодження з усіма, хто його використовує.
  • Головна пастка: бізнес-логіка поступово “заповзає” у ESB (так звані “smart pipes”), і сама шина перетворюється на новий, ще гірший моноліт — тільки прихований і незручний для дебагу.
  • Саме через ці проблеми індустрія масово почала переходити на мікросервісну філософію з принципом “smart endpoints, dumb pipes” (“розумна логіка — у самих сервісах, а не в трубі між ними”). Цю фразу в 2014 році популяризували Martin Fowler і James Lewis у своїй знаменитій статті про мікросервіси.

SOA — не те саме, що мікросервіси, хоча на перший погляд схожі. Головна різниця в тому, ДЕ живе “розум” інтеграції: у SOA він централізований у шині (ESB), у мікросервісах — розподілений по самих сервісах, а зв’язок між ними максимально простий (звичайний HTTP-виклик чи повідомлення в черзі).

Event-Driven Architecture: інша вісь координат

Усе, про що йшлося вище (моноліт → Service-Based → SOA → мікросервіси), — це питання “на скільки частин розрізати систему і хто цими частинами володіє”. Event-Driven Architecture (EDA) — про інше: “як ці частини спілкуються між собою”.

Замість того щоб сервіс А робив прямий синхронний запит до сервісу Б (“зроби це і дай мені відповідь прямо зараз”), сервіс А публікує подію (“замовлення №123 оплачено”) у брокер повідомлень (Kafka, RabbitMQ, NATS, AWS SNS/SQS) і більше про неї не думає. Усі, кому ця подія цікава, самі підписуються і реагують — коли їм зручно.

  ┌─────────┐   подія "order.paid"    ┌─────────┐
  │ Orders  │ ──────────────────────► │ Брокер  │
  │ service │  (публікує і забуває)   │ (Kafka/ │
  └─────────┘                         │RabbitMQ)│
                                       └────┬────┘
             ┌──────────────┬───────────────┤
             ▼                ▼               ▼
        ┌─────────┐    ┌───────────┐   ┌────────────┐
        │ Billing │    │ Shipping  │   │ Email / SMS│
        └─────────┘    └───────────┘   └────────────┘
             кожен підписник реагує незалежно від інших

Це як різниця між телефонним дзвінком і постом у груповому чаті. Дзвінок (синхронний виклик) вимагає, щоб обидва боки були на зв’язку прямо зараз. Пост у чаті (подія) публікується один раз, а служба доставки, бухгалтерія й система сповіщень реагують на нього кожна у свій час, незалежно одна від одної.

Плюси:

  • Максимально слабка зв’язаність (decoupling): сервіс-видавець події взагалі не знає, хто й скільки підписників на неї реагує. Новий сервіс-підписник можна додати, не торкаючись видавця.
  • Добра стійкість до пікових навантажень: якщо підписник тимчасово лежить чи повільний, повідомлення чекають у черзі, а не втрачаються й не блокують видавця.
  • Природно підходить для real-time потоків даних, аналітики, сповіщень.
  • Легко масштабувати обробку: додав більше інстансів-обробників — швидше розбирається черга.

Мінуси:

  • Важче побачити “наскрізний” шлях даних: подія може пройти через кілька сервісів, і щоб відстежити весь ланцюжок, потрібен розподілений трейсинг і correlation ID в кожному повідомленні.
  • Eventual consistency замість миттєвої: видавець не отримує негайного підтвердження, що всі підписники обробили подію.
  • Повідомлення можуть доставлятися двічі (типова гарантія багатьох брокерів — “at least once delivery”), тому обробники мають бути ідемпотентними: повторна обробка того самого повідомлення не повинна зламати дані.
  • Схема події неявно стає публічним контрактом: якщо видавець змінить формат події, усі підписники можуть зламатися непомітно, без явної помилки на етапі збірки чи деплою.

На практиці Event-Driven рідко використовують “замість” мікросервісів — частіше разом: мікросервіси як одиниці деплою, а events — основний спосіб спілкування між ними замість прямих синхронних викликів.

Space-Based Architecture: коли навантаження різко стрибає

Останній зі стилів у цьому огляді — найнішевіший. Space-Based Architecture (інколи її називають просто “cloud architecture pattern”) вирішує одну конкретну проблему: що робити, коли навантаження на систему не просто велике, а різко й непередбачувано стрибає — розпродаж, продаж квитків на концерт, вірусний пост. У звичайній архітектурі саме в такі моменти першою “падає” база даних: усі запити рано чи пізно йдуть через неї, і вона стає вузьким горлечком.

Ідея Space-Based Architecture: прибрати базу даних із критичного шляху запиту. Дані тримаються в розподіленій пам’яті (in-memory data grid) між багатьма processing units — кожен такий вузол має і логіку, і копію потрібних даних в оперативній пам’яті. Запис у “справжню” базу даних відбувається асинхронно, пізніше — цей паттерн називають write-behind.

       запити (навантаження, що різко стрибає)
                        │
       ┌────────────────┼─────────────────┐
       ▼                 ▼                  ▼
 ┌───────────┐    ┌───────────┐     ┌───────────┐
 │Processing │    │Processing │     │Processing │   ← динамічно
 │  Unit 1   │    │  Unit 2   │     │  Unit N   │     додаються й
 │ (логіка + │    │ (логіка + │     │ (логіка + │     прибираються
 │ дані в    │    │ дані в    │     │ дані в    │     під навантаж.
 │ пам'яті)  │    │ пам'яті)  │     │ пам'яті)  │
 └─────┬─────┘    └─────┬─────┘     └─────┬─────┘
       └────────────────┼────────────────┘
        write-behind: запис у БД пізніше, асинхронно
                        ▼
                   ┌─────────┐
                   │   БД    │
                   └─────────┘

Назва “space” походить від старої концепції tuple space (ідея з JavaSpaces) — “простору”, де дані просто існують у розподіленій пам’яті, доступні звідусіль, а не прив’язані жорстко до однієї бази даних. Саме на цій ідеї свого часу будувалась компанія GigaSpaces; сьогодні схожу роль in-memory data grid виконують, наприклад, Hazelcast чи Apache Ignite.

Аналогія: чорна п’ятниця у великому магазині. Замість однієї каси, де все одразу “б’ється” в головну бухгалтерську книгу (і в черзі стоїть натовп), відкривають одразу десятки кас. Кожна каса сама рахує свою готівку (processing unit зі своїми даними в пам’яті), а звіряються з головною книгою (БД) тільки ввечері, оптом.

Плюси:

  • Екстремальна горизонтальна еластичність: processing units додаються й прибираються на льоту залежно від навантаження.
  • База даних більше не вузьке горлечко — а це головна причина падінь систем саме під піковим навантаженням.
  • Дуже низька латентність: дані читаються й пишуться в оперативній пам’яті, а не на диску при кожному запиті.

Мінуси:

  • Висока складність: підтримувати консистентність копій даних між десятками вузлів у пам’яті — нетривіальна інженерна задача.
  • Ризик втрати даних, якщо вузол впаде до того, як write-behind встиг зберегти зміни в базі даних (пом’якшується реплікацією всередині самого data grid, але повністю не зникає).
  • Дорожче: оперативна пам’ять на багатьох вузлах коштує помітно більше за дисковий простір звичайної бази даних.
  • Значно менше інженерів мають реальний досвід із цим паттерном, ніж із “звичайними” мікросервісами чи базами даних.
  • Overkill, якщо у системи немає насправді екстремальних і непередбачуваних стрибків навантаження — для переважної більшості застосунків це невиправдана складність.

Event-Driven і Space-Based у цю таблицю навмисно не внесені — вони не про “скільки сервісів”, а про інші осі. Event-Driven — про спосіб комунікації, і накладається на будь-який зі стилів вище. Space-Based — про специфічне рішення проблеми піків навантаження, і теж може комбінуватися, наприклад, із мікросервісами.

Який стиль обрати

  • Стартап, MVP, невелика команда → Моноліт. Найшвидший старт, найменший інфраструктурний overhead. Розділяти рано.
  • Моноліт виріс, команда теж, але повноцінні мікросервіси — це overkill → Service-Based Architecture. Найдешевший спосіб отримати незалежний деплой без розподіленої бази даних і event-шини.
  • Великий enterprise з десятками legacy-систем (мейнфрейми, різні епохи, різні відділи), потрібне повторне використання сервісів усією компанією → SOA, хоча сьогодні її нерідко замінюють легшими комбінаціями API gateway і мікросервісоподібних рішень навіть у великих компаніях.
  • Великий продукт, багато незалежних команд, потрібне незалежне масштабування й деплой кожної частини, DevOps-культура вже зріла → Мікросервіси.
  • Потрібна слабка зв’язаність компонентів, real-time потоки, реакція на події замість прямих запитів → Event-Driven, найчастіше накладений на мікросервіси.
  • Непередбачувані екстремальні піки навантаження (розпродажі, квитки, вірусний контент) → Space-Based Architecture, і то лише якщо звичайне масштабування бази даних (read-репліки, шардинг, кешування) вже не вистачає.

Резюме

  • Моноліт і мікросервіси — це два краї одного спектра, а не єдині два варіанти в принципі.
  • Service-Based Architecture — прагматичний компроміс: незалежний деплой сервісів, але спільна база даних. Найчастіший реальний перший крок при розпилюванні моноліту.
  • SOA — попередник мікросервісів із централізованою ESB-шиною. Чудово інтегрує legacy enterprise-системи, але ESB легко перетворюється на прихований новий моноліт.
  • Event-Driven Architecture — не про кількість сервісів, а про спосіб комунікації: події замість прямих викликів. Часто комбінується з мікросервісами.
  • Space-Based Architecture — нішевий паттерн для екстремальних, непередбачуваних піків навантаження, де базу даних прибирають із критичного шляху запиту на користь розподіленої пам’яті.
  • Жоден стиль не є “правильним за замовчуванням” — кожен вирішує конкретну проблему конкретного масштабу. Вибір архітектури — завжди trade-off між простотою і гнучкістю/масштабованістю, а не пошук ідеального рішення.
