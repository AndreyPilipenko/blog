Kubernetes словник: усі ключові визначення від Pod до Gateway API

1. Велика картина: як терміни пов’язані між собою

Kubernetes працює так: ти описуєш бажаний стан («хочу 3 копії web:2.0 по 256 MiB пам’яті, доступні за адресою shop.example.com»), а система безперервно приводить реальний стан до бажаного. Майже кожен термін нижче — це або об’єкт (опис того, що ти хочеш), або контролер (механізм, який це втілює).

2. Кластер і архітектура

Kubernetes (K8s) — це оркестратор контейнерів: платформа, яка запускає контейнери на групі серверів, перезапускає їх при падінні, масштабує, оновлює без простою і дає їм мережу та сховище. «8» в K8s — це вісім літер між K і s.

Cluster (кластер) — це набір машин (нод) під керуванням одного control plane, які разом поводяться як один великий комп’ютер для запуску контейнерів.

Node (нода, вузол) — це машина (віртуалка або залізо), на якій реально запускаються Pod. На кожній ноді працюють kubelet, container runtime і зазвичай kube-proxy.

  • Раніше казали master і worker, тепер — control plane node і worker node.
  • Стан ноди описують conditions: Ready, MemoryPressure, DiskPressure, PIDPressure, NetworkUnavailable. NotReady означає, що kubelet перестав звітувати або щось зламалося на ноді (мережа, CNI, runtime).

Control Plane (площина керування) — це «мозок» кластера: компоненти, які зберігають бажаний стан, приймають рішення (де запустити Pod, скільки їх має бути) і реагують на зміни. Це kube-apiserver, etcd, kube-scheduler, kube-controller-manager і, у хмарі, cloud-controller-manager.

  • У керованих кластерах (EKS, GKE, AKS) control plane від тебе приховано: ним керує провайдер.

kube-apiserver — це єдина вхідна точка в кластер: REST API, через який усі (kubectl, kubelet, контролери, CI) читають і змінюють об’єкти. Він виконує автентифікацію, авторизацію, admission і лише після цього пише в etcd.

  • Ніхто, крім apiserver, не звертається до etcd напряму.
  • Він не зберігає стану, тому його масштабують горизонтально за балансувальником.

etcd — це розподілене консистентне key-value сховище (консенсус за алгоритмом Raft), у якому лежить увесь стан кластера: кожен Deployment, Secret, Pod, Node.

  • Втратити etcd без бекапу означає втратити кластер: контейнери ще якийсь час працюватимуть, але керувати ними вже не буде чим.
  • Кворум — це більшість членів: кластер із 3 членів переживе втрату одного, із 5 — двох. Тому кількість членів etcd завжди непарна.

kube-scheduler — це компонент, який для кожного нового Pod без ноди вибирає, на яку ноду його поставити. Спершу він відфільтровує ноди, що не підходять (мало ресурсів, taint, affinity), потім оцінює решту й обирає найкращу.

  • Scheduler не запускає Pod, він лише записує рішення (binding, поле spec.nodeName). Запускає Pod kubelet.

kube-controller-manager — це процес, у якому працюють вбудовані контролери: Deployment, ReplicaSet, StatefulSet, Job, Node, EndpointSlice, ServiceAccount та інші. Кожен стежить за своїм типом об’єктів і доводить реальність до бажаного стану.

cloud-controller-manager — це компонент control plane, який інтегрує кластер із хмарою: створює хмарні балансувальники для Service типу LoadBalancer, прибирає з кластера ноди, яких уже немає в хмарі, налаштовує маршрути.

kubelet — це агент на кожній ноді, який отримує від apiserver список Pod, призначених на його ноду, запускає їхні контейнери через container runtime, монтує томи, виконує probes і звітує статус назад.

  • kubelet — це не контейнер, а сервіс на хості (зазвичай systemd).
  • Якщо kubelet ліг, нода через деякий час переходить у NotReady.

kube-proxy — це компонент на кожній ноді, який реалізує Service: програмує в ядрі правила (iptables, IPVS або nftables), за якими трафік на віртуальну IP сервісу потрапляє на один із реальних Pod.

  • У сучасних режимах він сам трафік не проксіює, лише пише правила в ядро.
  • Cilium та деякі інші CNI можуть повністю замінити kube-proxy на eBPF.

Container runtime (середовище виконання контейнерів) — це програма, яка фізично запускає контейнери на ноді: containerd або CRI-O. kubelet спілкується з нею через CRI.

  • Docker як runtime (dockershim) прибрали з Kubernetes у версії 1.24. Образи, зібрані Docker, працюють як і раніше: це звичайні OCI-образи. Як влаштований сам стек containerd і runc, розібрано в статті Docker зсередини.

CRI (Container Runtime Interface) — це стандартний gRPC-інтерфейс між kubelet і container runtime. Завдяки йому kubelet байдуже, що працює під ним, containerd чи CRI-O.

CNI (Container Network Interface) — це стандарт плагінів, які дають Pod мережу: виділяють IP, створюють інтерфейси, налаштовують маршрути між нодами. Приклади: Calico, Cilium, Flannel, AWS VPC CNI.

  • Без CNI-плагіна ноди залишаються NotReady, а Pod без мережі.

CSI (Container Storage Interface) — це стандарт драйверів сховища: як Kubernetes створює, підключає і монтує диски (EBS, Ceph, NFS, Longhorn тощо) без зміни коду самого Kubernetes.

kubectl — це CLI-клієнт до kube-apiserver. Усе, що він робить, — це HTTP-запити до API.

kubeconfig — це файл (за замовчуванням ~/.kube/config) з адресами кластерів, обліковими даними і контекстами.

Context (контекст) — це іменована трійка «кластер + користувач + namespace за замовчуванням» у kubeconfig. Перемкнув контекст — перемкнув, з яким кластером і від чийого імені працюєш.

  • Класична аварія: здається, що ти в контексті staging, а насправді в prod.

Managed Kubernetes (керований Kubernetes) — це кластер, у якому control plane, його оновлення і доступність бере на себе хмарний провайдер: Amazon EKS, Google GKE, Azure AKS. Тобі лишаються ноди і навантаження.

kubeadm — це офіційний інструмент для розгортання кластера на власних машинах: ініціалізує control plane, генерує сертифікати, приєднує ноди.

kind / minikube / k3s — це легкі варіанти Kubernetes: kind і minikube для локальних експериментів і CI, k3s — компактний дистрибутив для edge і невеликих інсталяцій.

3. Об’єкти та API: як Kubernetes «думає»

Desired state (бажаний стан) — це те, що ти описав у маніфесті (у полі spec): скільки реплік, який образ, які ресурси. Kubernetes нічого не «виконує один раз», а постійно звіряє реальність із цим описом.

Current state (поточний стан) — це те, що є насправді. Контролери і kubelet записують його в поле status об’єкта.

Reconciliation loop (цикл узгодження) — це базовий механізм Kubernetes: контролер нескінченно повторює «подивися на поточний стан → порівняй із бажаним → зроби крок, щоб їх зблизити». Тому вбитий Pod повертається сам, а прибрати його назавжди можна, лише змінивши бажаний стан (наприклад, зменшивши replicas).

Controller (контролер) — це процес, що реалізує reconciliation loop для певного типу об’єктів. Deployment controller стежить за Deployment, ReplicaSet controller — за ReplicaSet і так далі.

Object (об’єкт) — це запис у Kubernetes API, що описує частину бажаного стану: конкретний Deployment web, конкретний Service db. Майже кожен об’єкт має поля apiVersion, kind, metadata, spec і status.

Resource (ресурс API) — це тип об’єктів, доступний за певним шляхом в API: pods, deployments, services.

  • Обережно: «ресурсами» також називають CPU і пам’ять (див. requests і limits). Це різні речі.

Kind — це тип об’єкта в маніфесті: Pod, Deployment, Service.

apiVersion / API group (група API) — це група і версія API, до якої належить kind: v1 (core-група: Pod, Service, ConfigMap), apps/v1 (Deployment, StatefulSet), networking.k8s.io/v1 (Ingress, NetworkPolicy), gateway.networking.k8s.io/v1 (Gateway API).

  • Версії проходять шлях v1alpha1 → v1beta1 → v1. Застарілі версії з часом видаляють, тому старі маніфести після апгрейду кластера іноді перестають застосовуватися.

Manifest (маніфест) — це YAML- або JSON-файл з описом одного чи кількох об’єктів, який застосовують через kubectl apply.

spec і status — spec — це те, що ти хочеш (пише користувач), status — це те, що є (пише Kubernetes).

Declarative vs imperative (декларативний vs імперативний підхід) — декларативний: «ось файл із бажаним станом, приведи кластер до нього» (kubectl apply). Імперативний: «виконай цю дію» (kubectl run, kubectl scale, kubectl edit). У проді працюють декларативно і через Git, інакше стан кластера розходиться з репозиторієм.

Namespace (простір імен) — це логічний розділ усередині кластера: простір імен для об’єктів і межа для RBAC-прав, квот і політик. В одному namespace не може бути двох Deployment з ім’ям web, у різних — може.

  • Namespace не ізолює мережу: Pod з різних namespace за замовчуванням бачать один одного. Для ізоляції потрібні NetworkPolicy.
  • Не всі об’єкти живуть у namespace: Node, PersistentVolume, StorageClass, ClusterRole і сам Namespace — кластерні.
  • Стартові namespace: default, kube-system, kube-public, kube-node-lease.

Label (мітка) — це пара ключ=значення на об’єкті (app=web, env=prod), за якою інші об’єкти його знаходять. Мітки — це клей Kubernetes: Service знаходить свої Pod за мітками, ReplicaSet рахує свої Pod за мітками.

Selector (селектор) — це запит за мітками: «усі Pod, де app=web і tier=frontend». Селектори використовують Service, ReplicaSet, Deployment, NetworkPolicy, kubectl get -l.

  • Якщо селектор Service не збігається з мітками Pod, у сервісу немає endpoints і трафік нікуди не йде. Одна з найчастіших помилок.

Annotation (анотація) — це пара ключ=значення для метаданих, за якими не шукають: автор, git commit, налаштування для ingress-контролера чи Prometheus. На відміну від міток, анотації не беруть участі в селекторах і можуть бути довгими.

Owner reference (посилання на власника) — це запис у metadata, що вказує на батьківський об’єкт: Pod знає свій ReplicaSet, ReplicaSet — свій Deployment.

Garbage collection (каскадне видалення) — це механізм, який за owner reference видаляє дочірні об’єкти разом із батьківським: видалив Deployment → зникли його ReplicaSet → зникли Pod.

Finalizer (фіналізатор) — це «замок» у metadata.finalizers, який не дає об’єкту остаточно видалитися, доки певний контролер не виконає прибирання (наприклад, не видалить хмарний диск чи балансувальник). Поки замок не знято, об’єкт висить у Terminating.

  • Namespace, який вічно «Terminating», — майже завжди об’єкт усередині з фіналізатором, контролер якого вже не працює.

Event (подія) — це короткоживучий об’єкт-запис про те, що сталося: Scheduled, Pulling, FailedScheduling: 0/3 nodes are available, BackOff. Перше, що дивляться при дебазі (kubectl describe, kubectl get events).

  • Події зберігаються недовго, за замовчуванням близько години.

4. Pod і контейнери

Container (контейнер) — це звичайний Linux-процес, ізольований через namespaces (що він бачить) і обмежений через cgroups (скільки він може спожити), запущений з образу.

Image (образ) — це незмінний пакет із файловою системою і метаданими (команда запуску, змінні оточення), з якого стартує контейнер. Посилання на образ має вигляд registry/repo:tag або registry/repo@sha256:digest.

  • Тег latest — це не «остання версія», а просто тег за замовчуванням. У проді використовують фіксований тег або digest.

imagePullPolicy — це правило, коли kubelet завантажує образ: IfNotPresent (лише якщо його немає на ноді), Always (звіряється з реєстром при кожному запуску), Never. Для тегу latest або образу без тегу за замовчуванням діє Always, для решти — IfNotPresent.

Pod (под) — це найменша одиниця, яку Kubernetes запускає і планує: обгортка навколо одного або кількох контейнерів, які завжди живуть на одній ноді, мають одну IP-адресу, спільний мережевий простір (бачать одне одного через localhost) і можуть ділити томи.

  • Kubernetes не запускає контейнери напряму, він запускає Pod.
  • Pod смертний і одноразовий. Помер — його не «воскрешають», а створюють новий Pod з новим ім’ям і новою IP. Тому до Pod не звертаються напряму за IP, для цього є Service.
  • «Голий» Pod без контролера після падіння ноди ніхто не відновить. У проді Pod створюють через Deployment, StatefulSet, DaemonSet або Job.
  • Кілька контейнерів в одному Pod тримають лише тоді, коли вони нероздільні (застосунок + sidecar). Застосунок і базу даних в один Pod не кладуть.

Pause container — це крихітний службовий контейнер, який створюється першим у кожному Pod і тримає його мережевий namespace. Решта контейнерів Pod підключаються до цього namespace, тому IP належить Pod, а не окремому контейнеру.

Init container (ініціалізуючий контейнер) — це контейнер, який виконується до основних контейнерів, по черзі і до успішного завершення: дочекатися бази, застосувати міграції, згенерувати конфіг. Поки всі init-контейнери не завершилися з кодом 0, застосунок не стартує.

Sidecar container (допоміжний контейнер) — це контейнер, що працює поруч з основним протягом усього життя Pod: проксі service mesh (Envoy), збирач логів, агент секретів.

  • Нативний sidecar (стабільний з Kubernetes 1.33) — це init-контейнер з restartPolicy: Always: він стартує раніше за застосунок і зупиняється після нього. Це закрило стару проблему, коли Job не міг завершитися, бо sidecar продовжував працювати.

Ephemeral container (тимчасовий контейнер) — це контейнер, який додають у вже запущений Pod для дебагу (kubectl debug), наприклад з busybox або netshoot, коли в образі застосунку немає навіть shell (distroless).

Static Pod (статичний Pod) — це Pod, яким kubelet керує напряму з файлу на диску ноди (зазвичай /etc/kubernetes/manifests), без участі apiserver. Так у кластерах kubeadm запускаються самі компоненти control plane. В API видно лише його дзеркальну копію (mirror pod).

restartPolicy — це правило, що робити з контейнером, коли він завершився: Always (за замовчуванням, для довгоживучих сервісів), OnFailure (перезапуск лише при ненульовому коді виходу, для Job), Never.

Pod template (шаблон Pod) — це опис Pod (spec.template) всередині Deployment, ReplicaSet, StatefulSet, DaemonSet або Job: форма, за якою контролер штампує Pod.

5. Контролери: ReplicaSet, Deployment, StatefulSet, DaemonSet, Job

Workload (робоче навантаження) — це застосунок, запущений у Kubernetes, а також загальна назва для контролерів, що керують Pod: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob.

Replicas (репліки) — це бажана кількість однакових Pod у Deployment, ReplicaSet або StatefulSet.

ReplicaSet — це контролер, єдина задача якого — тримати рівно N Pod, що відповідають його селектору. Стало менше — створює нові з шаблону, стало більше — видаляє зайві.

  • ReplicaSet не вміє оновлювати: якщо змінити образ у його шаблоні, наявні Pod залишаться старими, а новий шаблон застосується лише до нових Pod.
  • Тому ReplicaSet майже ніколи не створюють руками: ним керує Deployment.
  • Ім’я виглядає як web-7d9f8c6b5, де суфікс — це pod-template-hash, хеш шаблону Pod.
  • Його попередник ReplicationController застарів, його не використовують.

Deployment — це контролер для stateless-застосунків, який описує бажаний стан застосунку (образ, кількість реплік, стратегію оновлення) і керує ReplicaSet’ами так, щоб оновлювати застосунок без простою і мати змогу відкотитися.

  • Ланцюжок: Deployment → ReplicaSet → Pod.
  • Кожна зміна spec.template (образ, env, ресурси, мітки Pod) створює новий ReplicaSet. Deployment поступово скейлить новий угору, а старий униз — це і є rolling update.
  • Старі ReplicaSet з нулем реплік залишаються як історія ревізій (revisionHistoryLimit, за замовчуванням 10). Rollback просто скейлить старий ReplicaSet назад.
  • Зміна лише replicas новий ReplicaSet не створює: це масштабування, а не оновлення.
  • Pod у Deployment взаємозамінні: випадкові імена, жодного власного диска.

StatefulSet — це контролер для stateful-застосунків (бази даних, Kafka, ZooKeeper, etcd), де кожна копія має власну ідентичність. Кожен Pod отримує:

  • стабільне ім’я з порядковим номером: db-0, db-1, db-2 замість випадкового суфікса;
  • стабільне DNS-ім’я через headless Service: db-0.db.prod.svc.cluster.local;
  • власний PVC з volumeClaimTemplates, який переходить до Pod з тим самим номером після перестворення;
  • впорядкований запуск і масштабування: db-0 стартує першим, а при зменшенні видаляється останнім.

Що важливо знати про StatefulSet:

  • StatefulSet не налаштовує реплікацію бази за тебе, він дає лише стабільні ім’я і диск. Як репліки синхронізуються, вирішує сама база або оператор.
  • При видаленні StatefulSet його PVC за замовчуванням не видаляються, дані зберігаються.

DaemonSet — це контролер, який запускає по одному Pod на кожній ноді (або на кожній ноді з певними мітками). Додалася нода — на ній автоматично з’явився Pod.

  • Для чого: агенти логів (Fluent Bit), моніторингу (node-exporter), CNI- і CSI-драйвери, kube-proxy.

Job — це контролер для задач, які мають завершитися: запустити Pod, дочекатися успішного виходу (код 0) і зупинитися. Міграції, бекапи, пакетна обробка.

  • completions — скільки успішних завершень потрібно; parallelism — скільки Pod працює одночасно; backoffLimit — скільки спроб, після яких Job вважається проваленим (за замовчуванням 6); activeDeadlineSeconds — загальний таймаут.
  • ttlSecondsAfterFinished автоматично прибирає завершені Job.

CronJob — це контролер, який за розкладом у форматі cron створює Job: щоночі бекап, щогодини звіт.

  • concurrencyPolicy: Allow (запуски можуть перетинатися), Forbid (пропустити запуск, якщо попередній ще йде), Replace (зупинити попередній і запустити новий).
  • Розклад за замовчуванням рахується в часовому поясі kube-controller-manager (зазвичай UTC). Явно задати пояс можна полем timeZone.

6. Оновлення і rollout

Rollout (викатка) — це процес переходу Deployment (а також StatefulSet чи DaemonSet) від однієї версії шаблону Pod до іншої. Кожен rollout створює нову ревізію.

Revision (ревізія) — це пронумерована версія шаблону Pod у Deployment. Фізично це один зі збережених ReplicaSet.

Rollback (відкат) — це повернення до попередньої ревізії (kubectl rollout undo): Deployment скейлить старий ReplicaSet угору, а поточний униз. По суті це той самий rolling update, тільки «назад».

RollingUpdate (поступове оновлення) — це стратегія Deployment за замовчуванням: старі Pod замінюються новими поступово, без простою. Нею керують два параметри:

  • maxSurge — скільки Pod понад replicas можна тимчасово створити під час оновлення (за замовчуванням 25%);
  • maxUnavailable — скільки Pod із replicas може бути недоступно під час оновлення (за замовчуванням 25%).
replicas=3, maxSurge=1, maxUnavailable=0  →  максимум 4 Pod, мінімум 3 доступні

крок 0    [v1] [v1] [v1]             —
крок 1    [v1] [v1] [v1]             [v2]
крок 2    [v1] [v1]                  [v2] [v2]
крок 3    [v1]                       [v2] [v2] [v2]
крок 4    —                          [v2] [v2] [v2]    ← v1 лишається з replicas=0 для rollback
  • Rolling update вважає новий Pod доступним лише після того, як він пройшов readiness probe. Без неї Kubernetes вважатиме Pod готовим одразу після старту контейнера, навіть якщо застосунок ще вантажиться.

Recreate (перестворення) — це стратегія, за якої спершу видаляються всі старі Pod, і лише потім створюються нові. Є простій, зате дві версії ніколи не працюють одночасно. Потрібна, коли застосунок не терпить двох версій поруч або тримає ексклюзивний RWO-диск.

Blue/Green — це стратегія, за якої поруч зі старою версією (blue) повністю піднімається нова (green), а трафік перемикається одним рухом (зміною селектора Service або маршруту). У Deployment її немає: роблять двома Deployment або через Argo Rollouts чи Flagger.

Canary (канаркове оновлення) — це стратегія, за якої нова версія спершу отримує малу частку трафіку (5%, 20% …), і цю частку збільшують, поки метрики в нормі. У Gateway API робиться вагами в HTTPRoute, автоматизується через Argo Rollouts або Flagger.

minReadySeconds — це скільки секунд новий Pod має пробути Ready без падінь, перш ніж Deployment вважатиме його доступним і перейде до наступного кроку.

progressDeadlineSeconds — це скільки секунд Deployment може не просуватися, перш ніж rollout отримає статус «провалено» (за замовчуванням 600). Автоматичного відкату при цьому немає, лише позначка в статусі, на яку має зреагувати CI/CD.

7. Ресурси: requests, limits, QoS

На цьому розділі найчастіше «пливуть» на співбесідах, і саме через нього найчастіше падають застосунки в проді.

Requests (запити ресурсів) — це гарантований мінімум CPU і пам’яті, який контейнер просить для себе. Scheduler дивиться лише на requests: Pod поставлять тільки на ту ноду, де сума requests усіх її Pod разом із новим не перевищує allocatable ноди.

  • Requests — це бронювання, а не реальне споживання. Pod може просити 1 CPU і використовувати 0.05, але для scheduler цей 1 CPU на ноді вже зайнятий.
  • CPU requests також визначають частку процесорного часу під час конкуренції: коли нода перевантажена, контейнер з request 1 CPU отримує вдвічі більше часу, ніж контейнер з 500m (через cgroup cpu.weight).
  • Від requests рахується відсоток використання в HPA.
  • Немає requests — scheduler вважає, що Pod нічого не потребує, і може напхати на ноду більше, ніж вона витягне.

Limits (ліміти ресурсів) — це жорстка стеля, вище якої контейнер ресурсів не отримає. Її забезпечує ядро через cgroups, і для CPU та пам’яті вона працює по-різному:

  • CPU limit — контейнер, що впирається в ліміт, тротлиться: процес не вбивають, він просто чекає наступного періоду планування (100 мс). Виглядає це як «застосунок раптом гальмує і latency стрибає», хоча CPU на ноді вільний.
  • Memory limit — контейнер, що перевищив ліміт, вбиває OOM killer ядра: статус OOMKilled, exit code 137, рестарт.
  • Якщо задати лише limits без requests, requests автоматично стануть рівними limits.
  • Сума limits на ноді може перевищувати її ємність (overcommit). Це нормально, поки всі Pod не захочуть свій ліміт одночасно.
  • Поширена практика (не догма): для пам’яті limit ставити завжди і часто рівним request, бо пам’ять нестислива. Для CPU limit або не ставити зовсім, або ставити з великим запасом, щоб не ловити тротлінг.

Що відбувається з контейнером залежно від споживання:

CPU units (одиниці CPU) — це спосіб записати CPU: 1 = одне ядро (vCPU), 500m = пів ядра (m — мілі-ядра, тисячні частки), 100m = 0.1 ядра.

Memory units (одиниці пам’яті) — це байти із суфіксами: Ki, Mi, Gi — двійкові (1 Mi = 1 048 576 байт), K, M, G — десяткові (1 M = 1 000 000 байт).

  • Пастка: memory: 512m — це 0.512 байта (m означає «мілі»), а не 512 мегабайт. Правильно писати 512Mi.

CPU throttling (тротлінг CPU) — це примусове призупинення процесів контейнера, коли вони вичерпали свою CPU-квоту (limit) у поточному 100-мілісекундному періоді. Видно в метриці container_cpu_cfs_throttled_periods_total.

  • Багатопотоковий застосунок з limit 1 CPU може на чотирьох потоках «з’їсти» всю квоту за перші 25 мс періоду і решту 75 мс стояти.

OOMKilled — це статус контейнера, якого ядро вбило за перевищення memory limit (exit code 137 = 128 + номер сигналу SIGKILL 9).

  • Не плутати з eviction: OOMKilled — це ядро вбило один контейнер за його власний ліміт; eviction — це kubelet виселив цілий Pod, бо на ноді закінчується пам’ять.

QoS class (клас якості обслуговування) — це клас, який Kubernetes автоматично присвоює Pod за його requests і limits. Він визначає, кого першим приносять у жертву, коли на ноді закінчується пам’ять:

  • Guaranteed — у кожного контейнера задані requests і limits і для CPU, і для пам’яті, причому requests = limits. Йде під ніж останнім.
  • Burstable — хоча б у одного контейнера є request або limit, але умови Guaranteed не виконані. Середина черги.
  • BestEffort — жодних requests і limits ні в кого. Йде під ніж першим.
  • Точніше, kubelet при виселенні враховує ще й пріоритет Pod і те, наскільки Pod перевищив свої requests, але QoS — головний орієнтир.

Allocatable (доступні для Pod ресурси) — це скільки ресурсів ноди реально доступно для Pod: Capacity мінус kube-reserved, system-reserved і поріг eviction. Нода на 16 GiB віддає під Pod помітно менше, і scheduler рахує саме від allocatable.

Overcommit (перепідписка) — це ситуація, коли сума limits усіх Pod на ноді більша за її реальну ємність. Ставка на те, що піки в Pod не збігатимуться.

Eviction (виселення) — це примусове видалення Pod з ноди kubelet’ом, коли ноді бракує нестисливих ресурсів: пам’яті, диска, inode чи PID (стани MemoryPressure, DiskPressure, PIDPressure). Pod отримує статус Evicted, а контролер створює заміну на іншій ноді.

  • Існує й виселення через API (його використовує kubectl drain), і воно, на відміну від виселення через тиск на ноді, поважає PodDisruptionBudget.

LimitRange — це об’єкт у namespace, який задає дефолтні requests і limits для контейнерів, що їх не вказали, а також мінімум і максимум для одного контейнера чи Pod.

ResourceQuota (квота ресурсів) — це об’єкт у namespace, який обмежує сумарне споживання всього namespace: суму requests і limits CPU та пам’яті, кількість Pod, Service і PVC, обсяг сховища.

  • Якщо в namespace є квота на CPU або пам’ять, Pod без відповідних requests/limits буде відхилено. Тому квоту зазвичай ставлять разом із LimitRange, який підставляє дефолти.

In-place Pod resize (зміна ресурсів на льоту) — це зміна requests і limits CPU та пам’яті у запущеного Pod без його перестворення (стабільна з Kubernetes 1.35, через subresource resize у Pod). Зміна ресурсів у шаблоні Deployment, як і раніше, запускає звичайний rollout.

8. Планування: куди потрапить Pod

Scheduling (планування) — це вибір ноди для Pod. Відбувається один раз: прив’язаний до ноди Pod Kubernetes сам не переносить, навіть якщо з’явилася краща нода. «Переїзд» — це завжди видалення Pod і створення нового.

nodeSelector — це найпростіший спосіб прив’язати Pod до нод: «лише на ноди з міткою disktype=ssd».

Node affinity (спорідненість з нодою) — це розширена версія nodeSelector з виразами (In, NotIn, Exists, Gt …) і двома режимами: requiredDuringSchedulingIgnoredDuringExecution (жорстка умова: не виконано — Pod висить у Pending) і preferredDuringSchedulingIgnoredDuringExecution (побажання з вагою).

  • IgnoredDuringExecution у назві означає: якщо мітки ноди змінилися вже після запуску, запущений Pod не виселяють.

Pod affinity (спорідненість з Pod) — це правило «постав мій Pod поруч із Pod, що мають такі мітки» (на ту саму ноду або в ту саму зону). Наприклад, кеш поруч із застосунком.

Pod anti-affinity (антиспорідненість) — це правило «не стався мій Pod поруч із Pod, що мають такі мітки». Класичне застосування: розкидати репліки одного Deployment по різних нодах, щоб падіння однієї ноди не забрало всі копії.

Topology key (ключ топології) — це мітка ноди, яка визначає, що саме вважається «поруч»: kubernetes.io/hostname (та сама нода) або topology.kubernetes.io/zone (та сама зона доступності).

Topology spread constraints (обмеження розподілу) — це правило рівномірно розподіляти Pod по доменах (нодах, зонах). Наприклад, maxSkew: 1 по зонах означає, що кількість Pod у будь-яких двох зонах відрізняється не більш ніж на 1. Сучасніша і гнучкіша заміна anti-affinity для розкидання реплік.

Taint (пляма) — це позначка на ноді, яка відштовхує Pod: «сюди не можна, хіба що ти це терпиш». Формат key=value:effect, ефекти такі:

  • NoSchedule — нові Pod без відповідної toleration сюди не плануються;
  • PreferNoSchedule — бажано не планувати;
  • NoExecute — нові не плануються, а вже запущені Pod без toleration виселяються.
  • Приклад: на control plane нодах стоїть taint node-role.kubernetes.io/control-plane:NoSchedule, тому звичайні Pod туди не потрапляють.

Toleration (толерантність) — це позначка на Pod, яка дозволяє йому ігнорувати певний taint.

  • Toleration дозволяє Pod потрапити на ноду з taint, але не змушує його туди йти. Щоб Pod працював саме на виділених нодах, потрібні taint, toleration і node affinity разом.

PriorityClass (клас пріоритету) — це об’єкт, що задає числовий пріоритет Pod. Від нього залежить порядок у черзі scheduler і preemption.

Preemption (витіснення) — це ситуація, коли для Pod з високим пріоритетом немає місця, і scheduler видаляє Pod з нижчим пріоритетом, щоб звільнити для нього ноду.

Descheduler — це окремий компонент (не входить у Kubernetes з коробки), який виселяє Pod, розміщені неоптимально (перекіс по нодах, порушені правила affinity), щоб scheduler поставив їх краще.

PodDisruptionBudget, PDB (бюджет збоїв) — це обмеження на добровільні збої: «з Pod з міткою app=web одночасно має бути доступно щонайменше 2» (minAvailable) або «недоступним може бути щонайбільше 1» (maxUnavailable). Його поважають kubectl drain, оновлення нод і cluster autoscaler.

  • PDB не захищає від недобровільних збоїв: падіння ноди, OOM, kernel panic.
  • PDB з maxUnavailable: 0 (або з minAvailable, рівним кількості реплік) назавжди заблокує drain.

Voluntary / involuntary disruption (добровільний / недобровільний збій) — добровільні збої ініціює людина або автоматика: drain, апгрейд, зменшення кількості нод. Недобровільні трапляються самі: апаратний збій, падіння ноди, OOM, втрата мережі.

Cordon — це позначити ноду як непридатну для нових Pod (SchedulingDisabled). Уже запущені Pod продовжують працювати.

Drain — це cordon плюс виселення всіх Pod з ноди (з повагою до PDB і graceful shutdown), щоб ноду можна було обслуговувати. Pod від DaemonSet при цьому зазвичай пропускають.

Uncordon — це повернення ноди до планування після обслуговування.

9. Здоров’я і життєвий цикл: фази, probes, завершення

Pod phase (фаза Pod) — це загальний стан Pod, одне з п’яти значень:

  • Pending — Pod прийнято, але запущено ще не всі контейнери: чекає на планування, завантажує образ, монтує томи. Якщо не вистачило ноди, причина буде в подіях (FailedScheduling);
  • Running — Pod прив’язаний до ноди, і хоча б один контейнер працює, стартує або перезапускається;
  • Succeeded — усі контейнери завершилися успішно і перезапускатися не будуть (типово для Job);
  • Failed — усі контейнери завершилися, і хоча б один — з помилкою;
  • Unknown — стан невідомий, зазвичай через втрату зв’язку з нодою.
  • CrashLoopBackOff, ImagePullBackOff, Terminating, Evicted — це не фази, а причини і стани, які kubectl get pods показує в колонці STATUS.

Container state (стан контейнера) — це стан окремого контейнера: Waiting (з причиною, наприклад ContainerCreating або CrashLoopBackOff), Running або Terminated (з exit code і причиною, наприклад OOMKilled, Completed, Error).

Pod conditions (умови Pod) — це набір прапорців у статусі Pod, серед них PodScheduled, Initialized, ContainersReady, Ready. Трафік від Service Pod отримує лише тоді, коли Ready=True.

CrashLoopBackOff — це стан, коли контейнер стартує, падає, kubelet його перезапускає, а він знову падає. Між спробами kubelet робить паузу, яка зростає експоненційно (10 с, 20 с, 40 с … до 5 хвилин). Це симптом, а не причина: причину шукають у логах попереднього запуску (kubectl logs --previous) і в exit code.

ImagePullBackOff / ErrImagePull — це стан, коли kubelet не може завантажити образ: помилка в імені чи тезі, немає доступу до приватного реєстру (не вказано imagePullSecrets), спрацював rate limit реєстру. Між спробами діє така сама експоненційна пауза.

Probe (перевірка) — це перевірка, яку kubelet періодично виконує над контейнером: HTTP GET (успіх — код 200–399), TCP-з’єднання, команда всередині контейнера (успіх — exit 0) або gRPC health check. Є три види перевірок, і вони роблять різні речі.

Liveness probe (перевірка живучості) — це перевірка «чи живий процес, чи не завис». Провалилася кілька разів поспіль — kubelet перезапускає контейнер.

  • Liveness не повинна перевіряти зовнішні залежності (базу, інші сервіси). Інакше впала база → провалилася liveness → перезапускаються всі Pod одночасно, і проблема стає тільки гіршою.

Readiness probe (перевірка готовності) — це перевірка «чи готовий контейнер приймати трафік». Провалилася — Pod прибирають з endpoints Service (трафік на нього не йде), але не перезапускають. Знову проходить — Pod повертають.

  • Саме readiness визначає, чи вважає rolling update новий Pod доступним.

Startup probe (перевірка запуску) — це перевірка «чи застосунок уже стартував». Поки вона не пройшла, liveness і readiness не виконуються. Потрібна повільним застосункам (Java, прогрів великого кешу), щоб liveness не вбивала їх ще під час запуску.

Graceful shutdown (коректне завершення) — це послідовність, через яку проходить Pod при видаленні:

  1. Pod отримує стан Terminating і одночасно з цим прибирається з endpoints Service;
  2. виконується preStop hook, якщо він є;
  3. контейнери отримують SIGTERM: застосунок має доробити поточні запити і вийти;
  4. якщо контейнер не завершився за terminationGracePeriodSeconds (за замовчуванням 30 с, разом із часом preStop), він отримує SIGKILL.
  • Через те що крок 1 відбувається паралельно, трафік ще кілька секунд може йти на Pod, який уже отримав SIGTERM. Тому часто додають preStop із затримкою на 5–10 секунд.

preStop / postStart hooks (хуки життєвого циклу) — це команди або HTTP-запити, які kubelet виконує безпосередньо перед зупинкою контейнера (preStop) або одразу після його старту (postStart).

Exit code (код виходу) — це код завершення процесу контейнера: 0 — успіх, 1 — помилка застосунку, 137 — вбито через SIGKILL (часто OOMKilled або не вклався в grace period), 143 — завершився за SIGTERM.

10. Мережа: Service, DNS, Ingress, Gateway API, NetworkPolicy

Мережева модель

Kubernetes network model (мережева модель Kubernetes) — це базові правила мережі: кожен Pod має власну IP-адресу, будь-який Pod може достукатися до будь-якого іншого Pod за його IP без NAT на будь-якій ноді, а агенти на ноді бачать усі Pod на ній. Як саме це реалізувати (оверлей VXLAN, BGP-маршрутизація, eBPF), вирішує CNI-плагін. Що таке VXLAN і чому через нього ламається MTU, розібрано в статті VLAN і VXLAN.

Pod CIDR / Service CIDR — це два різні діапазони адрес: з Pod CIDR отримують IP Pod (зазвичай кожна нода має свою підмережу), з Service CIDR — віртуальні ClusterIP сервісів. Вони не повинні перетинатися ні між собою, ні з мережею нод.

hostNetwork — це режим, у якому Pod використовує мережевий простір самої ноди: її IP і її порти. Потрібен системним компонентам (CNI, kube-proxy, деякі ingress-контролери), для звичайних застосунків небажаний.

North-south / east-west traffic (трафік північ-південь / схід-захід) — north-south — це трафік ззовні в кластер і назад (Gateway, Ingress, LoadBalancer); east-west — трафік між сервісами всередині кластера (Service, service mesh).

Service

Service (сервіс) — це об’єкт, що дає групі Pod (знайдених за селектором міток) одну стабільну адресу і DNS-ім’я і балансує трафік між ними. Pod приходять і йдуть, їхні IP змінюються, а адреса Service залишається.

  • Service працює на рівні L4 (TCP, UDP, SCTP): він балансує з’єднання, а не HTTP-запити, і нічого не знає про шляхи URL чи заголовки.
  • Типи Service: ClusterIP, NodePort, LoadBalancer, ExternalName.

ClusterIP — це тип Service за замовчуванням: віртуальна IP-адреса, доступна лише всередині кластера. Ця IP не належить жодному інтерфейсу, її «існування» забезпечують правила kube-proxy. Тому ping на ClusterIP зазвичай не відповідає, а curl працює.

NodePort — це тип Service, який додатково відкриває той самий порт (за замовчуванням з діапазону 30000–32767) на кожній ноді: трафік на <IP будь-якої ноди>:<nodePort> потрапляє в сервіс. Включає в себе ClusterIP.

LoadBalancer — це тип Service, для якого хмарний провайдер (через cloud-controller-manager) або MetalLB на власному залізі створює зовнішній балансувальник з публічною IP. Включає в себе NodePort і ClusterIP.

  • Один Service типу LoadBalancer — це один хмарний балансувальник і окремий рядок у рахунку. Для десятків HTTP-сервісів дешевше один спільний Gateway або Ingress.

ExternalName — це тип Service без проксіювання: просто DNS CNAME на зовнішнє ім’я (db.example.com). Дозволяє застосунку звертатися до зовнішньої бази за внутрішнім ім’ям.

Headless Service (безголовий сервіс) — це Service з clusterIP: None: без віртуальної IP і без балансування. DNS-запит до нього повертає IP усіх Pod напряму, а для StatefulSet — ще й окреме ім’я кожного Pod (db-0.db…). Потрібен StatefulSet і клієнтам, які самі обирають, до якого екземпляра йти (бази даних, Kafka).

port / targetPort / nodePort — port — це порт самого Service; targetPort — порт контейнера, куди піде трафік; nodePort — порт на нодах (для NodePort і LoadBalancer).

Endpoints / EndpointSlice — це об’єкти зі списком реальних адрес IP:порт тих Pod, що зараз стоять за Service і пройшли readiness. EndpointSlice — сучасна масштабована версія, у якій список розбито на частини (за замовчуванням до 100 адрес у кожній). Старий API Endpoints оголошено застарілим з Kubernetes 1.33.

  • «Service не працює» → перше питання: чи є в нього endpoints? Список порожній — селектор не збігається з мітками Pod або жоден Pod не Ready.

kube-proxy modes (режими kube-proxy) — це способи, якими kube-proxy реалізує Service: iptables (класичний режим за замовчуванням), ipvs (хеш-таблиці IPVS у ядрі; історично його обирали для кластерів із тисячами сервісів) і nftables (новий режим, стабільний з 1.33, на який переходять з обох попередніх). Альтернатива — eBPF-датаплейн Cilium без kube-proxy взагалі.

DNS

CoreDNS — це DNS-сервер кластера (Deployment у kube-system), який резолвить імена сервісів і Pod.

Service DNS name (DNS-ім’я сервісу) — це ім’я, за яким Pod знаходять сервіси: <service>.<namespace>.svc.cluster.local. З того самого namespace достатньо написати просто <service>, з іншого — <service>.<namespace>.

Ingress

Ingress — це об’єкт із правилами HTTP/HTTPS-маршрутизації ззовні до Service: «shop.example.com/api → service api:80, TLS-сертифікат із Secret shop-tls». Сам по собі він нічого не робить: правила втілює Ingress controller.

  • Ingress API заморожено, нових можливостей у ньому не буде. Усе нестандартне (rewrite, таймаути, canary) робиться анотаціями, специфічними для конкретного контролера, тому маніфести не переносяться між контролерами.
  • Наступник Ingress — Gateway API.

Ingress controller (Ingress-контролер) — це реальний reverse proxy у кластері (ingress-nginx, Traefik, HAProxy, NGINX Ingress Controller від F5 тощо), який читає об’єкти Ingress і налаштовує себе відповідно до них. Без контролера Ingress — це просто записи в etcd.

  • Community-проєкт ingress-nginx оголошено retired: його підтримку припинено в березні 2026. Для нових кластерів дивляться в бік Gateway API.

IngressClass — це об’єкт, який вказує, який контролер обслуговує конкретний Ingress (поле ingressClassName), коли контролерів у кластері кілька.

Gateway API

Gateway API — це сучасний стандарт Kubernetes для маршрутизації вхідного (і внутрішнього) трафіку, наступник Ingress. Це набір CRD у групі gateway.networking.k8s.io, який розділяє відповідальність між ролями і з коробки вміє те, для чого в Ingress були потрібні анотації: маршрутизацію за заголовками, методом і query-параметрами, розподіл трафіку за вагами (canary), редіректи і rewrite, дзеркалювання запитів, а також протоколи, крім HTTP (gRPC, TLS, TCP, UDP).

  • Головна ідея — розділення ролей:
    • провайдер інфраструктури відповідає за GatewayClass;
    • команда платформи — за Gateway;
    • розробники застосунку — за HTTPRoute у своєму namespace.
  • Gateway API — це специфікація, а реалізують її різні контролери: Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, Traefik, Kong, хмарні реалізації (наприклад, GKE Gateway). Маніфести переносяться між ними в межах базових (core) можливостей.
  • CRD Gateway API не входять у «голий» Kubernetes: їх встановлюють окремо, або це робить провайдер чи контролер.

GatewayClass — це кластерний об’єкт, що описує тип шлюзу і контролер, який його реалізує (controllerName). Аналог IngressClass. Зазвичай його один раз створює інсталятор контролера.

Gateway — це об’єкт, що описує конкретну точку входу трафіку: listener’и (порт, протокол, hostname), TLS-сертифікати і з яких namespace маршрутам дозволено до нього прикріплюватися (allowedRoutes). За цим описом контролер піднімає реальний проксі чи балансувальник з адресою.

HTTPRoute — це об’єкт із правилами маршрутизації HTTP: до якого Gateway прикріпитися (parentRefs), для яких hostname, за якими умовами (шлях, заголовки, query, метод) і куди слати трафік (backendRefs — Service з вагами). Живе в namespace застосунку, тому розробники керують своїми маршрутами без доступу до спільного Gateway.

GRPCRoute / TLSRoute / TCPRoute / UDPRoute — це маршрути для інших протоколів: gRPC (за сервісом і методом), TLS passthrough (за SNI), сирий TCP і UDP. GRPCRoute стабільний, а TLS-, TCP- і UDP-маршрути довго були в experimental-каналі, тож їхній статус варто перевіряти для своєї версії Gateway API і свого контролера.

parentRefs / backendRefs — parentRefs у маршруті вказує, до якого Gateway (і якого listener’а) він прикріплюється; backendRefs — куди слати трафік (зазвичай Service, порт і вага).

ReferenceGrant — це об’єкт Gateway API, який явно дозволяє посилання між namespace. Наприклад, HTTPRoute з namespace shop хоче слати трафік на Service у namespace payments: власник payments має створити ReferenceGrant. Так чужа команда не зможе без дозволу «підчепити» твій сервіс до свого маршруту.

Ізоляція і mesh

NetworkPolicy (мережева політика) — це firewall для Pod на рівні L3/L4: які Pod, namespace чи IP-діапазони можуть звертатися до вибраних Pod (ingress) і куди вибрані Pod можуть звертатися самі (egress).

  • За замовчуванням дозволено все. Щойно Pod потрапляє під хоча б одну політику для певного напрямку, у цьому напрямку йому дозволено лише те, що дозволено явно.
  • Застосовує політики CNI. Якщо CNI їх не підтримує (наприклад, чистий Flannel), об’єкти створяться, але нічого не робитимуть, і жодної помилки ти не побачиш.
  • Типовий підхід — «default deny» на namespace плюс точкові дозволи. Не забудь дозволити egress на DNS (порт 53), інакше в namespace перестане резолвитися все.

Service mesh (сервісна сітка) — це шар інфраструктури (Istio, Linkerd, Cilium), який перехоплює трафік між сервісами (через sidecar-проксі або на рівні ноди) і дає mTLS між Pod, ретраї, таймаути, circuit breaking, детальні метрики і трасування без змін у коді застосунку.

11. Конфігурація і секрети

ConfigMap — це об’єкт для несекретної конфігурації у вигляді пар ключ-значення або цілих файлів, яку підключають у Pod як змінні оточення або як файли в томі. Дозволяє запускати один і той самий образ у різних середовищах.

  • Розмір одного ConfigMap обмежено 1 MiB.
  • Змінні оточення з ConfigMap читаються лише при старті контейнера: після зміни ConfigMap потрібен рестарт Pod. Файли в томі оновлюються самі з певною затримкою (крім змонтованих через subPath, ті не оновлюються ніколи).

Secret (секрет) — це об’єкт для чутливих даних: паролів, токенів, TLS-ключів, доступів до реєстру. Підключається в Pod так само, як ConfigMap.

  • Дані в Secret закодовані в base64, а це кодування, а не шифрування: будь-хто з правом читати Secret бачить пароль.
  • В etcd секрети за замовчуванням лежать у відкритому вигляді, тому вмикають encryption at rest.
  • Типи: Opaque (довільні дані), kubernetes.io/tls, kubernetes.io/dockerconfigjson (доступ до реєстру), kubernetes.io/service-account-token.
  • Secret не комітять у Git. Варіанти: External Secrets Operator (тягне значення з Vault чи AWS Secrets Manager), Sealed Secrets, SOPS.

Encryption at rest (шифрування у спокої) — це налаштування kube-apiserver (EncryptionConfiguration), за якого Secret (а за бажанням і інші ресурси) шифруються перед записом в etcd, часто ключем із зовнішнього KMS.

env / envFrom (змінні оточення) — це спосіб передати конфігурацію в контейнер змінними оточення: по одній (env, зокрема зі значенням з ConfigMap чи Secret через valueFrom) або всі ключі об’єкта разом (envFrom).

Downward API — це спосіб передати контейнеру інформацію про нього самого: ім’я Pod, namespace, IP, ім’я ноди, мітки, власні requests і limits — через змінні оточення або файли.

imagePullSecrets — це посилання на Secret з доступом до приватного реєстру образів, яким kubelet користується при завантаженні образу.

Projected volume (проєкційний том) — це том, що збирає в одній директорії кілька джерел: Secret, ConfigMap, Downward API і токен ServiceAccount.

12. Сховище: Volume, PV, PVC, StorageClass

Volume (том) — це директорія, доступна контейнерам Pod, яка переживає рестарт окремого контейнера. Власна файлова система контейнера тимчасова: після рестарту все, що записано поза томом, зникає.

emptyDir — це порожній том, що створюється разом із Pod і видаляється разом із Pod. Для тимчасових файлів, кешу, обміну файлами між контейнерами одного Pod. Може жити в RAM (medium: Memory), і тоді його обсяг зараховується в memory limit.

hostPath — це том, що монтує в Pod директорію або файл з файлової системи ноди. Небезпечний (доступ до хоста, прив’язка до конкретної ноди), тому потрібен лише системним агентам: логи, моніторинг, CSI.

PersistentVolume, PV (постійний том) — це кластерний об’єкт, що представляє реальний шматок сховища: хмарний диск, NFS-шару, LUN, локальний диск. Живе незалежно від Pod.

PersistentVolumeClaim, PVC (заявка на том) — це запит застосунку на сховище: «мені потрібно 20Gi, режим ReadWriteOnce, клас fast-ssd». Kubernetes знаходить (або створює) відповідний PV і прив’язує їх один до одного (стан Bound). Pod посилається на PVC, а не на PV.

  • Аналогія: PV — це квартира, PVC — заявка на оренду, StorageClass — забудовник, який зводить квартиру під заявку.
  • PVC живе в namespace, PV — кластерний. Зв’язок між ними один до одного.

StorageClass (клас сховища) — це опис типу сховища і того, як його створювати: який CSI-провізіонер, які параметри (тип диска, IOPS, реплікація), яка reclaim policy, чи можна розширювати том. Саме StorageClass робить можливим динамічне провізіонування.

  • StorageClass з анотацією storageclass.kubernetes.io/is-default-class: "true" використовується для PVC, у яких клас не вказано.

Dynamic provisioning (динамічне провізіонування) — це автоматичне створення PV (і реального диска) під новий PVC через StorageClass і CSI-драйвер. Альтернатива — статичне провізіонування, коли адміністратор заздалегідь створює PV руками.

Access modes (режими доступу) — це способи, якими том можна змонтувати:

  • ReadWriteOnce (RWO) — читання і запис з однієї ноди (кілька Pod на тій самій ноді можуть ділити том);
  • ReadOnlyMany (ROX) — лише читання, з багатьох нод;
  • ReadWriteMany (RWX) — читання і запис з багатьох нод (NFS, CephFS, EFS; звичайні блочні хмарні диски цього не вміють);
  • ReadWriteOncePod (RWOP) — читання і запис лише одним Pod у всьому кластері.
  • Пастка: Deployment на 3 репліки з одним RWO-томом. Pod, що потрапили на інші ноди, застрягнуть у ContainerCreating з помилкою Multi-Attach.

Reclaim policy (політика повернення) — це те, що станеться з PV і реальним диском, коли PVC видалено: Delete (диск видаляється, дефолт для динамічних томів) або Retain (PV і дані залишаються, їх прибирають або перепідключають вручну). Для важливих баз даних обирають Retain.

volumeBindingMode — це момент прив’язки PVC до PV: Immediate (одразу) або WaitForFirstConsumer (коли з’явиться Pod, якому він потрібен). Другий режим потрібен для зональних дисків: інакше диск створиться в зоні A, Pod заплануються в зону B і не зможуть його змонтувати.

Volume expansion (розширення тому) — це збільшення розміру PVC (через spec.resources.requests.storage), якщо StorageClass має allowVolumeExpansion: true. Зменшити PVC не можна.

VolumeSnapshot (знімок тому) — це знімок PVC у певний момент часу, зроблений через CSI-драйвер. З нього можна створити новий PVC.

13. Масштабування

Horizontal / vertical scaling (горизонтальне / вертикальне масштабування) — горизонтальне — це додати більше копій (Pod або нод), вертикальне — дати кожній копії більше CPU і пам’яті.

metrics-server — це легкий компонент, що збирає з kubelet поточне споживання CPU і пам’яті Pod і нод і віддає його через Metrics API. Потрібен для kubectl top і для HPA за CPU чи пам’яттю. Це не система моніторингу: історії він не зберігає.

HorizontalPodAutoscaler, HPA (горизонтальний автоскейлер Pod) — це контролер, який автоматично змінює replicas у Deployment чи StatefulSet за метриками: CPU, пам’ять, кастомні (RPS, довжина черги) або зовнішні.

  • Відсоток CPU в HPA рахується від requests, а не від limits і не від ядер ноди. Немає requests — HPA за CPU utilization не працює.
  • При зменшенні реплік діє вікно стабілізації (за замовчуванням 5 хвилин), щоб кількість реплік не «стрибала» туди-сюди.
  • Якщо реплікам керує HPA, не вказуй replicas у маніфесті Deployment, який застосовуєш через GitOps, інакше кожен apply скидатиме масштаб.

VerticalPodAutoscaler, VPA (вертикальний автоскейлер Pod) — це окремий проєкт (у Kubernetes з коробки його немає), який аналізує реальне споживання і рекомендує або автоматично виставляє контейнерам requests і limits. Класично змінює ресурси через перестворення Pod, а з in-place resize може робити це без рестарту.

  • HPA і VPA за однією метрикою (наприклад, CPU) на одному Deployment конфліктують.

Cluster Autoscaler — це компонент, який додає ноди, коли Pod застрягли в Pending через нестачу ресурсів, і прибирає недовантажені ноди, Pod з яких можна розселити. Працює з групами нод (ASG, managed node groups).

  • Реагує на requests Pending Pod, а не на реальне завантаження CPU нод.

Karpenter — це альтернативний автоскейлер нод: замість фіксованих груп він під конкретні Pending Pod одразу підбирає і створює інстанс потрібного типу і розміру, а також консолідує (ущільнює) ноди. Народився в AWS, тепер є і для інших провайдерів.

KEDA — це автоскейлер на основі подій: масштабує за станом зовнішніх систем (довжина черги Kafka, RabbitMQ чи SQS, cron, метрики Prometheus) і вміє scale to zero — зменшувати кількість реплік до нуля, коли подій немає. Всередині використовує HPA.

14. Безпека і доступи

Authentication (автентифікація) — це перевірка «хто ти»: клієнтський сертифікат, токен, OIDC (вхід через SSO).

  • У Kubernetes немає об’єкта User: звичайні користувачі існують лише як ім’я в сертифікаті чи токені від зовнішньої системи.

Authorization (авторизація) — це перевірка «що тобі дозволено». Основний механізм — RBAC.

RBAC (Role-Based Access Control, рольовий доступ) — це модель доступу, у якій права описують у ролях (які дії над якими ресурсами), а ролі прив’язують до користувачів, груп або ServiceAccount.

  • RBAC вміє лише дозволяти, правил «заборонити» немає. Усе, що не дозволено явно, заборонено.
  • Дії (verbs): get, list, watch, create, update, patch, delete. Увага: право list на Secret фактично дає їхній вміст.

Role (роль) — це набір дозволів у межах одного namespace.

ClusterRole (кластерна роль) — це набір дозволів на рівні всього кластера або для кластерних ресурсів (nodes, PV, namespaces). Може також бути шаблоном, який прив’язують у конкретному namespace через RoleBinding.

RoleBinding (прив’язка ролі) — це прив’язка Role (або ClusterRole) до суб’єкта в одному namespace.

ClusterRoleBinding (кластерна прив’язка ролі) — це прив’язка ClusterRole до суб’єкта на весь кластер. Видати комусь ClusterRoleBinding на cluster-admin означає віддати ключі від усього.

Subject (суб’єкт) — це той, кому видають права: User, Group або ServiceAccount.

ServiceAccount (сервісний обліковий запис) — це ідентичність для процесів у Pod, а не для людей: від її імені застосунок звертається до Kubernetes API. Кожен Pod працює від якогось ServiceAccount (якщо не вказано, то від default свого namespace).

  • Токен ServiceAccount монтується в Pod як файл. Сучасні токени короткоживучі, прив’язані до конкретного Pod і оновлюються автоматично. Якщо застосунку не потрібен доступ до API, монтування вимикають (automountServiceAccountToken: false).
  • Через ServiceAccount також видають доступ до хмари без статичних ключів: IRSA і EKS Pod Identity в AWS, Workload Identity в GCP та Azure.

Admission controller (контролер допуску) — це «митниця» kube-apiserver: плагін, який перехоплює запит після автентифікації й авторизації, але до запису в etcd, і може змінити об’єкт (mutating) або відхилити запит (validating). Приклади вбудованих: LimitRanger, ResourceQuota, PodSecurity.

Mutating / Validating admission webhook — це зовнішні admission-контролери у вигляді HTTP-сервісів: mutating змінює об’єкт (так Istio додає sidecar), validating вирішує «так чи ні» (OPA Gatekeeper, Kyverno). Спочатку виконуються всі mutating, потім усі validating.

  • Webhook з failurePolicy: Fail, який ліг, може заблокувати створення Pod у всьому кластері.

ValidatingAdmissionPolicy — це вбудований (стабільний з 1.30) спосіб описувати правила валідації виразами CEL прямо в об’єкті Kubernetes, без окремого webhook-сервісу.

Pod Security Standards, PSS (стандарти безпеки Pod) — це три стандартні профілі безпеки Pod:

  • privileged — без обмежень;
  • baseline — забороняє явно небезпечне (privileged, hostNetwork, hostPath тощо);
  • restricted — суворий профіль: запуск не від root, без підвищення привілеїв, мінімум capabilities, seccomp.

Pod Security Admission, PSA — це вбудований admission-контролер, що застосовує PSS на рівні namespace через мітки (pod-security.kubernetes.io/enforce: restricted) у режимах enforce, audit і warn. Замінив PodSecurityPolicy, яку видалили в 1.25.

SecurityContext (контекст безпеки) — це налаштування безпеки Pod або контейнера: від якого UID і GID запускати (runAsUser, runAsNonRoot), чи можна підвищувати привілеї (allowPrivilegeEscalation), Linux capabilities, файлова система лише для читання, профілі seccomp, AppArmor і SELinux, режим privileged.

Privileged container (привілейований контейнер) — це контейнер з майже повним доступом до хоста: усі capabilities, усі пристрої. Фактично це root на ноді, тому такі контейнери дозволяють лише системним компонентам.

Audit log (журнал аудиту) — це журнал kube-apiserver, у який записується, хто, коли і що робив через API. Головне джерело правди під час розслідування інцидентів.

15. Розширення і доставка: CRD, оператори, Helm, GitOps

CustomResourceDefinition, CRD (визначення власного ресурсу) — це спосіб додати в Kubernetes новий тип об’єктів (новий kind) з власною схемою без зміни коду Kubernetes. Після цього з новим типом працюють як із вбудованим, наприклад kubectl get certificates.

Custom Resource, CR (власний ресурс) — це конкретний об’єкт типу, визначеного через CRD: наприклад, Certificate з ім’ям shop-tls від cert-manager. Об’єкти Gateway API — теж custom resources.

Operator (оператор) — це CRD плюс контролер, у код якого вкладено операційні знання адміністратора: як розгорнути, оновити, забекапити і перемкнути на репліку конкретну систему. Ти пишеш «хочу кластер PostgreSQL на 3 інстанси», а оператор (CloudNativePG, Strimzi для Kafka, Prometheus Operator) робить решту.

Helm — це пакетний менеджер для Kubernetes: збирає маніфести застосунку в шаблонізований пакет і встановлює його з потрібними параметрами.

Chart (чарт) — це пакет Helm: шаблони маніфестів, values.yaml з параметрами за замовчуванням і метадані.

Release (реліз) — це конкретна інсталяція чарта в кластері з конкретними values і власною історією версій (helm upgrade, helm rollback).

Values (значення) — це параметри, які підставляються в шаблони чарта: values.yaml, файли через -f prod.yaml, окремі значення через --set.

Kustomize — це інструмент налаштування маніфестів без шаблонів: є база (base) і накладання (overlays) для різних середовищ із патчами поверх бази. Вбудований у kubectl (kubectl apply -k).

GitOps — це підхід, за якого Git — єдине джерело правди про стан кластера, а агент усередині кластера (Argo CD, Flux) постійно синхронізує кластер із репозиторієм і повертає назад ручні зміни (drift). Деплой — це merge в Git, rollback — revert. Детальніше про пайплайни — у статті CI/CD.

Server-side apply — це режим kubectl apply --server-side, за якого зміни зливає сам apiserver і веде облік, яким полем який «менеджер» (людина, контролер, HPA) володіє. Так різні інструменти не перетирають зміни одне одного.

ClusterIP vs NodePort vs LoadBalancerЛише всередині кластера → плюс порт на кожній ноді → плюс зовнішній балансувальник; кожен наступний тип включає попередній
