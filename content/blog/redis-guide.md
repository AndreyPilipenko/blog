# Redis від А до Я: повний мануал для DevOps/SRE

> Redis є майже в кожному продакшені: кеш перед базою, сесії, черги, rate limiting, лідерборди, розподілені локи. Його легко запустити (`docker run redis`) і так само легко покласти: однією командою `KEYS *`, забутим `maxmemory`, `fork` на 50 ГБ даних або репліками, які годинами по колу роблять full sync. Ця стаття про те, **як Redis працює всередині**, чому він поводиться саме так, де в нього граблі, як його експлуатувати й дебажити, і що питають на співбесідах, коли хочуть перевірити, чи ти справді тримав його в продакшені.

Майже все, що тут написано про Redis, стосується і **Valkey** — open source форку, який після зміни ліцензії Redis у 2024 році став основним двигуном у AWS і Google Cloud. Де поведінка відрізняється, про це сказано окремо. Поведінку команд, дефолти і тексти помилок у статті перевірено на живих Redis 8.10 і Valkey 9.1.

## 1. Що таке Redis і де його використовують {#what}

### 1.1 Одним абзацом

**Redis** (REmote DIctionary Server) — сервер структур даних у пам'яті. Це не просто «key-value»: значенням ключа може бути рядок, хеш, список, множина, відсортована множина, стрім, бітмап чи HyperLogLog, і для кожного типу є свої атомарні команди. Ти не читаєш об'єкт у застосунок, не змінюєш його там і не пишеш назад. Ти кажеш серверу «додай елемент у список», «збільш лічильник», «дай топ-10 гравців», і він робить це сам за мікросекунди.

Майже вся поведінка Redis випливає з трьох речей:

1. **Дані живуть у RAM.** Звідси швидкість, але й обмеження: датасет мусить уміститися в пам'ять, а пам'ять дорога.
2. **Команди виконуються в одному потоці.** Звідси атомарність кожної команди без жодних блокувань, але й головна пастка: одна повільна команда зупиняє всіх клієнтів.
3. **Диск і репліки — опційні та асинхронні.** Persistence (RDB, AOF) і реплікація за замовчуванням асинхронні: це швидко, але підтверджений запис **можна втратити**.

### 1.2 Де Redis використовують

| Сценарій | Що використовують | Нюанс |
|---|---|---|
| Кеш перед БД або API | Strings / Hashes + TTL | Інвалідація і cache stampede (розділ 11) |
| Сесії користувачів | Hash + TTL | Втратив Redis — розлогінив усіх; потрібна реплікація |
| Rate limiting | `INCR` + `EXPIRE`, Sorted Set, Lua | Атомарність і ключі, що «забули» TTL |
| Лічильники, статистика | `INCR`, `HINCRBY`, HyperLogLog | HLL рахує унікальних приблизно (~0.81%) |
| Лідерборди, рейтинги | Sorted Set | O(log N) на вставку, топ-N за мілісекунди |
| Черги задач | List (`LPUSH` / `BRPOP`, `BLMOVE`), Streams | Надійна доставка — не за замовчуванням |
| Події, стрімінг | Streams + consumer groups | Обмежені пам'яттю; один стрім живе на одному шарді |
| Pub/Sub, нотифікації | `PUBLISH` / `SUBSCRIBE` | Fire-and-forget: офлайн-підписник усе пропустить |
| Розподілені локи | `SET key token NX PX 30000` | Не для гарантій коректності (розділ 11.3) |
| Геопошук | `GEOADD`, `GEOSEARCH` | Під капотом — Sorted Set |
| Дедуплікація | Set, Bloom filter | Bloom у Redis 8 є «з коробки», у Valkey — модулем |
| Пошук, вектори, AI | Query Engine, Vector Sets | Залежить від версії та редакції (розділ 3.9) |

### 1.3 Чим Redis НЕ є

- **Не реляційна база.** Немає JOIN і довільних запитів. Ключ, за яким шукатимеш дані, треба знати наперед: модель даних у Redis проєктують від запитів, а не від сутностей.
- **Не durable storage за замовчуванням.** `OK` у відповіді не означає, що запис уже на диску чи на репліці. Навіть з AOF і `appendfsync always` реплікація лишається асинхронною.
- **Не Kafka.** Streams схожі на лог із consumer groups, але живуть у пам'яті, а один стрім не шардиться. Зберігати в ньому тижні подій дорого.
- **Не безкоштовний за пам'яттю.** Кожен ключ має накладні витрати в десятки байтів. Мільярд дрібних ключів — це вже не «кеш», а сотні гігабайтів RAM.
- **Не «поставив і забув».** Без `maxmemory`, моніторингу і продуманої persistence Redis ламається в найнезручніший момент.

### 1.4 Redis, Valkey і ліцензії: що сталося у 2024–2025

| Дата | Подія |
|---|---|
| до 2024 | Redis — open source під BSD-3. Остання BSD-гілка — 7.2 |
| 20.03.2024 | Redis Ltd. оголошує перехід на подвійну ліцензію RSALv2 + SSPLv1, починаючи з 7.4. Це source-available, а не open source у розумінні OSI: зокрема, не можна запускати Redis як керований сервіс для інших |
| 28.03.2024 | Linux Foundation запускає **Valkey** — форк Redis 7.2.4 під BSD-3. Підтримують AWS, Google Cloud, Oracle, Ericsson, Snap та інші |
| 29.07.2024 | Redis 7.4 — перший реліз під новою ліцензією |
| 15.09.2024 | Valkey 8.0. У жовтні AWS запускає ElastiCache і MemoryDB for Valkey |
| 01.05.2025 | Redis 8.0 додає третю ліцензію — **AGPLv3**, схвалену OSI. Redis Community Edition перейменовано на **Redis Open Source** |
| 21.10.2025 | Valkey 9.0 |
| 2026 | Redis 8.6, 8.8, 8.10; Valkey 9.1, 9.2 у RC |

Що з цього важливо для інженера:

- **Для власної інфраструктури** можна використовувати і Redis, і Valkey. Ліцензійні обмеження RSAL / SSPL стосуються передусім тих, хто продає Redis як сервіс, а AGPL вимагає відкрити зміни, якщо ти модифікував Redis і надаєш його по мережі. Але в багатьох компаніях AGPL і SSPL заборонені внутрішньою політикою, тож питання до юристів реальне.
- **Хмари обрали Valkey:** AWS (ElastiCache, MemoryDB) і Google (Memorystore for Valkey) роблять його основним двигуном і дають на нього нижчу ціну.
- **Дві гілки поступово розходяться.** До Redis 7.2 включно Valkey — прямий наступник. Починаючи з Redis 7.4, у кожного проєкту свої фічі, свої дефолти і свій формат RDB. Порівняння і наслідки для міграції — у розділі 16.

## 2. Як Redis працює всередині {#internals}

### 2.1 Однопотоковий? І так, і ні

Класичне питання на співбесіді: «Redis однопотоковий?». Правильна відповідь: **виконання команд однопотокове, а процес Redis — ні**.

```
                  ┌──────────────────────── redis-server ─────────────────────────┐
                  │                                                               │
  клієнти ─TCP─▶  │  ┌──────────────── main thread ───────────────┐               │
 (тисячі          │  │ event loop (epoll / kqueue)                │               │
  з'єднань)       │  │  ├ accept нових з'єднань                   │               │
                  │  │  ├ читання і парсинг команд          (*)   │               │
                  │  │  ├ ВИКОНАННЯ КОМАНД — строго по одній      │               │
                  │  │  ├ запис відповідей                  (*)   │               │
                  │  │  └ serverCron (hz разів на секунду):       │               │
                  │  │     active expire, rehash, статистика...   │               │
                  │  └────────────────────────────────────────────┘               │
                  │  (*) при io-threads > 1 цю роботу забирають I/O-потоки        │
                  │                                                               │
                  │  ┌── bio threads ───────────┐   ┌── I/O threads (6.0+) ──┐    │
                  │  │ close() файлів           │   │ read / parse / write   │    │
                  │  │ fsync() для AOF          │   │ сокетів клієнтів       │    │
                  │  │ lazy free (UNLINK, ...)  │   └────────────────────────┘    │
                  │  └──────────────────────────┘                                 │
                  └──────────────────────────┬────────────────────────────────────┘
                                             │ fork()
                               ┌─────────────▼───────────────┐
                               │ дочірній процес:            │
                               │ BGSAVE (RDB), BGREWRITEAOF, │
                               │ RDB для full sync реплік    │
                               └─────────────────────────────┘
```

- **Main thread** крутить event loop: через `epoll` дізнається, на яких сокетах є дані, і **виконує команди по одній**. Тому кожна команда атомарна: поки виконується `INCR`, жодна інша команда не втрутиться, і жодних м'ютексів для цього не треба.
- **Фонові потоки (bio)** закривають файли, роблять `fsync` для AOF і **lazy free**, тобто звільняють пам'ять великих об'єктів після `UNLINK` чи `FLUSHALL ASYNC`.
- **I/O-потоки** (з 6.0, параметр `io-threads`) читають сокети, парсять запити і пишуть відповіді. Самі команди однаково виконує main thread.
- **Дочірні процеси через `fork()`** роблять RDB-снапшоти, переписують AOF і готують дані для full sync реплік. Чим fork небезпечний — у розділі 6.

> **Головне:** один потік виконання означає, що пропускна здатність інстансу впирається в **одне ядро CPU**. Додати ядер не допоможе. Масштабуються горизонтально: Redis Cluster або кілька незалежних інстансів.

### 2.2 Чому він такий швидкий з одним потоком

- **RAM замість диска.** Доступ до пам'яті — близько 100 нс, до SSD — десятки чи сотні мікросекунд.
- **Немає блокувань і перемикань контексту** при виконанні команд. Багатопотокова база витрачає чимало часу на синхронізацію, Redis — нуль.
- **Ефективні структури даних**: для кожного типу своя, плюс компактні кодування для маленьких об'єктів (розділ 3).
- **I/O multiplexing.** Один потік через `epoll` обслуговує десятки тисяч з'єднань, бо не чекає на жодне з них.
- **Простий протокол RESP**, який парситься майже без витрат.

Порядок цифр: **сотні тисяч простих операцій за секунду** на інстанс без pipelining і **мільйони** з pipelining. Найчастіше вузьке місце не CPU Redis, а мережа, RTT і кількість запитів, які робить застосунок.

### 2.3 Наслідок: одна повільна команда блокує всіх

Команди виконуються по черзі, тому команда, яка працює 2 секунди, — це **2 секунди повного простою для всіх клієнтів**. Нові запити стоять у черзі, latency росте, health checks падають, а Sentinel може навіть вирішити, що master помер.

```
час ───────────────────────────────────────────────────────────────────▶
main thread: [GET][SET][INCR][██████████ KEYS * (2.3 s) ██████████][GET][GET] ...
                                         ▲
                 тут чекають УСІ інші клієнти: GET, який зазвичай
                 виконується за 1 мкс, отримує latency 2+ секунди
```

Тому в Redis так важливо знати **складність команд** (розділ 3.10). O(1) і O(log N) — безпечно. O(N) на великій колекції — потенційний інцидент.

### 2.4 Протокол RESP і round trip

Клієнт спілкується з Redis по TCP (порт **6379**) протоколом **RESP** (REdis Serialization Protocol). Команда `SET user:1 Alice` на дроті виглядає так:

```
*3\r\n$3\r\nSET\r\n$6\r\nuser:1\r\n$5\r\nAlice\r\n
```

Це масив із трьох bulk-рядків. Відповідь — `+OK\r\n`. Помилки починаються з `-` (`-ERR ...`, `-WRONGTYPE ...`), числа з `:`, рядки з `$`, масиви з `*`. З Redis 6 є **RESP3** (вмикається командою `HELLO 3`): у ньому з'явилися типи map, set, double, boolean і **push**-повідомлення, на яких побудоване client-side caching.

Redis розуміє й «inline»-команди, тому для швидкої перевірки вистачить `nc`:

```bash
printf 'PING\r\n' | nc -q1 127.0.0.1 6379     # +PONG
```

У класичному режимі кожна команда — це **round trip**: відправив, дочекався відповіді, відправив наступну. Якщо RTT між застосунком і Redis 0.5 мс (сусідня AZ), то 10 000 послідовних `GET` займуть 5 секунд, хоча сам Redis витратить на них кілька мілісекунд. Рішення — **pipelining**: відправити пачку команд одразу і потім прочитати всі відповіді (розділ 10).

### 2.5 Нумеровані бази `SELECT 0..15` — краще не треба

Redis має **нумеровані бази** (`databases 16`, команда `SELECT 3`). Виглядає як ізоляція, але нею не є:

- усі бази ділять **один потік**, один `maxmemory`, одну persistence і один конфіг, тож «важкий» сервіс у базі 3 гальмує сервіс у базі 0;
- `FLUSHALL` знищує всі бази разом, а переплутати `FLUSHDB` і `FLUSHALL` дуже легко;
- політика витіснення і більшість метрик — спільні;
- **Redis Cluster підтримує лише базу 0** (Valkey з версії 9.0 дозволяє кілька баз і в кластері, якщо задати `cluster-databases`; за замовчуванням там теж одна).

Для ізоляції сервісів краще окремі інстанси (вони дешеві) або хоча б префікси в іменах ключів: `billing:invoice:42`, `auth:session:abc`.

## 3. Типи даних і їхні внутрішні кодування {#data-types}

Кожен тип Redis має **два або більше внутрішніх кодувань**: компактне для маленьких об'єктів і повноцінне для великих. Перехід між ними автоматичний. Знати про це треба з двох причин: від кодування залежить **пам'ять** (різниця буває в рази) і **швидкість операцій**.

### 3.1 Зведена таблиця

| Тип | Для чого | Внутрішнє кодування | Основні операції і складність |
|---|---|---|---|
| String | Кеш, лічильники, прапорці, бітмапи | `int`, `embstr` (короткі рядки), `raw` | `GET` / `SET` / `INCR` — O(1) |
| List | Черги, стеки, «останні N подій» | `listpack` (малий), `quicklist` (великий) | `LPUSH` / `RPOP` — O(1), `LINDEX` / `LRANGE` — O(N) |
| Hash | Об'єкти: поле → значення | `listpack`, `hashtable` | `HGET` / `HSET` — O(1), `HGETALL` — O(N) |
| Set | Унікальні елементи, теги | `intset`, `listpack`, `hashtable` | `SADD` / `SISMEMBER` — O(1), `SMEMBERS` — O(N) |
| Sorted Set | Рейтинги, пріоритети, часові вікна | `listpack`, `skiplist` + hashtable | `ZADD` / `ZRANK` — O(log N), `ZSCORE` — O(1) |
| Stream | Лог подій, consumer groups | radix tree з listpack-вузлів | `XADD` — O(1), `XRANGE` — O(N) |
| Bitmap | Прапорці за ID, активність за днями | Звичайний String | `SETBIT` / `GETBIT` — O(1), `BITCOUNT` — O(N) |
| HyperLogLog | Кількість унікальних (приблизно) | String (sparse / dense, до 12 КБ) | `PFADD` / `PFCOUNT` — O(1) |
| Geo | Точки на мапі, пошук поруч | Sorted Set (geohash як score) | `GEOSEARCH` — O(N + log M) |

Подивитися кодування і розмір ключа:

```
127.0.0.1:6379> HSET user:1 name Alice age 30
(integer) 2
127.0.0.1:6379> OBJECT ENCODING user:1
"listpack"
127.0.0.1:6379> MEMORY USAGE user:1
(integer) 52
```

### 3.2 Strings

- Найпростіший тип, але значенням може бути будь-що до **512 МБ**: текст, JSON, серіалізований protobuf, картинка.
- Внутрішньо це **SDS** (simple dynamic string). Ціле число зберігається як `int` без рядка взагалі, короткий рядок — як `embstr` (одна алокація разом із заголовком об'єкта), довший — як `raw`. У старих статтях пишуть, що поріг `embstr` — 44 байти. У нових версіях (Redis 8.x, Valkey 8+) у ту саму алокацію вбудовується ще й ключ, тому поріг залежить і від довжини ключа (у Valkey він помітно більший).
- `INCR`, `INCRBY`, `INCRBYFLOAT`, `DECR` — атомарні лічильники без гонок. На них будують rate limiting і генерацію ID.
- `SET` має купу опцій: `EX` / `PX` (TTL), `NX` (лише якщо ключа немає), `XX` (лише якщо є), `GET` (повернути старе значення), `KEEPTTL` (не скидати TTL). Окремі команди `SETNX`, `SETEX`, `GETSET` вважаються застарілими.

> **Пастка:** `SET` без `KEEPTTL` **скидає TTL** ключа. Детально — у розділі 4.

### 3.3 Lists

- Список з O(1) вставкою і видаленням з обох кінців. Великий список — це `quicklist`: зв'язаний список компактних блоків `listpack` (за замовчуванням до 8 КБ кожен, `list-max-listpack-size -2`).
- Черга: `LPUSH` + `RPOP` (або блокуючий `BRPOP`). Стек: `LPUSH` + `LPOP`. «Останні 100 подій»: `LPUSH` + `LTRIM 0 99`.
- `LINDEX`, `LSET`, `LINSERT` — O(N). Список — не масив.
- Надійна черга: `BLMOVE queue processing RIGHT LEFT 0` (раніше `BRPOPLPUSH`) атомарно перекладає задачу в список «в обробці», щоб вона не загубилася, якщо воркер упаде посеред роботи.

### 3.4 Hashes

- Об'єкт з полями: `HSET user:1 name Alice email a@example.com`. Читати можна одне поле (`HGET`), кілька (`HMGET`) або всі (`HGETALL`).
- Маленький хеш (за замовчуванням до 512 полів і кожне значення до 64 байтів — параметри `hash-max-listpack-entries` і `hash-max-listpack-value`) зберігається як **listpack**: суцільний масив байтів без вказівників. Пошук у ньому O(N), але N маленьке, тому через кеш CPU це навіть швидше за hashtable. Щойно поріг перевищено, хеш конвертується в `hashtable` і **назад уже не повертається**, навіть якщо поля видалити. (Списки, до речі, з 7.2 вміють повертатися з `quicklist` у `listpack`, а хеші й множини — ні.)
- TTL на **окреме поле** хешу з'явився лише в **Redis 7.4** (`HEXPIRE`, `HTTL`, `HPERSIST`), у Valkey — у 9.0. До того TTL ставився тільки на ключ цілком.

**Класичний трюк економії пам'яті**, який Instagram описав ще у 2011 році: замість мільйонів окремих ключів `media:1155315 → 939` групувати їх у хеші-«кошики»: `HSET media:1155 315 939` (ID ділиться на номер кошика і поле). Кожен кошик лишається listpack'ом, і накладні витрати на окремий ключ зникають. Так Instagram зменшив пам'ять приблизно вчетверо: з ~70 МБ до ~16 МБ на мільйон записів. Вони робили кошики по 1000 полів і для цього піднімали поріг компактного кодування (тоді ще ziplist) до 1000; з дефолтним порогом 512 кошики варто робити меншими.

### 3.5 Sets

- Невпорядкована множина унікальних рядків: теги, «хто вже бачив пост», унікальні IP за годину.
- Кодування: `intset` (лише цілі числа, до 512 елементів), `listpack` (до 128 коротких рядків, з 7.2), `hashtable`.
- `SINTER`, `SUNION`, `SDIFF` зручні, але **дорогі**: перетин двох множин по мільйону елементів — сотні мілісекунд блокування.

### 3.6 Sorted Sets (ZSET)

- Множина, де кожен елемент має `score` (double), і елементи завжди відсортовані за ним. Лідерборди, черги з пріоритетом, «події за останні 5 хвилин» (score = timestamp), sliding window rate limiting.
- Маленька ZSET (до 128 елементів) — listpack. Велика — це одночасно **skiplist і hashtable**: hashtable дає `ZSCORE` за O(1), skiplist — `ZRANK`, `ZRANGE`, `ZRANGEBYSCORE` за O(log N + M).
- Чому skiplist, а не збалансоване дерево? Автор Redis пояснював так: skiplist простіше реалізувати й дебажити, за швидкістю він не гірший, на ньому природно робляться range-запити, а баланс між пам'яттю і швидкістю легко підкрутити. Популярне «розумне» питання на співбесіді.

```bash
ZADD leaderboard 1500 alice 1720 bob 980 carol
ZRANGE leaderboard 0 9 REV WITHSCORES    # топ-10 (старий варіант — ZREVRANGE)
ZREVRANK leaderboard alice               # місце alice (рахуючи з нуля)
ZINCRBY leaderboard 50 carol             # атомарно додати очки
```

### 3.7 Streams

- Append-only лог записів з автоматичними ID вигляду `<мілісекунди>-<номер>`, така собі маленька Kafka всередині Redis (з 5.0).
- **Consumer groups**: кожне повідомлення в групі отримує лише один consumer. Отримане, але не підтверджене через `XACK` повідомлення лежить у **PEL** (Pending Entries List), і якщо consumer помер, інший може забрати його через `XAUTOCLAIM`.
- Стрім сам не обрізається. Без `MAXLEN` / `MINID` у `XADD` (або окремого `XTRIM`) він росте, доки не з'їсть усю пам'ять. `MAXLEN ~ 1000000` з тильдою — наближене обрізання, набагато дешевше за точне.

```bash
XADD orders MAXLEN ~ 1000000 * order_id 42 amount 99.90
XGROUP CREATE orders billing $ MKSTREAM
XREADGROUP GROUP billing worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1792195200000-0
XPENDING orders billing                                 # отримані, але не підтверджені
XAUTOCLAIM orders billing worker-2 60000 0-0 COUNT 10   # забрати ті, що "зависли" > 60 с
```

### 3.8 Bitmaps, HyperLogLog, Geo

- **Bitmap** — звичайний String, з яким працюють побітово: `SETBIT online:2026-10-17 <user_id> 1`, а `BITCOUNT` скаже, скільки користувачів було онлайн. 100 мільйонів користувачів — це 12.5 МБ.
  > **Пастка:** `SETBIT key 4294967295 1` одразу виділяє **512 МБ**, бо рядок розширюється до найбільшого зміщення. Бітмап за великими розрідженими ID (наприклад, snowflake) — погана ідея.
- **HyperLogLog** — ймовірнісна структура: рахує кількість унікальних елементів з похибкою **~0.81%** і займає не більше **12 КБ**, байдуже, мільйон там елементів чи мільярд. Команди `PFADD`, `PFCOUNT`, `PFMERGE`. Самі елементи HLL не зберігає, тож отримати їхній список неможливо.
- **Geo** — `GEOADD`, `GEOSEARCH ... BYRADIUS 5 km`. Під капотом Sorted Set, де score — це 52-бітний geohash, тому `ZRANGE` і `ZREM` працюють і з geo-ключами.

### 3.9 Нові типи і модулі: JSON, пошук, вектори, Array

- **Redis 8** включив у бінарні дистрибутиви (Docker, APT, RPM, snap, brew) те, що раніше було Redis Stack: **JSON** (`JSON.SET`, `JSON.GET` з JSONPath), **Query Engine** (`FT.CREATE`, `FT.SEARCH`, `FT.AGGREGATE`, `FT.HYBRID`: вторинні індекси, повнотекстовий і векторний пошук по хешах і JSON), **TimeSeries** (`TS.*`) і ймовірнісні структури (**Bloom**, **Cuckoo**, **Count-Min Sketch**, **Top-K**, **t-digest**). Формально це досі модулі, які завантажуються автоматично. Якщо збирати Redis з вихідників, їх треба збирати окремо.
- **Vector Sets** (з 8.0, автор — antirez) — тип у ядрі для векторів і пошуку схожих (`VADD`, `VSIM`) на основі HNSW. Офіційно досі позначений як beta.
- **Array** (8.8) — масив із доступом за індексом (`ARSET`, `ARGET` та інші команди `AR*`).
- **Compact hashes** (8.10) — кодування, яке зберігає назви полів один раз для хешів з однаковою «схемою». Автоматична конвертація за замовчуванням вимкнена.
- **Valkey** пішов іншим шляхом: ядро без вбудованих модулів і окремі BSD-модулі `valkey-json`, `valkey-bloom` (лише Bloom), `valkey-search` (векторний, а з 1.2 і повнотекстовий пошук), `valkey-ldap`. Усе разом зібрано в образі `valkey/valkey-bundle`. Аналогів TimeSeries, Vector Sets, Cuckoo / CMS / Top-K там немає.

Практичний висновок: як тільки застосунок починає використовувати `JSON.*`, `FT.*`, `TS.*` чи `V*`, він прив'язується до конкретного двигуна і версії. Це варто фіксувати в документації сервісу.

### 3.10 Складність команд: що не можна запускати на проді

| Небезпечно | Чому | Що робити замість |
|---|---|---|
| `KEYS pattern` | O(N) по **всіх** ключах інстансу, блокує сервер на секунди | `SCAN 0 MATCH pattern COUNT 1000` |
| `SMEMBERS`, `HGETALL`, `LRANGE 0 -1`, `ZRANGE 0 -1` на великих колекціях | O(N), гігантська відповідь, блокування і сплеск трафіку | `SSCAN`, `HSCAN`, `ZSCAN`, діапазони на кшталт `LRANGE 0 99` |
| `DEL` великої колекції | Звільнення мільйонів алокацій у main thread | `UNLINK` (звільняє пам'ять у фоні) |
| `FLUSHALL` / `FLUSHDB` | O(N) синхронно | `FLUSHALL ASYNC` (і подумай двічі) |
| `SINTER` / `SUNION` / `SDIFF`, `ZUNIONSTORE`, `SORT` на великих даних | O(N·M), O(N log N) | Рахувати заздалегідь, менші набори, окремий інстанс під аналітику |
| `MONITOR` | Кожна команда копіюється клієнту, пропускна здатність падає в рази | Секунди, не хвилини; краще `SLOWLOG` і `INFO commandstats` |
| Довгий Lua-скрипт | Атомарний, тобто блокує всіх на весь час виконання | Короткі скрипти, обробка батчами |
| `SAVE` | Синхронний дамп на диск у main thread | `BGSAVE` |
| `DEBUG SLEEP`, `DEBUG RELOAD` | Буквально зупиняють сервер (з 7.0 `DEBUG` за замовчуванням вимкнено) | Ніколи на проді |

**`SCAN` — не магія.** Його гарантії варто знати:

- повна ітерація (від курсора `0` до повернення `0`) поверне **всі елементи, які існували весь час ітерації**;
- той самий елемент **може повернутися кілька разів**, і застосунок має це переживати (повторний `UNLINK` нічого не зламає);
- елементи, додані чи видалені під час ітерації, можуть повернутися, а можуть і ні;
- `COUNT` — лише підказка. Виклик може повернути **0 ключів і ненульовий курсор**: це не кінець, ітеруй далі;
- `MATCH` фільтрує **після** вибірки, тому на рідкісному патерні буде багато порожніх сторінок;
- курсор не тримає стану на сервері, тому ітерацію можна будь-коли кинути;
- у Redis Cluster `SCAN` працює **в межах одного вузла**, тож обходити треба кожен master.

```bash
# Безпечно видалити всі ключі за маскою, пачками по 1000 (standalone Redis)
redis-cli --scan --pattern 'session:*' --count 1000 | xargs -r -n 1000 redis-cli UNLINK
```

> У Cluster `UNLINK` з кількома ключами з різних слотів поверне `CROSSSLOT`, тому там видаляй по одному ключу (з pipelining) або групуй ключі за слотом. А ще краще — щоб такі ключі мали TTL і видалялися самі.

## 4. TTL: як ключі живуть і вмирають {#ttl}

### 4.1 Як поставити TTL

```bash
SET session:abc '{"user":42}' EX 3600     # значення і TTL однією командою (атомарно)
EXPIRE key 60                             # TTL у секундах
PEXPIRE key 1500                          # у мілісекундах
EXPIREAT key 1792195200                   # до Unix-часу
EXPIRE key 60 NX                          # лише якщо TTL ще не було (7.0+); також XX, GT, LT
TTL key                                   # скільки лишилося: -1 = без TTL, -2 = ключа немає
PERSIST key                               # прибрати TTL
GETEX key EX 300                          # прочитати і подовжити TTL (6.2+)
```

### 4.2 Пастки TTL

Ці нюанси питають на співбесідах, і на них же горять у продакшені:

- **`SET` скидає TTL.** `SET key value` без `EX`/`KEEPTTL` перезаписує ключ разом з TTL, і ключ стає вічним. Класичний витік пам'яті: код оновлює значення в кеші через `SET` без TTL, і «тимчасові» ключі живуть роками.
- **Команди, які змінюють значення, але не замінюють його, TTL не чіпають:** `INCR`, `APPEND`, `LPUSH`, `HSET`, `SADD`, `ZADD`. TTL зникає лише тоді, коли ключ видаляють або перезаписують цілком (`DEL`, `SET`, `GETSET`, команди `*STORE`).
- **Rate limiter без TTL.** `INCR counter` + окремий `EXPIRE counter 60`: якщо процес упаде між цими двома командами, лічильник залишиться без TTL, і користувача заблокує назавжди. Робити атомарно (розділ 11.4).
- **`RENAME` переносить TTL** на нове ім'я. Якщо цільовий ключ існував, його значення і TTL просто зникають.
- **`EXPIRE key 0` або від'ємний TTL** видаляє ключ одразу. У keyspace notifications при цьому прилетить подія `del`, а не `expired`.
- **TTL ставиться на ключ цілком.** Не можна задати TTL окремому елементу списку чи множини. Для полів хешу таке є з Redis 7.4 (`HEXPIRE`) і Valkey 9.0. Для решти — Sorted Set зі score = час протухання і періодичне `ZREMRANGEBYSCORE`.
- **TTL зберігається як абсолютний Unix-час.** Якщо перенести RDB на сервер з іншим годинником, ключі можуть «протухнути» відразу під час завантаження. Годинник на серверах Redis має бути синхронізований (NTP / chrony).

### 4.3 Як Redis насправді видаляє прострочені ключі

Redis не має таймера на кожен ключ. Прострочені ключі видаляються двома способами:

1. **Пасивно (lazy):** при зверненні до ключа Redis перевіряє TTL, і якщо час минув, видаляє ключ і відповідає так, ніби його не було.
2. **Активно (active expire cycle):** `hz` разів на секунду (за замовчуванням 10) Redis бере вибірку ключів із TTL і видаляє прострочені. Якщо серед вибірки прострочених забагато (близько 25% і більше), цикл повторюється, але з лімітом процесорного часу, щоб не заблокувати сервер. Агресивність налаштовує `active-expire-effort` (1–10).

```
┌─────────── active expire cycle (hz = 10 → кожні 100 мс) ────────────┐
│                                                                     │
│   ┌──▶ взяти вибірку ключів з TTL                                   │
│   │               │                                                 │
│   │               ▼                                                 │
│   │      видалити прострочені                                       │
│   │               │                                                 │
│   │               ▼                                                 │
│   └─ так ── прострочених > ~25%? ── ні ──▶ чекати наступного тіку   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Що з цього випливає:

- **Прострочений ключ може ще якийсь час займати пам'ять.** Оцінка частки таких ключів — `expired_stale_perc` в `INFO stats`.
- **Подія `expired` у keyspace notifications приходить не тоді, коли TTL дійшов до нуля, а тоді, коли ключ фізично видалили.** Якщо до ключа ніхто не звертається, затримка може бути значною. Тому будувати планувальник задач на «спрацюванні» `expired` — погана ідея: події можуть запізнюватися, а pub/sub ще й не гарантує доставку.
- **Expire storm.** Якщо мільйон ключів створили одночасно з однаковим TTL, вони одночасно й протухнуть, і active expire з'їсть помітну частину CPU. Додавай до TTL випадковий jitter.

### 4.4 TTL і репліки

- **Репліки самі ключі не видаляють.** Коли ключ протухає на master, той надсилає в потік реплікації явний `DEL`. Так дані на репліках гарантовано не розходяться з master.
- Але щоб не віддавати мертві дані, репліка при **читанні** перевіряє TTL за своїм годинником і відповідає, що ключа немає (з Redis 3.2).
- Наслідок: якщо master перевантажений і не встигає протухати ключі, пам'ять росте і на ньому, і на всіх репліках.

## 5. Пам'ять: maxmemory, витіснення, фрагментація, big keys {#memory}

### 5.1 `maxmemory`: за замовчуванням ліміту немає

На 64-бітних системах `maxmemory` за замовчуванням дорівнює `0`, тобто **без ліміту**. Redis їстиме пам'ять, доки його не вб'є OOM killer ядра або доки контейнер не отримає `OOMKilled`. Тому `maxmemory` треба ставити **завжди**.

Скільки ставити? Не всю пам'ять сервера. Понад `maxmemory` Redis потрібна пам'ять на:

- **copy-on-write під час `fork`** (RDB, AOF rewrite, full sync репліки): при інтенсивному записі — аж до розміру датасету (розділ 6.2);
- **буфери клієнтів і реплік** (output buffers): буфери реплік і AOF навмисно **не враховуються** в `maxmemory` (пояснення — у 5.4);
- **фрагментацію** алокатора;
- операційну систему і page cache.

Практичне правило: з persistence і репліками — `maxmemory` десь **50–70% RAM**, для чистого кешу без persistence — до ~80–85%. У Kubernetes те саме рахується від memory limit контейнера.

### 5.2 Політики витіснення (`maxmemory-policy`)

Коли пам'ять дійшла до `maxmemory`, Redis діє відповідно до політики:

| Політика | Що витісняє | Коли використовувати |
|---|---|---|
| `noeviction` (**за замовчуванням**) | Нічого. Команди, що збільшують пам'ять, отримують помилку `OOM` | Redis як сховище, де втрачати дані не можна |
| `allkeys-lru` | Ключі, які найдовше не читали | Типовий кеш |
| `allkeys-lfu` | Ключі, які рідко читають | Кеш з чітко вираженими «гарячими» ключами |
| `allkeys-random` | Випадкові ключі | Рівномірний доступ (рідко) |
| `volatile-lru` / `volatile-lfu` / `volatile-random` | Те саме, але **лише серед ключів з TTL** | Мікс кешу і даних в одному інстансі |
| `volatile-ttl` | Ключі з найменшим залишком TTL | Коли TTL відображає «цінність» ключа |
| `allkeys-lrm` / `volatile-lrm` (**Redis 8.6+**, у Valkey немає) | Ключі, які найдовше не **змінювали** (Least Recently Modified): читання «свіжість» не оновлює | Коли цінність ключа визначає оновлення, а не читання: ключ, який часто читають, але давно не оновлювали, вважається застарілим і йде першим |

Отже, у Redis 8.6+ політик уже десять, а не вісім, як пишуть у більшості старих матеріалів.

> **Пастка №1:** з `noeviction` при заповненні пам'яті Redis **не падає**, а відмовляє в записі: `OOM command not allowed when used memory > 'maxmemory'`. Читання і `DEL` працюють. Для кешу це гірше, ніж витіснення: застосунок починає сипати помилками.
>
> **Пастка №2:** з `volatile-*` Redis витісняє лише ключі з TTL. Якщо таких немає (а розробники забули ставити TTL), `volatile-lru` поводиться **як `noeviction`** — і ти отримуєш OOM-помилки при «налаштованому витісненні».

### 5.3 LRU і LFU у Redis — наближені

Справжній LRU вимагав би тримати всі ключі у зв'язаному списку і переставляти їх при кожному зверненні, а це пам'ять і CPU. Redis робить простіше:

- у кожного об'єкта є 24-бітне поле з часом останнього доступу (для LFU — лічильник частоти);
- при витісненні Redis бере **випадкову вибірку** з `maxmemory-samples` ключів (за замовчуванням 5) і кладе найкращих кандидатів у невеликий **eviction pool**, звідки й витісняє;
- `maxmemory-samples 10` дає результат, майже не відмінний від справжнього LRU, ціною трохи більшого CPU.

**LFU** (з Redis 4.0) зберігає не кількість звернень, а логарифмічний лічильник (Morris counter) на 8 біт: чим більший лічильник, тим менша ймовірність, що наступне звернення його збільшить. Лічильник з часом «остигає», щоб колись популярний, а тепер забутий ключ не жив вічно. Налаштування — `lfu-log-factor` і `lfu-decay-time`. Новий ключ стартує не з нуля, а з невеликого значення, інакше його витіснили б одразу після створення.

### 5.4 Що, крім даних, їсть пам'ять

```bash
redis-cli INFO memory
```

| Поле | Що означає |
|---|---|
| `used_memory` | Скільки виділив алокатор Redis (дані + накладні витрати) |
| `used_memory_rss` | Скільки пам'яті процесу бачить ОС (resident set size) |
| `used_memory_peak` | Пік `used_memory` |
| `used_memory_dataset` | Власне дані |
| `used_memory_overhead` | Структури сервера, буфери клієнтів, backlog |
| `mem_clients_normal` | Буфери звичайних клієнтів |
| `mem_clients_slaves` | Буфери реплік |
| `mem_replication_backlog` | Replication backlog |
| `mem_not_counted_for_evict` | Пам'ять, яка не враховується при порівнянні з `maxmemory` |
| `mem_fragmentation_ratio` | `used_memory_rss / used_memory` |

Типові «пожирачі» пам'яті, які не видно в `DBSIZE`:

- **Output buffers клієнтів.** Повільний підписник pub/sub, `MONITOR`, клієнт, що запросив `HGETALL` на мільйон полів і повільно читає. Ліміти: `client-output-buffer-limit` (для `normal` за замовчуванням ліміту немає!) і `maxmemory-clients` (з 7.0) для витіснення самих клієнтів. Хто саме їсть пам'ять — поле `omem` у `CLIENT LIST`.
- **Буфери реплік і replication backlog** (розділ 7).
- **Lua-скрипти** і кеш скриптів, особливо коли скрипти генерують динамічно, з даними всередині тексту.
- **Накладні витрати на ключ**: запис у хеш-таблиці, заголовок об'єкта, SDS, окремий запис у таблиці TTL. Для дрібних значень оверхед може бути більшим за самі дані.

**Чому буфери реплік не враховуються в `maxmemory`?** Інакше можливий смертельний цикл: буфер репліки росте → Redis витісняє ключі → кожне витіснення — це `DEL`, який теж летить у буфер репліки → буфер росте ще більше → Redis витісняє ще… і так доки база не спорожніє. Тому `redis.conf` прямо радить залишати запас RAM понад `maxmemory`, якщо є репліки.

### 5.5 Фрагментація

`mem_fragmentation_ratio = used_memory_rss / used_memory`:

| Значення | Що це означає |
|---|---|
| ~1.0–1.5 | Норма |
| > 1.5 | Помітна фрагментація: ОС тримає за Redis більше, ніж йому реально треба |
| < 1.0 | **Частину пам'яті Redis витіснено у swap.** Latency летить у космос, це гірше за фрагментацію |
| Дуже велике (5, 10…) на майже порожньому інстансі | Нормально: базова RSS процесу на тлі крихітного датасету |

Звідки фрагментація: Redis (через jemalloc) виділяє і звільняє дрібні шматки пам'яті різного розміру. Після масового видалення ключів звільнене місце розкидане по сторінках, і **RSS не зменшується**: алокатор тримає ці сторінки для нових даних. Тому «видалили половину ключів, а пам'ять процесу не впала» — нормальна поведінка, а не витік.

Що робити:

```bash
redis-cli MEMORY DOCTOR                  # Redis сам підкаже, що не так
redis-cli MEMORY PURGE                   # попросити jemalloc віддати ОС брудні сторінки
redis-cli CONFIG SET activedefrag yes    # активна дефрагментація на льоту (лише з jemalloc)
```

`activedefrag` переміщує значення у пам'яті, щоб звільнити сторінки, і робить це поступово, у межах заданого відсотка CPU (`active-defrag-cycle-min` / `-max`). Інший спосіб — перезапуск або failover на репліку, яка після full sync завантажила дані «начисто».

### 5.6 Як економити пам'ять

- **Ставити TTL** на все, що є кешем.
- **Тримати колекції в межах listpack-порогів**, де це можливо (трюк з хеш-кошиками з розділу 3.4).
- **Короткі імена ключів** мають сенс лише при сотнях мільйонів ключів, але `user:1000:profile` замість `application:production:user_profile:1000` — безкоштовна економія.
- **Стискати великі значення на клієнті** (zstd, lz4, gzip), особливо JSON.
- **Не зберігати те, що можна порахувати**, і не дублювати дані в кількох форматах.
- **Розбирати пам'ять за фактами:** `MEMORY USAGE key`, `redis-cli --bigkeys` / `--memkeys`, аналіз RDB-файлу офлайн.

### 5.7 Big keys і hot keys

**Big key** — ключ з величезним значенням: String на 50 МБ, хеш на 5 мільйонів полів, список на 10 мільйонів елементів. Чим поганий:

- будь-яка O(N)-операція над ним блокує сервер;
- `DEL` блокує (рятує `UNLINK`), так само як і протухання по TTL, якщо не ввімкнено `lazyfree-lazy-expire` (у Valkey 8+ він увімкнений за замовчуванням, у Redis — ні);
- кожне читання — сплеск мережевого трафіку;
- у Cluster він не ділиться між шардами: один вузол переповнений, інші порожні;
- при решардингу `MIGRATE` такого ключа блокує обидва вузли і може впасти по таймауту.

**Hot key** — ключ, на який припадає непропорційно багато запитів (головна сторінка, конфіг фіче-флагів, лічильник популярного товару). Він упирає один вузол (одне ядро!) у стелю, незалежно від того, скільки шардів у кластері.

Як знайти:

```bash
redis-cli --bigkeys                 # найбільший ключ кожного типу (за кількістю елементів), через SCAN
redis-cli --memkeys                 # найбільші ключі за пам'яттю (MEMORY USAGE)
redis-cli --hotkeys                 # найгарячіші ключі; вимагає maxmemory-policy *-lfu
redis-cli MEMORY USAGE mykey SAMPLES 0    # точний розмір ключа (0 = порахувати всі елементи)
redis-cli OBJECT FREQ mykey         # LFU-лічильник ключа (лише з LFU-політикою)
redis-cli --keystats                # 7.4+: --bigkeys і --memkeys разом, плюс розподіл розмірів (перцентилі)
redis-cli HOTKEYS START METRICS 2 CPU NET COUNT 10 DURATION 60   # Redis 8.6+: hot keys без LFU-політики
redis-cli HOTKEYS GET               # топ ключів за часом CPU і мережевим трафіком
```

`--hotkeys` працює лише з LFU-політикою, бо бере частоту з LFU-лічильників ключів. Команда `HOTKEYS` у Redis 8.6+ рахує реальний час CPU і байти мережі на ключ і LFU не потребує. У кластері допомагає `CLUSTER SLOT-STATS` (Redis 8.2+, Valkey 8.0+), який показує навантаження по слотах.

`--bigkeys`, `--memkeys`, `--keystats` і `--hotkeys` обходять ключі через `SCAN`, тож сервер не блокують, але створюють навантаження. На дуже великих інстансах краще запускати їх на репліці або аналізувати RDB-файл офлайн.

Як лікувати:

- **Big key:** розбити на кілька ключів (`user:42:events:2026-10`, по місяцях), шардувати хеш за префіксом, читати порціями (`HSCAN`, `ZRANGE` з діапазоном), видаляти через `UNLINK`, стискати значення.
- **Hot key:** локальний кеш у застосунку з коротким TTL (або client-side caching, розділ 11.6), читання з реплік, кілька копій ключа (`config:{1..8}`) і випадковий вибір копії при читанні.

## 6. Persistence: RDB, AOF і fork {#persistence}

Redis тримає дані в пам'яті, а на диск пише лише для того, щоб пережити перезапуск. Варіантів чотири:

| Режим | Що на диску | Скільки можна втратити | Коли |
|---|---|---|---|
| Без persistence | Нічого | Усе | Чистий кеш, який легко прогріти з БД |
| RDB | Періодичний снапшот | Усе після останнього снапшота (хвилини) | Кеш, який шкода втрачати; бекапи |
| AOF | Журнал усіх записів | ~1 секунду (`everysec`) | Дані, які не можна втратити |
| RDB + AOF | Обидва | ~1 секунду | Рекомендований варіант для «сховища» |

### 6.1 RDB: снапшот через fork

RDB — компактний бінарний дамп усього датасету в один файл (`dump.rdb`).

```
            BGSAVE (за розкладом save або вручну)
                         │
   main thread ──────────┼─── fork() ─────────────────────────────▶ обслуговує клієнтів далі
                         │       │   (на час fork main thread стоїть)
                         │       ▼
                         │   дочірній процес бачить "заморожену" копію пам'яті
                         │   і пише її у temp-<pid>.rdb
                         │       │
                         │       ▼
                         │   rename(temp-<pid>.rdb → dump.rdb)  — атомарно
```

- Розклад задає `save <секунди> <змін>`. Вбудований дефолт — `save 3600 1 300 100 60 10000`: снапшот через годину, якщо була хоч одна зміна, через 5 хвилин, якщо змін 100, і щохвилини, якщо змін 10 000. (У `redis.conf` до версії 6.0 включно стояло `save 900 1`, `save 300 10`, `save 60 10000`.) Вимкнути — `save ""`.
- `BGSAVE` робить снапшот у дочірньому процесі. `SAVE` робить його **в main thread і блокує сервер** на весь час запису. На проді `SAVE` руками не запускають.
- Файл пишеться в тимчасовий і **атомарно перейменовується**, тому копіювати `dump.rdb` для бекапу можна будь-коли.
- При `SHUTDOWN` (і `SIGTERM`), якщо налаштовані save-точки, Redis робить фінальний синхронний снапшот. `SHUTDOWN NOSAVE` — без нього.
- Якщо `BGSAVE` впав (немає місця, немає прав, не вдався fork), то з дефолтним `stop-writes-on-bgsave-error yes` Redis **перестає приймати записи**: `MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk`. Це захист: краще помітна відмова, ніж тиха робота без бекапів.

Плюси RDB: компактний файл, швидке завантаження при старті, зручно для бекапів і реплікації. Мінус: втрачається все, що записано після останнього снапшота.

### 6.2 Fork і copy-on-write: головний ризик persistence

`fork()` не копіює пам'ять процесу одразу, а лише таблиці сторінок. Сторінки спільні для батька і дитини, доки хтось у них не запише: тоді ядро копіює сторінку (**copy-on-write**, COW). Що з цього випливає:

1. **На час самого `fork()` main thread стоїть.** Копіювання таблиць сторінок займає приблизно 10–20 мс на кожен гігабайт на сучасному залізі й віртуалках, а на старих Xen-віртуалках доходило до сотень мілісекунд на гігабайт. Інстанс на 50 ГБ «замерзає» на сотні мілісекунд при кожному `BGSAVE`. Скільки тривав останній fork — `latest_fork_usec` в `INFO stats`.
2. **Пам'ять може подвоїтися.** Кожна сторінка, яку змінили, поки дитина пише RDB, копіюється. При інтенсивному записі процеси разом займуть до 2× розміру датасету. Скільки скопіювали — `rdb_last_cow_size` і `current_cow_size` в `INFO persistence`. Звідси правило запасу RAM понад `maxmemory` із розділу 5.1.
3. **Transparent Huge Pages (THP) у режимі `always` роблять усе гірше:** копіюється не сторінка в 4 КБ, а 2 МБ, і кожен дрібний запис під час fork коштує дорого. Redis при старті попереджає, якщо THP у режимі `always`, і радить `madvise` або `never`. З версії 6.2 параметр `disable-thp yes` (дефолт) вимикає THP для самого процесу Redis навіть при `always`, але надійніше налаштувати це на рівні ОС.
4. **`vm.overcommit_memory = 0`** (дефолт ядра) може відмовити у fork великого процесу, хоча реально через COW стільки пам'яті не знадобиться: `Can't save in background: fork: Cannot allocate memory`. Redis при старті прямо пише: `WARNING Memory overcommit must be enabled!`.

```bash
# Налаштування ОС для Redis (зберегти в /etc/sysctl.d/ і в systemd unit / tmpfiles)
sysctl -w vm.overcommit_memory=1
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled   # або never; головне — не always
```

> **Практичний висновок:** на великих і навантажених на запис інстансах снапшоти часто роблять **на репліці**, а на master persistence вимикають або залишають лише AOF. Але тоді обов'язково прочитай розділ 6.7.

### 6.3 AOF: журнал записів

AOF (Append Only File) — журнал усіх команд, що змінюють дані, у форматі RESP. При старті Redis просто «програє» його заново.

```
appendonly yes
# варіанти: always | everysec | no
appendfsync everysec
```

| `appendfsync` | Як працює | Скільки можна втратити | Ціна |
|---|---|---|---|
| `always` | `fsync` після кожної ітерації event loop, перед відповіддю клієнтам | Практично нічого | Latency і пропускна здатність прив'язані до диска |
| `everysec` (**дефолт**) | `fsync` раз на секунду у фоновому потоці | ~1 секунду (у гіршому випадку ~2) | Майже безкоштовно |
| `no` | `fsync` вирішує ОС (зазвичай раз на ~30 с) | Десятки секунд | Найшвидше |

Чому при `everysec` може бути й 2 секунди: якщо диск не встигає і попередній `fsync` ще триває, Redis якийсь час чекає, а потім пише без `fsync`, щоб не блокувати сервер. У лозі з'являється `Asynchronous AOF fsync is taking too long (disk is busy?)`. Це сигнал, що диск не тягне.

**AOF rewrite.** Журнал постійно росте: мільйон `INCR counter` — це мільйон записів, хоча стан описує одна команда `SET counter 1000000`. Тому Redis періодично переписує AOF (`BGREWRITEAOF`, автоматично за `auto-aof-rewrite-percentage 100` і `auto-aof-rewrite-min-size 64mb`): дочірній процес через fork записує поточний стан компактно.

**Multi-part AOF (з Redis 7.0).** AOF — це вже не один файл, а каталог `appendonlydir/`:

```
appendonlydir/
├── appendonly.aof.1.base.rdb    # базовий знімок (у форматі RDB, бо aof-use-rdb-preamble yes)
├── appendonly.aof.1.incr.aof    # інкрементальні команди після базового знімка
└── appendonly.aof.manifest      # який файл base, які incr і в якому порядку
```

Під час rewrite Redis відкриває новий incr-файл, а дитина пише новий base; після цього маніфест атомарно оновлюється, а старі файли видаляються. Завантаження при старті: base (швидко, бо це RDB) плюс програвання incr.

Якщо Redis упав посеред запису і останній запис в AOF обрізаний, з дефолтним `aof-load-truncated yes` він завантажить усе, що можна, і напише попередження. Якщо файл пошкоджений посередині, Redis не стартує, і тоді допоможе `redis-check-aof --fix` (спершу зроби копію файлу).

### 6.4 RDB чи AOF?

| | RDB | AOF |
|---|---|---|
| Втрата даних при падінні | Від останнього снапшота (хвилини) | ~1 с з `everysec` |
| Розмір на диску | Компактний | Більший, росте до rewrite |
| Швидкість старту | Швидко | Повільніше (з RDB-преамбулою — майже як RDB) |
| Навантаження | fork за розкладом | Постійний запис на диск + fork на rewrite |
| Бекапи | Ідеально: один файл | Каталог, обережно з rewrite (розділ 6.6) |

Офіційна рекомендація: якщо потрібна надійність, близька до PostgreSQL, вмикай обидва. Якщо дані — кеш, який можна втратити, вистачить RDB або взагалі нічого.

> **Пастка: як увімкнути AOF на живому інстансі.** Якщо в Redis з RDB просто прописати `appendonly yes` у конфіг і перезапустити, Redis при старті шукатиме AOF, не знайде його і може стартувати **з порожньою базою**. Документація прямо попереджає про втрату даних. Правильно: `CONFIG SET appendonly yes` на живому сервері, дочекатися завершення rewrite (`aof_rewrite_in_progress:0` в `INFO persistence`), потім `CONFIG REWRITE` або правка `redis.conf`.

### 6.5 FLUSHALL і persistence

Дві речі, які корисно знати до того, як хтось виконає `FLUSHALL` на проді:

- **З налаштованими save-точками `FLUSHALL` одразу синхронно перезаписує `dump.rdb` порожнім снапшотом.** Попередній знімок на диску зникає за мілісекунди (і з `ASYNC` теж). Рятують лише бекапи, що лежать **деінде**.
- **З AOF шанс є.** `FLUSHALL` — це просто ще одна команда в журналі. Якщо rewrite ще не відбувся:

```bash
redis-cli CONFIG SET auto-aof-rewrite-percentage 0   # 1. заборонити rewrite, інакше історія зникне
redis-cli SHUTDOWN                                   # 2. зупинити Redis
cp -a appendonlydir appendonlydir.bak                # 3. бекап
# 4. в останньому *.incr.aof видалити запис "*1\r\n$8\r\nFLUSHALL\r\n"
#    (і все, що після нього, якщо ці записи теж не потрібні)
redis-server /etc/redis/redis.conf                   # 5. стартувати: дані повернуться
```

Репліки отримали `FLUSHALL` через реплікацію і теж порожні. Тому захист від цієї команди — ACL (розділ 12), а не надія на диск.

### 6.6 Бекапи

- **RDB** копіювати безпечно будь-коли (атомарний `rename`). Типова схема: `BGSAVE` (або розклад) → копія `dump.rdb` з таймстемпом → S3 / інше сховище. Віддалено зняти RDB з інстансу: `redis-cli --rdb /backup/dump-$(date +%F).rdb`.
- **AOF (7.0+)** — копіювати каталог `appendonlydir` цілком, але **не під час rewrite**: тимчасово `CONFIG SET auto-aof-rewrite-percentage 0`, перевірити `aof_rewrite_in_progress:0`, скопіювати, повернути налаштування.
- **Redis 8.10** додав команду `BACKUP` — серверну реалізацію бекапу і відновлення на основі multi-part AOF.
- **Відновлення треба тестувати.** Бекап, з якого ніхто ніколи не піднімав Redis, бекапом не є. І пам'ятай, що RDB нової версії не завантажиться старішим сервером: формат RDB має версію (7.4 → 12, 8.6 → 13, 8.8 → 14, 8.10 → 15), а downgrade не підтримується.

### 6.7 Пастка: master без persistence і автоперезапуск

Класичний сценарій, через який втрачали дані цілком «надійні» кластери з репліками. Його описує сама документація Redis:

```
1. master (persistence вимкнено) ──реплікація──▶ replica B, replica C   (дані є на всіх)
2. master падає; systemd / Kubernetes миттєво перезапускає його
3. master стартує з ПОРОЖНЬОЮ базою (диска ж немає)
4. B і C бачать, що master повернувся, і роблять full sync...
5. ...з порожнього master. Дані знищено на всіх трьох вузлах.
```

З Sentinel те саме: master може перезапуститися швидше, ніж Sentinel помітить падіння (`down-after-milliseconds`), і failover не почнеться.

Правило: **якщо на master немає persistence, він не повинен автоматично перезапускатися**, або в нього має бути увімкнена persistence. У Kubernetes це особливо підступно, бо там автоперезапуск — поведінка за замовчуванням.

## 7. Реплікація {#replication}

### 7.1 Як працює

Master-replica, асинхронна, один master — багато реплік (і репліки реплік).

```bash
# на репліці (або replicaof в конфігу)
REPLICAOF 10.0.0.1 6379
```

У кожного master є **replication ID** (випадковий рядок) і **offset** — скільки байтів потоку реплікації він згенерував. Репліка пам'ятає ID свого master і свій offset.

```
                       PSYNC <replid> <offset>
   replica ───────────────────────────────────────────────▶ master
                                                              │
                ┌─── replid збігається і offset ще є ─────────┤
                │    у replication backlog?                   │
                ▼                                             ▼
   +CONTINUE: partial resync                     +FULLRESYNC: full sync
   master досилає лише                           master робить RDB (fork),
   пропущений шматок потоку                      передає весь датасет,
   (швидко, дешево)                              потім потік змін (дорого)
```

- **Partial resync** можливий, якщо пропущений шматок ще лежить у **replication backlog** — кільцевому буфері на master (`repl-backlog-size`, у Redis за замовчуванням лише **1 МБ**, у Valkey — 10 МБ).
- **Full sync**: master робить RDB через fork (з 7.0 за замовчуванням diskless: `repl-diskless-sync yes`, тобто RDB одразу йде в сокет, без диска), репліка завантажує його, викинувши свої дані, і далі отримує потік команд.
- **PSYNC2** (з 4.0): після failover новий master пам'ятає ID старого, тому інші репліки можуть зробити partial resync до нього, а не full sync. Репліка, яку коректно перезапустили, теж може продовжити з partial resync.

**Нова схема full sync у Redis 8.** У Redis 8.0+ (з diskless sync) RDB і потік реплікації йдуть **двома з'єднаннями паралельно**, а потік змін накопичується **на репліці** (ліміт `replica-full-sync-buffer-limit`), а не в буфері master'а. Це зменшує пам'ять master'а під час синхронізації. У Valkey є схожа dual-channel реплікація (`dual-channel-replication-enabled`), але вона за замовчуванням вимкнена.

### 7.2 Реплікація асинхронна: що це означає

Master відповідає клієнту `OK` **до того**, як репліки отримали запис. Якщо master упав одразу після цього, а репліку зробили новим master, **підтверджений запис утрачено**. Інструменти, щоб зменшити ризик:

- **`WAIT numreplicas timeout`** — заблокувати клієнта, доки N реплік не підтвердять отримання запису (в пам'ять, не на диск). Повертає, скільки реплік підтвердили. Це не робить Redis strongly consistent: failover може обрати репліку без цього запису, але ймовірність втрати сильно падає.
- **`WAITAOF numlocal numreplicas timeout`** (7.2+) — дочекатися `fsync` в AOF локально і/або на репліках.
- **`min-replicas-to-write N` + `min-replicas-max-lag S`** — master відмовляє в записі (`NOREPLICAS Not enough good replicas to write.`), якщо в нього менше N реплік з лагом не більше S секунд. Головний захист від split-brain (розділ 8.4).

### 7.3 Пастка: нескінченний full sync

Сценарій, який виглядає як «репліка ніяк не може синхронізуватися»:

1. Репліка відвалилась на хвилину (мережа, рестарт).
2. Поки її не було, master згенерував більше даних, ніж уміщує backlog (1 МБ — це менше секунди на навантаженому інстансі), тому partial resync неможливий → **full sync**.
3. Поки master робить і передає RDB великого датасету, нові записи накопичуються в буфері для репліки. Буфер перевищує `client-output-buffer-limit replica 256mb 64mb 60` (256 МБ одразу або 64 МБ протягом 60 секунд) → master **розриває з'єднання**.
4. Репліка підключається знову → новий full sync → новий fork → знову переповнення буфера → і так по колу. Master при цьому раз за разом робить fork і жере CPU, пам'ять і мережу.

У лозі master: `scheduled to be closed ASAP for overcoming of output buffer limits`, а в `INFO stats` стрімко росте `sync_full`.

Лікування:

```bash
# Backlog: швидкість потоку реплікації × час можливого відключення × запас.
# Наприклад, 5 МБ/с × 60 с × 2 ≈ 600 МБ
redis-cli CONFIG SET repl-backlog-size 512mb
# Дати full sync завершитися
redis-cli CONFIG SET client-output-buffer-limit "replica 1gb 512mb 120"
```

Швидкість потоку видно з того, як росте `master_repl_offset` в `INFO replication` (байтів за секунду). Для нових версій частину проблеми знімає rdb-channel реплікація Redis 8 (буфер тепер на репліці, але ліміт усе одно є).

### 7.4 Репліки: що треба знати

- **`replica-read-only yes`** (дефолт). Записати в репліку не вийде: `READONLY You can't write against a read only replica.` Писати в репліку можна, але це майже завжди погана ідея: при наступному full sync ці дані зникнуть.
- **Читання з реплік — це stale reads.** Лаг зазвичай мілісекунди, але під навантаженням чи при проблемах з мережею — секунди і більше. «Записав у master — одразу прочитав з репліки» може повернути старе значення.
- **`replica-serve-stale-data yes`**: якщо зв'язок з master втрачено, репліка далі відповідає старими даними. З `no` — помилкою.
- **Репліки не протухають ключі самі** і не витісняють за `maxmemory` (`replica-ignore-maxmemory yes`): вони чекають `DEL` від master. Тому пам'яті на репліці має бути не менше, ніж на master.
- **Під час full sync репліка завантажує новий датасет** і на цей час (якщо не ввімкнено async loading через `repl-diskless-load swapdb`) відповідає `LOADING Redis is loading the dataset in memory`.

Моніторинг лагу:

```bash
redis-cli INFO replication
# на master:
# slave0:ip=10.0.0.2,port=6379,state=online,offset=8812345,lag=0
# master_repl_offset:8812345            ← lag у байтах = master_repl_offset - offset репліки
# на репліці:
# master_link_status:up                 ← down = проблема
# master_last_io_seconds_ago:0          ← скільки секунд тиші від master
# master_sync_in_progress:0             ← 1 = зараз іде full sync
```

## 8. Sentinel: автоматичний failover {#sentinel}

Реплікація сама по собі не робить failover: якщо master упав, репліки так і лишаться репліками. **Redis Sentinel** — окремі процеси (зазвичай порт 26379), які:

- **моніторять** master і репліки;
- **сповіщають** (pub/sub-події, скрипти) про проблеми;
- **роблять автоматичний failover**: обирають репліку, промоутять її в master і перенаправляють на неї інші репліки;
- **працюють як configuration provider**: клієнт питає Sentinel «хто зараз master?», а не тримає IP у конфігу.

Sentinel не проксує трафік і не шардує дані. Він лише стежить і переконфігуровує.

### 8.1 Як Sentinel вирішує, що master помер

```
# останнє число — quorum
sentinel monitor mymaster 10.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
```

1. **SDOWN (subjectively down)** — один Sentinel не отримав валідної відповіді на `PING` протягом `down-after-milliseconds`.
2. **ODOWN (objectively down)** — щонайменше **quorum** Sentinel'ів погодилися, що master у SDOWN.
3. **Вибори лідера.** Щоб почати failover, один Sentinel має отримати голоси **більшості всіх Sentinel'ів** (не quorum!). Кожні вибори мають свою епоху (epoch), як у Raft.
4. **Вибір репліки.** Відкидаються репліки, які надто довго не мали зв'язку з master. Решта сортуються: спершу менший `replica-priority` (0 — ніколи не промоутити), потім більший replication offset (більше даних), потім менший run ID.
5. **Промоушн:** `REPLICAOF NO ONE` на обраній репліці, інші репліки перенаправляються на неї (по `parallel-syncs` за раз), конфігурація оновлюється і розсилається всім Sentinel'ам. Старий master, коли повернеться, стане реплікою.

> **Quorum vs majority — улюблене питання на співбесіді.** Quorum впливає лише на **виявлення** падіння (ODOWN). Для самого failover потрібна **більшість** Sentinel'ів. Наприклад, з 5 Sentinel'ами і quorum 2 двох достатньо, щоб визнати master мертвим, але failover почнеться, тільки якщо ще живі й доступні щонайменше 3.

### 8.2 Чому Sentinel'ів мінімум три і де їх ставити

```
ПОГАНО: 2 Sentinel'и                        ДОБРЕ: 3 Sentinel'и на 3 незалежних вузлах
┌────────────────┐  ┌────────────────┐      ┌───────────┐  ┌───────────┐  ┌───────────┐
│ host A         │  │ host B         │      │ host A    │  │ host B    │  │ host C    │
│ master  + S1   │  │ replica + S2   │      │ master    │  │ replica   │  │ replica   │
└────────────────┘  └────────────────┘      │ + S1      │  │ + S2      │  │ + S3      │
host A помер: S2 — це 1 з 2, не більшість,  └───────────┘  └───────────┘  └───────────┘
failover НЕМОЖЛИВИЙ                         host A помер: S2 + S3 = 2 з 3 → failover
```

- Sentinel'и мають стояти в **незалежних зонах відмови** (різні хости, ідеально — різні AZ). Три Sentinel'и на одному гіпервізорі — це один Sentinel.
- Sentinel'и можна ставити й на хости застосунків — це навіть корисно: вони «бачать» мережу так само, як клієнти.
- Sentinel'и самі знаходять один одного та репліки через pub/sub-канал `__sentinel__:hello` на master, а свій стан **записують у свій конфіг-файл**. Тому файл має бути доступний на запис (у Docker і Kubernetes про це часто забувають).

### 8.3 Клієнти мають знати про Sentinel

Після failover IP master'а змінився. Клієнт має:

- при підключенні питати Sentinel: `SENTINEL get-master-addr-by-name mymaster`;
- перепідключатися при помилці `READONLY` (він пише в старий master, який уже став реплікою) або при обриві з'єднання;
- за бажання підписатися на подію `+switch-master`.

Більшість бібліотек (Jedis, Lettuce, redis-py, go-redis, ioredis) це вміють, але треба явно використати Sentinel-клієнт, а не звичайний з IP.

> **Docker / NAT / Kubernetes:** Sentinel і репліки анонсують свої IP та порти. За NAT чи з перенаправленням портів анонсуються внутрішні адреси, до яких ніхто не може достукатися. Рішення: `sentinel announce-ip` / `announce-port`, `replica-announce-ip`, host networking, або з 6.2 — hostnames (`sentinel resolve-hostnames yes`, `sentinel announce-hostnames yes`).

### 8.4 Split-brain і втрата записів

```
                    мережевий розрив
     ┌──────────────────────┐ ║ ┌────────────────────────────────────┐
     │ старий master M1     │ ║ │ S1, S2, S3 (більшість)             │
     │ клієнт X далі пише   │ ║ │ промоутять R1 → новий master M2    │
     │ сюди: SET a 1 ... OK │ ║ │ інші клієнти пишуть у M2           │
     └──────────────────────┘ ║ └────────────────────────────────────┘
                              ║
     розрив зник: M1 стає реплікою M2 → full sync → усе, що клієнт X
     записав у M1 під час розриву, ЗНИКАЄ
```

Повністю уникнути втрат Redis не вміє (реплікація асинхронна), але можна обмежити вікно:

```
min-replicas-to-write 1
min-replicas-max-lag 10
```

Ізольований master через 10 секунд без підтверджень від реплік почне відмовляти в записі (`NOREPLICAS`), тож клієнт X втратить не більше ~10 секунд записів. Ціна: якщо репліки справді впадуть, master теж перестане приймати записи. Це свідомий вибір між доступністю і цілісністю.

### 8.5 Корисні команди

```bash
redis-cli -p 26379 SENTINEL masters                         # що моніторимо
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
redis-cli -p 26379 SENTINEL replicas mymaster
redis-cli -p 26379 SENTINEL sentinels mymaster              # інші Sentinel'и
redis-cli -p 26379 SENTINEL ckquorum mymaster               # чи досяжні quorum і більшість
redis-cli -p 26379 SENTINEL failover mymaster               # ручний failover (без згоди інших)
redis-cli -p 26379 SENTINEL reset mymaster                  # забути старі репліки/Sentinel'и
```

Для планових робіт без Sentinel є команда **`FAILOVER`** (6.2+): master сам координує перемикання на репліку, спершу дочекавшись, поки вона наздожене його offset, тому дані не губляться.

## 9. Redis Cluster: шардинг {#cluster}

Sentinel дає HA, але всі дані однаково мусять уміститися в пам'ять одного master, і весь запис іде в одне ядро. **Redis Cluster** розподіляє дані між кількома master'ами (шардами), у кожного з яких свої репліки.

### 9.1 16384 слоти

Простір ключів поділено на **16384 hash slots**. Слот ключа:

```
HASH_SLOT = CRC16(key) mod 16384
```

Кожен master відповідає за свій набір слотів:

```
      master A: слоти 0–5460        master B: 5461–10922        master C: 10923–16383
      ┌──────────────┐              ┌──────────────┐             ┌──────────────┐
      │   A          │              │   B          │             │   C          │
      └──────┬───────┘              └──────┬───────┘             └──────┬───────┘
             │ реплікація                  │                            │
      ┌──────▼───────┐              ┌──────▼───────┐             ┌──────▼───────┐
      │   A1         │              │   B1         │             │   C1         │
      └──────────────┘              └──────────────┘             └──────────────┘
      усі вузли з'єднані між собою по cluster bus (порт клієнта + 10000) і обмінюються gossip
```

```bash
redis-cli CLUSTER KEYSLOT foo           # 12182
redis-cli CLUSTER KEYSLOT bar           # 5061
```

**Чому саме 16384?** Автор Redis пояснював це так: кожен heartbeat-пакет між вузлами несе бітмап слотів вузла. 16384 біти — це 2 КБ, а 65536 — це вже 8 КБ у кожному ping/pong. При цьому кластер понад ~1000 master'ів не планувався, тож 16384 слотів вистачає з запасом.

### 9.2 Hash tags і CROSSSLOT

Команди з кількома ключами (`MGET`, `MSET`, `SUNION`, `RENAME`, транзакції, Lua-скрипти) працюють лише тоді, коли **всі ключі в одному слоті**. Інакше:

```
127.0.0.1:7001> MSET foo 1 bar 2
(error) CROSSSLOT Keys in request don't hash to the same slot
```

Щоб пов'язані ключі гарантовано опинилися в одному слоті, використовують **hash tags**: якщо в ключі є `{...}`, хешується лише вміст фігурних дужок.

```bash
CLUSTER KEYSLOT {user:1000}:profile    # 1649
CLUSTER KEYSLOT {user:1000}:cart       # 1649 — той самий слот
MSET {user:1000}:profile "..." {user:1000}:cart "..."    # працює
```

Нюанси, які люблять питати:

- хешується вміст **першої** пари `{` … `}`, і лише якщо він не порожній. `foo{}{bar}` хешується цілком, бо перша пара порожня;
- `foo{{bar}}zap` хешує `{bar` (від першої `{` до першої `}`);
- надмірне використання hash tags (наприклад, `{tenant}` для всіх ключів великого клієнта) складає все в один слот → один перевантажений шард.

### 9.3 MOVED, ASK і «розумні» клієнти

Клієнт може відправити команду будь-якому вузлу. Якщо слот не його:

```
127.0.0.1:7001> GET foo
(error) MOVED 12182 127.0.0.1:7003
```

- **`MOVED`** — «цей слот постійно живе на іншому вузлі». Клієнт має повторити запит туди і **оновити свою карту слотів** (через `CLUSTER SHARDS` або `CLUSTER SLOTS`).
- **`ASK`** — слот **зараз мігрує**, і саме цього ключа на старому вузлі вже немає. Клієнт має відправити на новий вузол спершу `ASKING`, потім команду. Це **одноразовий** редірект, карту слотів оновлювати не треба: міграція ще не завершена.

```
(error) ASK 12182 127.0.0.1:7001      # на новий вузол: ASKING + GET foo
```

Нормальні клієнтські бібліотеки тримають карту слотів у пам'яті й одразу шлють запит на правильний вузол, тож редіректи трапляються лише після змін топології. `redis-cli` для роботи з кластером запускають з `-c`, тоді він сам ходить за редіректами. Якщо в логах застосунку купа `MOVED`, значить клієнт не cluster-aware або не оновлює карту слотів.

Читання з реплік у кластері вимагає команди `READONLY` на з'єднанні з реплікою, інакше вона теж відповість `MOVED` на свій master.

### 9.4 Failover у кластері

Окремий Sentinel кластеру не потрібен, failover вбудований:

1. Вузол, який не отримує відповіді від іншого довше за `cluster-node-timeout` (типово 15 с), позначає його **PFAIL**.
2. Коли більшість master'ів повідомили про PFAIL (через gossip), вузол позначається **FAIL**, і ця новина розсилається всім.
3. Репліки впалого master'а запитують голоси в **master'ів**. Репліка з найсвіжішими даними (більшим offset) стартує вибори раніше.
4. Репліка, яка отримала голоси більшості master'ів, стає новим master і забирає слоти.

Наслідки:

- **Мінімум 3 master'и**, бо голосують саме master'и, і після падіння одного решта має становити більшість. Типова мінімальна конфігурація — **3 master + 3 replica** на різних хостах.
- **Якщо впав master і всі його репліки**, частина слотів залишилась без власника. З дефолтним `cluster-require-full-coverage yes` **весь кластер** перестає обслуговувати запити: `CLUSTERDOWN The cluster is down`. З `no` вузли далі обслуговують свої слоти, а запити до «осиротілих» слотів отримують помилку.
- **`cluster-allow-reads-when-down yes`** (6.0+) дозволяє читати, коли кластер у стані fail.
- **Replica migration** (`cluster-migration-barrier`): якщо в одного master'а не залишилося реплік, кластер може «позичити» репліку в master'а, у якого їх кілька.
- **Записи можна втратити**, як і з Sentinel: реплікація асинхронна, а master у меншій частині кластера під час мережевого розриву приймає записи, поки не мине `cluster-node-timeout`.

### 9.5 Решардинг і масштабування

```bash
redis-cli --cluster create 10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
          10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 --cluster-replicas 1
redis-cli --cluster check 10.0.0.1:6379
redis-cli --cluster add-node 10.0.0.7:6379 10.0.0.1:6379             # додати порожній master
redis-cli --cluster rebalance 10.0.0.1:6379 --cluster-use-empty-masters
redis-cli --cluster reshard 10.0.0.1:6379                            # перенести N слотів вручну
redis-cli --cluster del-node 10.0.0.1:6379 <node-id>                 # спершу забрати всі слоти
```

Класично слоти переносяться **ключ за ключем** командою `MIGRATE`. Вона блокує обидва вузли на час переносу ключа, тому великий ключ (розділ 5.7) може спричинити помітні затримки або впасти по таймауту, і тоді слот застрягає в стані migrating / importing (лікується `redis-cli --cluster fix`).

**Атомарна міграція слотів.** Нові версії переносять слоти цілком на боці сервера, з реплікацією потоку змін під час переносу: у Valkey 9.0 це `CLUSTER MIGRATESLOTS`, у Redis 8.4 — `CLUSTER MIGRATION`. З Redis 8.10 `redis-cli --cluster reshard` і `rebalance` уже використовують цей механізм.

### 9.6 Обмеження кластера

- **Лише база 0**, `SELECT` заборонений: `ERR SELECT is not allowed in cluster mode`. Valkey 9.0+ це обмеження зняв: кількість баз у кластері задає `cluster-databases` (за замовчуванням 1).
- **Мультиключові операції** — лише в межах одного слота (hash tags).
- **`SCAN` і `KEYS`** працюють у межах вузла. Обходити треба кожен master (Valkey 9.1 додав `CLUSTERSCAN` для обходу всього кластера).
- **Pub/Sub:** звичайний `PUBLISH` розсилається через cluster bus **на всі вузли**, і це погано масштабується. З 7.0 є **sharded pub/sub** (`SSUBSCRIBE` / `SPUBLISH`): канал прив'язаний до слота, і повідомлення не виходить за межі шарда.
- **Docker / NAT / Kubernetes:** вузли анонсують свої IP і в `MOVED` віддають саме їх. Потрібні `cluster-announce-ip`, `cluster-announce-port`, `cluster-announce-bus-port` або `cluster-announce-hostname` (7.0+).
- **Файл `nodes.conf`** веде сам Redis (ID вузла, епохи, слоти). Руками його не редагують і між вузлами не копіюють.
- **Cluster bus не має власної автентифікації**, якщо не ввімкнено `tls-cluster`: будь-хто, хто дістається до порту bus, може втрутитися в кластер. Закривати його фаєрволом. У вересневих патчах 2026 року Redis почав попереджати про це при старті і додав опцію `cluster-bus-port-protected-mode`.

### 9.7 Sentinel чи Cluster?

| | Sentinel | Cluster |
|---|---|---|
| Що дає | HA (failover) | HA + шардинг |
| Обсяг даних | Вміщується в RAM одного вузла | Більше, ніж уміщує один вузол |
| Запис | Одне ядро одного master'а | Масштабується з кількістю master'ів |
| Мультиключові операції | Будь-які | Лише в одному слоті |
| Бази `SELECT` | Є | Лише 0 (у Valkey 9+ — через `cluster-databases`) |
| Клієнт | Sentinel-aware | Cluster-aware |
| Мінімальна конфігурація | 1 master + 1–2 репліки + 3 Sentinel | 3 master + 3 репліки |
| Складність експлуатації | Нижча | Вища |

Правило: поки дані й навантаження вміщуються в один вузол із запасом — **Sentinel** (або керований сервіс). Cluster — коли справді потрібен горизонтальний шардинг.

## 10. Атомарність: pipelining, MULTI/EXEC, Lua, Functions {#atomicity}

### 10.1 Кожна команда атомарна

Оскільки команди виконуються по одній, **будь-яка окрема команда атомарна**: `INCR` з тисячі клієнтів одночасно дасть рівно +1000, `LPUSH` ніколи не загубить елемент, `SET key value NX` гарантовано спрацює лише для одного клієнта. Питання атомарності виникає, лише коли треба виконати **кілька** команд як одну операцію.

### 10.2 Pipelining

Pipelining — це оптимізація **мережі**, а не атомарність. Клієнт відправляє пачку команд, не чекаючи відповідей, і потім читає всі відповіді разом.

```
Без pipelining (RTT = 1 мс):           З pipelining:
GET a ──▶                              GET a ─┐
      ◀── 1 мс                         GET b  ├──▶
GET b ──▶                              GET c ─┘
      ◀── 1 мс                               ◀── 1 мс (усі три відповіді)
GET c ──▶
      ◀── 1 мс       = 3 мс                         = ~1 мс
```

```python
pipe = r.pipeline(transaction=False)   # transaction=False — чистий pipelining, без MULTI
for user_id in user_ids:
    pipe.get(f"user:{user_id}")
results = pipe.execute()               # один round trip замість тисячі
```

- Команди з pipeline **не атомарні**: між ними можуть виконатися команди інших клієнтів.
- Pipelining економить не лише RTT, а й системні виклики `read()` / `write()`, тому прискорює навіть на localhost.
- Сервер накопичує відповіді в пам'яті, тож гігантський pipeline на мільйон команд роздуває output buffer. Розумний розмір пачки — сотні чи тисячі команд.
- Масове завантаження даних: `cat data.txt | redis-cli --pipe`, де у файлі — команди у форматі протоколу RESP.

### 10.3 MULTI / EXEC

Транзакція: команди ставляться в чергу і виконуються одним блоком, без втручання інших клієнтів.

```
SET str hello
MULTI
INCR counter
LPUSH str x          ← str — це рядок, буде WRONGTYPE
INCR counter
EXEC
1) (integer) 1
2) (error) WRONGTYPE Operation against a key holding the wrong kind of value
3) (integer) 2       ← попри помилку вище, команда ВИКОНАЛАСЬ
```

Головне, що треба знати про транзакції Redis:

- **Rollback немає.** Якщо команда впала під час виконання (`WRONGTYPE`, переповнення при `INCR`), решта команд транзакції **все одно виконуються**. Redis пояснює це так: такі помилки — баги в коді, а підтримка rollback ускладнила б і сповільнила сервер.
- **Помилки на етапі постановки в чергу** (невідома команда, неправильна кількість аргументів, OOM) відміняють усю транзакцію: `EXECABORT Transaction discarded because of previous errors.`
- **Всередині транзакції не можна прочитати значення і прийняти рішення.** Усі команди повертають `QUEUED`, результати приходять тільки після `EXEC`. Для логіки «прочитай — порахуй — запиши» потрібен `WATCH` або Lua.
- **У Cluster** усі ключі транзакції мають бути в одному слоті.

**WATCH — оптимістичне блокування (check-and-set):**

```
WATCH balance:42                 # стежити за ключем
GET balance:42                   # → 100 (читаємо і рахуємо в застосунку)
MULTI
SET balance:42 70
EXEC                             # nil, якщо хтось змінив balance:42 після WATCH → повторити спробу
```

Якщо будь-який ключ під `WATCH` змінився до `EXEC`, транзакція не виконується, і `EXEC` повертає nil. Застосунок повторює цикл. З Redis 6.0.9 транзакцію відміняє і **протухання** ключа під `WATCH`. При високій конкуренції за ключ WATCH-цикли починають постійно повторюватися, і тоді краще Lua.

### 10.4 Lua-скрипти

```bash
redis-cli EVAL "local v = redis.call('GET', KEYS[1]) or 0
      if tonumber(v) >= tonumber(ARGV[1]) then
        return redis.call('DECRBY', KEYS[1], ARGV[1])
      end
      return -1" 1 balance:42 30
```

- Скрипт виконується **атомарно**: поки він працює, жодна інша команда не виконується. Це і сила (будь-яка логіка «прочитай — порахуй — запиши» без гонок), і небезпека (довгий скрипт блокує всіх).
- Після `busy-reply-threshold` (за замовчуванням 5000 мс; до 7.0 називався `lua-time-limit`) скрипт **не зупиняється**. Redis лише починає відповідати іншим клієнтам `BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.`
- `SCRIPT KILL` зупинить скрипт, тільки якщо той ще нічого не записав. Якщо записав: `UNKILLABLE Sorry the script already executed write commands against the dataset...`. Тоді лишається тільки чекати або `SHUTDOWN NOSAVE` з утратою всього, що не встигло потрапити на диск.
- **Атомарність ≠ «все або нічого».** Якщо скрипт упав посередині (наприклад, на `WRONGTYPE`), записи, зроблені до помилки, **залишаються**. Rollback немає і тут.
- **Усі ключі передавай через `KEYS`**, а не збирай імена всередині скрипта. Від цього залежить маршрутизація в Cluster (і всі ключі мають бути в одному слоті) та перевірка ACL.
- **`EVALSHA` і `NOSCRIPT`.** `SCRIPT LOAD` повертає SHA1, далі скрипт викликають через `EVALSHA`, щоб не пересилати текст. Але кеш скриптів **не зберігається** між перезапусками і не переїжджає на репліку при failover: після рестарту чи failover прийде `NOSCRIPT No matching script`, і клієнт має повторити через `EVAL`. Більшість бібліотек роблять це самі. З 7.4 скрипти, що потрапили в кеш через `EVAL`, ще й можуть витіснятися з нього.
- **Не генеруй скрипти динамічно** з даними всередині тексту: кожен новий текст — новий скрипт у кеші і витік пам'яті. Дані передаються через `ARGV`.

### 10.5 Functions (7.0+)

Functions — «Lua-скрипти, зроблені правильно»: бібліотека функцій завантажується один раз, **зберігається в RDB/AOF і реплікується** на репліки, тож після рестарту чи failover нічого не зникає.

```bash
redis-cli FUNCTION LOAD "#!lua name=bank
redis.register_function('withdraw', function(keys, args)
  local v = tonumber(redis.call('GET', keys[1]) or 0)
  local amount = tonumber(args[1])
  if v < amount then return -1 end
  return redis.call('DECRBY', keys[1], amount)
end)"

redis-cli FCALL withdraw 1 balance:42 30
redis-cli FUNCTION LIST
```

Функції з прапорцем `no-writes` можна викликати через `FCALL_RO`, зокрема на репліках.

### 10.6 Що коли використовувати

| | Атомарність | Логіка з умовами | Зменшує RTT | Нюанси |
|---|---|---|---|---|
| Pipelining | Ні | Ні | Так | Просто пачка команд |
| `MULTI` / `EXEC` | Так (без rollback) | Ні (лише через `WATCH`-цикл) | Так, якщо в pipeline | Один слот у Cluster |
| `WATCH` + `MULTI` | Оптимістичне блокування | Так, на боці застосунку | Ні | Повтори при конкуренції |
| Lua (`EVAL`) | Так (без rollback) | Так | Так | Блокує сервер; `NOSCRIPT` після рестарту |
| Functions | Так (без rollback) | Так | Так | Зберігаються і реплікуються (7.0+) |

## 11. Патерни: кеш, локи, rate limiting, черги {#patterns}

### 11.1 Cache-aside — найпоширеніший патерн

```python
import json, random
import redis

r = redis.Redis(host="redis", port=6379, decode_responses=True)

def get_user(user_id: int) -> dict:
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)                   # cache hit
    user = db.fetch_user(user_id)                   # cache miss → у базу
    ttl = 3600 + random.randint(0, 300)             # TTL з jitter проти лавини
    r.set(key, json.dumps(user), ex=ttl)
    return user

def update_user(user_id: int, data: dict) -> None:
    db.update_user(user_id, data)                   # 1. спершу база
    r.delete(f"user:{user_id}")                     # 2. потім інвалідація кешу
```

**Чому при оновленні ключ видаляють, а не перезаписують новим значенням?** Два паралельні оновлення можуть записати в БД у порядку A → B, а в кеш у порядку B → A, і тоді в кеші назавжди (до TTL) залишиться A. Видалення ідемпотентне: наступне читання саме візьме актуальне значення з бази.

Але гонка лишається й так:

```
Читач A                          Письменник B                   кеш            БД
GET user:1 → miss
SELECT → v1 (ще старе)
                                 UPDATE → v2                                    v2
                                 DEL user:1                     (порожньо)
SET user:1 v1  ──────────────────────────────────────────▶      v1 — застаріле до кінця TTL
```

Тому:

- **TTL ставиться завжди**, навіть якщо інвалідація «ідеальна». Це страховка від усіх гонок і багів;
- для критичних даних — **відкладене повторне видалення** (видалити ключ ще раз через пару секунд після оновлення) або інвалідація через **CDC** (Debezium читає binlog / WAL бази й видаляє ключі);
- кеш завжди **eventually consistent** з базою, і бізнес має бути до цього готовий.

| Патерн | Як працює | Ризик |
|---|---|---|
| Cache-aside (lazy loading) | Застосунок читає кеш, при промаху йде в БД і кладе в кеш | Перший запит повільний; гонки інвалідації |
| Read-through | Те саме, але це робить шар кешу / бібліотека | Те саме, логіка схована |
| Write-through | Запис іде в кеш і в БД синхронно | Повільніший запис; у кеші дані, які, може, ніхто не читатиме |
| Write-behind (write-back) | Запис у кеш, у БД — асинхронно пачками | Втрата даних, якщо Redis упаде до скидання в БД |

### 11.2 Біди кешу: stampede, penetration, avalanche, hot key

| Проблема | Що відбувається | Як лікувати |
|---|---|---|
| **Cache stampede** (thundering herd, dogpile) | Популярний ключ протух, і тисячі запитів одночасно йдуть у БД перераховувати одне й те саме | Лок на перерахунок (`SET lock:key 1 NX EX 10`, решта чекають або віддають старе значення); stale-while-revalidate; ймовірнісне раннє оновлення; фонове оновлення гарячих ключів |
| **Cache penetration** | Запити на дані, яких немає ні в кеші, ні в БД (бот перебирає ID), щоразу пробивають до бази | Кешувати «порожню відповідь» з коротким TTL; Bloom filter перед БД; валідація вводу |
| **Cache avalanche** | Масово протухли ключі (всім поставили однаковий TTL під час деплою) або Redis упав, і все навантаження пішло в БД | Jitter у TTL; поступовий прогрів; HA для Redis; circuit breaker і rate limit на походи в БД; локальний L1-кеш |
| **Hot key** | Один ключ отримує непропорційно багато запитів і впирає один вузол | Локальний кеш у застосунку, client-side caching, читання з реплік, копії ключа (`key:{1..N}`) |
| **Big key** | Один ключ на десятки МБ чи мільйони елементів | Розбити на частини, читати порціями, `UNLINK` замість `DEL` (розділ 5.7) |

**Ймовірнісне раннє оновлення** (алгоритм XFetch) варто знати хоча б на рівні ідеї: кожен запит з невеликою ймовірністю перераховує значення **до** протухання, причому ймовірність росте, коли до кінця TTL лишається мало. Перерахунок розмазується в часі, і масового промаху немає взагалі.

### 11.3 Розподілений лок

**Захопити:**

```
SET lock:order:42 <унікальний-токен> NX PX 30000
```

- `NX` — лише якщо лока ще немає; `PX 30000` — лок сам зникне через 30 секунд, якщо власник помре.
- Одна команда, а не `SETNX` + `EXPIRE`. Якщо процес упаде між ними, лок залишиться назавжди.
- **Унікальний токен** (UUID) потрібен, щоб відпустити лише **свій** лок.

**Відпустити** — тільки якщо лок досі наш:

```lua
-- EVAL "<скрипт>" 1 lock:order:42 <токен>
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

У нових версіях це вміють без Lua: `DELEX lock:order:42 IFEQ <токен>` (Redis 8.4+) або `DELIFEQ lock:order:42 <токен>` (Valkey 9.0+). А `SET ... IFEQ` (Redis 8.4+, Valkey 8.1+) дозволяє атомарно продовжити чи перезаписати лок, лише якщо значення збігається.

Чому не можна просто `DEL lock:order:42`: процес 1 захопив лок, завис на 40 секунд (GC, swap), лок протух, його захопив процес 2, а процес 1 прокинувся і своїм `DEL` зніс **чужий** лок.

**Межі такого лока.** Навіть із токеном лок у Redis не гарантує взаємного виключення:

```
клієнт 1: SET lock tok1 NX PX 10000 → OK ── GC-пауза 15 с ──────────────▶ пише в сховище (вважає, що лок його)
                                       лок протух через 10 с
клієнт 2:                                    SET lock tok2 NX PX 10000 → OK → пише в сховище
                                          ⇒ два «власники» одночасно
```

Плюс асинхронна реплікація: лок записали в master, той упав, не встигнувши передати його на репліку, новий master лока не має, і його захоплює другий клієнт.

- **Redlock** — алгоритм автора Redis: N (зазвичай 5) незалежних master'ів, лок вважається захопленим, якщо вдалося взяти його на більшості за час, менший за TTL.
- **Критика Мартіна Клеппманна** («How to do distributed locking», 2016): Redlock спирається на припущення про час (обмежені затримки мережі, паузи процесів, дрейф годинників). Для **коректності** потрібні **fencing tokens**: сервіс локів видає монотонно зростаючий номер, а сховище відкидає записи зі старішим номером. Redis такого механізму не дає.

Практичний висновок, який варто озвучити на співбесіді: **лок у Redis підходить для ефективності** (не робити ту саму роботу двічі, не запускати cron на двох вузлах), але **не для коректності**, де подвійне виконання — це гроші чи пошкоджені дані. Там потрібні etcd / ZooKeeper / Consul з fencing, або обмеження на рівні самої бази (унікальні індекси, `SELECT ... FOR UPDATE`, версії рядків).

### 11.4 Rate limiting

**Fixed window** — лічильник на вікно часу:

```
MULTI
INCR rl:user42:1792195260        # початок хвилини (Unix-час) в імені ключа
EXPIRE rl:user42:1792195260 60 NX
EXEC
```

`EXPIRE ... NX` (7.0+) ставить TTL лише один раз, а `MULTI` гарантує, що ключ не залишиться без TTL. У Redis 8.8+ є окрема команда:

```
INCREX rl:user42 BYINT 1 UBOUND 100 EX 60 ENX
1) (integer) 37     # нове значення
2) (integer) 1      # 1 — інкремент застосовано; 0 — ліміт 100 вже досягнуто, значення не змінилось
```

`ENX` ставить TTL лише тоді, коли його ще немає, тобто вікно починається з першого запиту.

Мінус fixed window: на межі вікон можна пропустити подвійний ліміт (100 запитів о 12:00:59 і ще 100 о 12:01:00).

**Sliding window log** — Sorted Set з таймстемпами запитів:

```lua
-- KEYS[1] = ключ лімітера, ARGV[1] = вікно (мс), ARGV[2] = ліміт, ARGV[3] = унікальний ID запиту
local t = redis.call('TIME')                                      -- час сервера, а не клієнта
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local window, limit = tonumber(ARGV[1]), tonumber(ARGV[2])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)          -- викинути старі запити
if redis.call('ZCARD', KEYS[1]) >= limit then
  return 0                                                        -- ліміт вичерпано
end
redis.call('ZADD', KEYS[1], now, ARGV[3])
redis.call('PEXPIRE', KEYS[1], window)
return 1
```

Точний, але кожен запит займає місце в пам'яті. Компромісні варіанти — sliding window counter (два сусідні fixed window з вагами) і token bucket / GCRA у Lua.

### 11.5 Черги і події

| | Pub/Sub | List | Streams | Для порівняння: Kafka |
|---|---|---|---|---|
| Зберігає повідомлення | Ні | Так, поки не забрали | Так, поки не обрізали | Так, на диску за retention |
| Гарантія доставки | At-most-once, лише онлайн-підписникам | Один отримувач; губиться, якщо воркер упав (крім `BLMOVE`-патерну) | Consumer groups, `XACK`, повторна доставка (at-least-once) | Consumer groups, offsets |
| Кілька незалежних читачів | Так, усі отримують копію | Ні, хто перший забрав | Так, кілька груп | Так |
| Перечитати історію | Ні | Ні | Так (`XRANGE`) | Так |
| Масштабування | Sharded pub/sub (7.0+) | Один ключ — один шард | Один стрім — один шард | Партиції |
| Обсяг | — | RAM | RAM | Диск, терабайти |

- **Pub/Sub** — для сповіщень, де втрата не критична (інвалідація локальних кешів, «онлайн-статуси»). Повільного підписника Redis відключить за `client-output-buffer-limit pubsub 32mb 8mb 60`.
- **List** — проста черга задач. Надійний варіант: `BLMOVE queue processing RIGHT LEFT 0` → обробити → `LREM processing 1 <задача>`. Окремий процес повертає в чергу задачі, що зависли в `processing`.
- **Streams** — повноцінна черга з підтвердженнями (розділ 3.7). Не забувай про `MAXLEN` і моніторинг `XPENDING`.
- **Keyspace notifications** (`notify-keyspace-events`, за замовчуванням вимкнені) працюють поверх pub/sub і мають ті самі слабкі гарантії. До того ж у Cluster кожен вузол шле події лише про свої ключі.

### 11.6 Client-side caching (6.0+)

Навіть 0.2 мс до Redis — це багато для ключа, який читають мільйон разів за секунду. Client-side caching дозволяє тримати копію в пам'яті застосунку, а Redis сам повідомляє, коли вона застаріла:

```
CLIENT TRACKING ON      # (RESP3) сервер запам'ятовує, які ключі читав цей клієнт
GET config:features     # клієнт кладе значення в локальний кеш
...                     # хтось інший виконав SET config:features ...
                        # сервер шле push-повідомлення: invalidate [config:features]
```

- **Default mode** — сервер пам'ятає ключі кожного клієнта (таблиця обмежена `tracking-table-max-keys`, за замовчуванням 1 мільйон).
- **Broadcasting mode** (`BCAST PREFIX config:`) — сервер нічого не пам'ятає, а розсилає інвалідації за префіксами всім, хто підписався.
- У RESP2 інвалідації йдуть через окреме з'єднання, підписане на `__redis__:invalidate` (`REDIRECT`).

Частина клієнтів уміє це «з коробки» (Lettuce, Jedis, redis-py, rueidis для Go). Це найкращий засіб від hot keys, коли значення змінюється рідко.

## 12. Безпека {#security}

### 12.1 Чому відкритий Redis = зламаний сервер

Модель безпеки Redis проста: він розрахований на роботу **в довіреній мережі**. Відкритий в інтернет Redis без пароля знаходять за години, а ботнети на кшталт P2PInfect і HeadCrab сканують порт 6379 постійно. Класичні вектори атак:

1. **Запис файлів через `CONFIG SET`.** Атакувальник виконує `CONFIG SET dir /root/.ssh`, `CONFIG SET dbfilename authorized_keys`, кладе свій SSH-ключ у значення ключа і робить `SAVE`. RDB-файл містить ключ серед «сміття», а sshd такі рядки спокійно приймає. Так само пишуть cron-задачі у `/var/spool/cron` чи web shell у каталог сайту. З Redis 7.0 такі параметри захищені: `enable-protected-configs no`, і `CONFIG SET dir` повертає `ERR CONFIG SET failed (possibly related to argument 'dir') - can't set protected config`.
2. **Rogue master + модуль.** `REPLICAOF <сервер атакувальника>` → «master» віддає замість RDB шкідливий `.so` → `MODULE LOAD` → виконання коду. З 7.0 команда `MODULE` вимкнена за замовчуванням (`enable-module-command no`).
3. **Вразливості в Lua.** CVE-2022-0543 (втеча з Lua-пісочниці в пакетах Debian/Ubuntu) масово використовували ботнети. **CVE-2025-49844 «RediShell»** — use-after-free у збирачі сміття Lua, який дає віддалене виконання коду. Redis і Wiz оцінили його в CVSS 10.0, NVD — у 9.9 (бо потрібне право виконувати `EVAL`). Баг жив у коді близько 13 років. Виправлено 3 жовтня 2025 року в Redis 6.2.20, 7.2.11, 7.4.6, 8.0.4, 8.2.2 і у Valkey 7.2.11, 8.0.6, 8.1.4. За даними Wiz, в інтернет дивилися близько 330 тисяч інстансів Redis, з них близько 60 тисяч без автентифікації.
4. **І далі по списку.** Лише у 2026 році security-релізи Redis виходили в лютому, травні, липні, серпні та вересні: RCE через шкідливий payload `RESTORE`, use-after-free при розблокуванні клієнтів, обхід ACL у `SORT` / `GEORADIUS` / `XREAD`, обхід TLS-автентифікації за сертифікатом. Висновок: оновлюватися регулярно, а команди на кшталт `RESTORE`, `EVAL`, `FUNCTION`, `MODULE` давати лише тим, кому вони справді потрібні.

> **Пастка з Docker.** Офіційний образ `redis` збирається з `protected-mode no` за замовчуванням: у контейнері з'єднання приходять не з loopback, і «захищений режим» лише заважав би. Тому `docker run -d -p 6379:6379 redis` на сервері з публічним IP — це **відкритий в інтернет Redis без пароля**. А Docker пише свої правила iptables в обхід `ufw`, тож фаєрвол на хості може не врятувати.

### 12.2 Шари захисту

**Мережа** — найважливіший шар:

- `bind` лише на приватний інтерфейс (дефолт у `redis.conf` — `bind 127.0.0.1 -::1`);
- security groups / фаєрвол: доступ до 6379 тільки з підмереж застосунків; порт cluster bus (6379 + 10000) — лише між вузлами кластера;
- `protected-mode yes` (дефолт поза Docker): без пароля і з `bind` на всі інтерфейси Redis прийматиме з'єднання лише з loopback.

**Автентифікація: від `requirepass` до ACL.** `requirepass` задає пароль користувачу `default`, і всі клієнти ходять під ним з повними правами. З Redis 6 є **ACL**: окремі користувачі з окремими паролями, обмеженням на ключі, канали і команди.

```
# /etc/redis/users.acl   (у redis.conf: aclfile /etc/redis/users.acl)
user default off
user app       on #<sha256-хеш-пароля> ~app:* &app:* +@all -@dangerous -@admin -@scripting
user readonly  on >ro-password ~* +@read +@connection
user admin     on >long-admin-password ~* &* +@all
```

- `~app:*` — доступ лише до ключів з префіксом `app:`; `%R~` / `%W~` (7.0+) — окремо на читання і запис;
- `&app:*` — канали pub/sub (з 7.0 нові користувачі за замовчуванням не мають доступу до жодного каналу);
- `+@read`, `-@dangerous`, `-@admin` — категорії команд (`ACL CAT` покаже всі, `ACL CAT dangerous` — що саме входить у «небезпечні»: `KEYS`, `FLUSHALL`, `CONFIG`, `MONITOR`, `DEBUG`, `SHUTDOWN`, `REPLICAOF`, `RESTORE`, `MIGRATE` та інші);
- `-@scripting` прибирає `EVAL` / `FCALL`: зайвим не буде, з огляду на RediShell;
- `#<sha256>` замість `>пароль` — у файлі лежить хеш, а не пароль; згенерувати надійний пароль допоможе `ACL GENPASS`.

```bash
redis-cli ACL DRYRUN app FLUSHALL        # перевірити права, нічого не виконуючи
# User app has no permissions to run the 'flushall' command
redis-cli ACL LOG 10                     # хто і що намагався зробити без прав / з неправильним паролем
redis-cli ACL WHOAMI
```

У Valkey 9.1 з'явилися права на рівні **номера бази** (`ACL SETUSER ... db=0,1`), у Valkey 9.2 очікуються ролі.

**TLS** (з 6.0): `tls-port 6380`, `port 0` (вимкнути відкритий порт), `tls-cert-file`, `tls-key-file`, `tls-ca-cert-file`, `tls-auth-clients yes`, а також `tls-replication yes` і `tls-cluster yes`, щоб шифрувати реплікацію і cluster bus. TLS коштує CPU, тому на навантажених інстансах вмикають `io-threads`: у Redis 8 і Valkey 8.1+ TLS-обробку виконують I/O-потоки. У Redis 8.6+ є автентифікація клієнтів за сертифікатом, у Valkey 9.1 — автоматичне перечитування сертифікатів.

**Решта:**

- Redis працює від окремого непривілейованого користувача, а не від root (тоді навіть успішний запис файлу не дасть root-доступу); systemd-hardening (`NoNewPrivileges`, `ProtectSystem`) не завадить.
- `enable-protected-configs`, `enable-debug-command`, `enable-module-command` лишити в `no`.
- `rename-command FLUSHALL ""` — старий спосіб сховати команду. Він ламає репліки й AOF, якщо конфіги розходяться, тож краще ACL.
- Sentinel теж треба закрити паролем (`requirepass` для самого Sentinel і `sentinel auth-pass` / `auth-user` для доступу до Redis).
- Регулярні оновлення: див. пункт 4 вище.

## 13. Продуктивність і latency {#performance}

### 13.1 Звідки береться latency

| Джерело | Як виглядає | Як перевірити |
|---|---|---|
| Мережа і RTT | Стабільно високий час навіть для `PING` | `redis-cli --latency` з хоста застосунку і з самого сервера |
| Повільні команди | Періодичні сплески для всіх клієнтів | `SLOWLOG GET`, `INFO commandstats` |
| Big keys | Сплески при читанні чи видаленні конкретних ключів | `--bigkeys`, `--memkeys`, `MEMORY USAGE` |
| `fork` (BGSAVE, AOF rewrite, full sync) | Сплески за розкладом save-точок | `latest_fork_usec`, `LATENCY LATEST` (подія `fork`) |
| THP | Сплески і зростання пам'яті під час fork | `cat /sys/kernel/mm/transparent_hugepage/enabled` |
| Swap | Усе повільно, `mem_fragmentation_ratio` < 1 | `vmstat 1` (стовпці si/so), `/proc/<pid>/smaps` |
| Повільний диск і AOF | `Asynchronous AOF fsync is taking too long` у лозі | `iostat -x 1`, `LATENCY LATEST` (події `aof-*`) |
| Масове протухання ключів | Сплески CPU, ростуть `expired_keys` | `INFO stats`, `expire_cycle_cpu_milliseconds` |
| Масове витіснення | Ростуть `evicted_keys` | `INFO stats` |
| Шквал нових з'єднань | CPU росте, `total_connections_received` летить угору | Пули з'єднань у клієнтів; з TLS це особливо дорого |
| Сусіди по гіпервізору | Latency без жодної причини всередині Redis | `redis-cli --intrinsic-latency 100`, steal time у `top` |

### 13.2 Інструменти

```bash
redis-cli --latency                       # мінімальна, максимальна і середня latency PING, безперервно
redis-cli --latency-history -i 15         # те саме, вікнами по 15 секунд
redis-cli --intrinsic-latency 100         # запускати НА СЕРВЕРІ: latency, яку дає сама ОС / гіпервізор
redis-cli --stat                          # ops/s, клієнти, пам'ять — щосекунди

redis-cli CONFIG SET latency-monitor-threshold 100   # записувати події довші за 100 мс
redis-cli LATENCY LATEST                  # останні сплески за типами подій (command, fork, aof-fsync-always, expire-cycle...)
redis-cli LATENCY DOCTOR                  # людською мовою: що не так і що робити

redis-cli SLOWLOG GET 10                  # 10 останніх повільних команд
redis-cli SLOWLOG LEN
redis-cli INFO commandstats               # calls, usec, usec_per_call, rejected_calls, failed_calls для кожної команди
redis-cli INFO latencystats               # 7.0+: p50 / p99 / p99.9 для кожної команди
```

Запис `SLOWLOG GET` виглядає так:

```
1) 1) (integer) 2            # ID запису
   2) (integer) 1792234806   # Unix-час
   3) (integer) 10           # тривалість у мікросекундах
   4) 1) "SET"               # команда з аргументами
      2) "foo"
      3) "bar"
   5) "127.0.0.1:42976"      # клієнт
   6) ""                     # ім'я клієнта (CLIENT SETNAME)
```

> **Пастка:** `SLOWLOG` вимірює лише **час виконання команди**. Час очікування в черзі (поки виконувалась чиясь повільна команда), мережу, читання запиту і fork він не бачить. «Slowlog порожній, а клієнти бачать 300 мс» — нормальна ситуація: шукай причину в таблиці вище. Поріг `slowlog-log-slower-than` за замовчуванням 10 000 мкс (10 мс), а для Redis це вже вічність, тому його часто знижують до 1–5 мс. Valkey 8.1 розширив slowlog до `COMMANDLOG`, який окремо логує ще й великі запити та великі відповіді.

`MONITOR` показує всі команди в реальному часі, але сильно знижує пропускну здатність. На проді — кілька секунд і з `head`, не більше.

### 13.3 I/O-потоки

```
# дефолт — 1, тобто I/O-потоки вимкнено
io-threads 4
```

- I/O-потоки допомагають, коли вузьке місце — **мережа**: багато з'єднань, великі відповіді, TLS. Повільні команди вони не прискорять, бо виконання все одно в main thread.
- У Redis 8.0 потоки переписали: кожен має власний event loop, читає, парсить і пише відповіді (разом із TLS). Параметр `io-threads-do-reads` більше нічого не робить. Redis заявляв до 2× пропускної здатності з `io-threads 8`.
- Valkey 8.0 зробив асинхронні I/O-потоки й заявив до 1.2 млн RPS на інстанс, а Valkey 9.1 — 2.1 млн RPS на одному вузлі (512-байтові значення, 9 I/O-потоків, pipeline). Важливо: це все **вимкнено за замовчуванням**, і такі цифри отримують лише з налаштованими `io-threads`.
- Практичне правило: вмикати, якщо ядер щонайменше 4 і CPU main thread упирається в 100%. Кількість потоків — менша за кількість ядер, щоб лишилося місце для main thread, fork і ОС.

### 13.4 Налаштування ОС

```
# /etc/sysctl.d/90-redis.conf
# інакше fork для BGSAVE може не вдатися
vm.overcommit_memory = 1
# не менше за tcp-backlog (511), інакше Redis попередить при старті
net.core.somaxconn = 4096
# мінімізувати swap (див. нижче)
vm.swappiness = 1
```

```bash
# THP: не always, а madvise або never (постійно — через systemd unit чи параметр ядра transparent_hugepage=...)
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
```

- **Ліміт файлових дескрипторів** має бути не менший за `maxclients` + 32 (`LimitNOFILE` у systemd). Інакше Redis при старті сам зменшить `maxclients` і напише про це в лог.
- **Swap.** Документація Redis радить мати swap, щоб при перевитраті пам'яті Redis «тормозив», а не був убитий OOM killer'ом: тоді є шанс помітити й зреагувати. Багато SRE для latency-критичних інсталяцій swap вимикають і покладаються на `maxmemory` та алерти. Обидва підходи робочі, головне — свідомий вибір і `maxmemory`.
- **Кілька інстансів на хост**, щоб використати ядра (кожен на своєму порту, бажано прив'язаний до свого ядра через `taskset` або cgroups). Кластер на одному хості — нормальний спосіб завантажити багатоядерну машину.

### 13.5 Клієнтська сторона

Більшість «Redis повільний» насправді виявляються проблемами клієнта:

- **Пул з'єднань.** Нове з'єднання на кожен запит — це TCP handshake (і TLS), а для Redis ще й зайва робота. Сотні застосунків × поди × пули = десятки тисяч з'єднань, тому стеж за `connected_clients` і `maxclients` (дефолт 10 000).
- **Таймаути і ретраї з backoff та jitter.** Агресивні ретраї без затримки перетворюють коротку проблему на retry storm, і Redis так і не встигає піднятися.
- **Pipelining** для пачок і **`MGET` / `MSET`** замість циклів з `GET`.
- **Не тягнути великі значення** без потреби: `HMGET` потрібних полів замість `HGETALL`, стискання.
- **`CLIENT SETNAME` / `CLIENT SETINFO`** (ім'я застосунку і бібліотеки, 7.2+), щоб у `CLIENT LIST` одразу було видно, хто є хто.

### 13.6 Бенчмарки

```bash
redis-benchmark -h 10.0.0.1 -t get,set -n 1000000 -c 50 -d 256 -q        # без pipelining
redis-benchmark -h 10.0.0.1 -t get,set -n 1000000 -c 50 -d 256 -P 16 -q  # pipeline по 16 команд
redis-benchmark -h 10.0.0.1 -t get -n 1000000 -c 50 --threads 4 -q       # кілька потоків клієнта
```

`redis-benchmark` міряє синтетику: однаковий розмір значень, рівномірні ключі. Для реалістичних тестів (розподіл ключів, мікс читання і запису, кластер) краще `memtier_benchmark`. І завжди запускай бенчмарк з окремої машини: інакше він конкуруватиме з Redis за CPU.

### 14.2 Prometheus: redis_exporter і алерти

Стандарт — [redis_exporter](https://github.com/oliver006/redis_exporter) (він працює і з Valkey). Мінімальний набір правил:

```yaml
groups:
  - name: redis
    rules:
      - alert: RedisDown
        expr: redis_up == 0
        for: 1m
        labels: {severity: critical}

      - alert: RedisMemoryNearMaxmemory
        expr: redis_memory_used_bytes / redis_memory_max_bytes > 0.9 and redis_memory_max_bytes > 0
        for: 5m
        labels: {severity: warning}

      - alert: RedisNoMaxmemory          # ліміту немає — рано чи пізно прийде OOM killer
        expr: redis_memory_max_bytes == 0
        for: 1h
        labels: {severity: warning}

      - alert: RedisEvictingKeys
        expr: increase(redis_evicted_keys_total[5m]) > 0
        labels: {severity: warning}

      - alert: RedisRejectedConnections
        expr: increase(redis_rejected_connections_total[5m]) > 0
        labels: {severity: critical}

      - alert: RedisTooManyConnections
        expr: redis_connected_clients / redis_max_clients > 0.8
        for: 5m
        labels: {severity: warning}

      - alert: RedisReplicaLinkDown
        expr: redis_master_link_up == 0
        for: 1m
        labels: {severity: critical}

      - alert: RedisFrequentFullResync
        expr: increase(redis_replica_resyncs_full[1h]) > 2
        labels: {severity: warning}

      - alert: RedisRdbSaveFailing
        expr: redis_rdb_last_bgsave_status == 0
        for: 5m
        labels: {severity: critical}

      - alert: RedisMissingBackup
        expr: time() - redis_rdb_last_save_timestamp_seconds > 24 * 3600
        labels: {severity: warning}

      - alert: RedisHighFragmentation
        expr: redis_mem_fragmentation_ratio > 1.5 and redis_memory_used_bytes > 1e9
        for: 30m
        labels: {severity: info}
```

Корисні графіки в Grafana: ops/s за командами (`rate(redis_commands_total[1m])`), середній час команди (`rate(redis_commands_duration_seconds_total[1m]) / rate(redis_commands_total[1m])`), hit ratio, пам'ять відносно `maxmemory`, кількість ключів у кожній базі (`redis_db_keys`), лаг реплікації.

### 14.3 Що шукати в логах

| Повідомлення | Що означає |
|---|---|
| `WARNING Memory overcommit must be enabled!` | Не виставлено `vm.overcommit_memory = 1` (розділ 6.2) |
| `You have Transparent Huge Pages (THP) support enabled in your kernel` | THP у режимі `always` |
| `WARNING: The TCP backlog setting of 511 cannot be enforced` | `net.core.somaxconn` менший за `tcp-backlog` |
| `Can't save in background: fork: Cannot allocate memory` | Не вдався fork для BGSAVE (overcommit, нестача RAM) |
| `Asynchronous AOF fsync is taking too long (disk is busy?)` | Диск не встигає за AOF |
| `... scheduled to be closed ASAP for overcoming of output buffer limits` | Клієнта або репліку відключено через переповнений output buffer |
| `Partial resynchronization not possible` + `Full resync requested` | Репліка пішла на full sync |
| `Connection with master lost` / `MASTER <-> REPLICA sync started` | Проблеми з реплікацією |
| `+sdown` / `+odown` / `+switch-master` (лог Sentinel) | Sentinel бачить падіння / почав failover / змінив master |

**Що сталося з Bitnami.** З 28 серпня 2025 року Broadcom звів безкоштовний каталог `docker.io/bitnami` до образів лише з тегом `latest` («для розробки»), а версіоновані теги до 29 вересня 2025 переїхали в заморожений `docker.io/bitnamilegacy`, який більше не оновлюється. Для продакшену Broadcom пропонує платні Bitnami Secure Images. Наслідки, з якими зустрічаються досі: `ImagePullBackOff` на старих тегах, неконтрольовані оновлення через `latest`, кластери на образах, які більше ніколи не отримають security-патчів. Варіанти: перейти на офіційні образи `redis` / `valkey` з власним чартом, на офіційний Helm-чарт Valkey або на оператор.

### 15.2 Граблі Redis у Kubernetes

- **Memory limit і `maxmemory`.** Ліміт контейнера рахує RSS разом із COW під час fork. Якщо `maxmemory` близький до ліміту, под отримає `OOMKilled` під час `BGSAVE` чи full sync. З persistence ставлять `maxmemory` десь 50–70% від ліміту. Requests для пам'яті роблять рівними limits, щоб под не витісняли першим.
- **`vm.overcommit_memory` і THP налаштовуються лише на вузлах.** `vm.overcommit_memory` не належить до namespaced sysctls, тож через `securityContext.sysctls` пода його не задати. Це робиться в конфігурації вузлів (DaemonSet, machine config, user data). `net.core.somaxconn` namespaced, але вважається unsafe і вимагає дозволу в kubelet (`--allowed-unsafe-sysctls`).
- **Автоперезапуск master без persistence** (розділ 6.7). У Kubernetes перезапуск — поведінка за замовчуванням. Або persistence на PVC, або оператор / Sentinel, який не дасть порожньому master'у розлити порожнечу на репліки.
- **Мережеві ідентичності.** IP пода змінюється після перезапуску. Для Sentinel і Cluster потрібні StatefulSet + headless Service і анонс DNS-імен (`replica-announce-ip`, `sentinel announce-hostnames yes`, `cluster-announce-hostname`), а `nodes.conf` кластера має лежати на PVC.
- **Розміщення.** Pod anti-affinity або `topologySpreadConstraints` за вузлами і зонами: master і його репліка на одному вузлі — це не HA. `PodDisruptionBudget`, щоб drain не забрав одночасно master і репліку.
- **Probes.** Під час завантаження великого датасету `PING` повертає `-LOADING`. Агресивна liveness probe вбиває под, який просто довго вантажиться, і виходить нескінченний цикл перезапусків. Для старту — `startupProbe` з великим запасом часу. Readiness — перевіряти, що відповідь саме `PONG` (а для реплік ще й `master_link_status:up`), а не лише код виходу `redis-cli`.
- **Graceful shutdown.** `terminationGracePeriodSeconds` має вистачати на фінальний снапшот. Перед видаленням пода з master корисно в `preStop` перемкнути роль на репліку (`FAILOVER` або `SENTINEL FAILOVER`).

### 15.3 Керовані сервіси

| Сервіс | Двигуни і версії (жовтень 2026) | Що варто знати |
|---|---|---|
| **AWS ElastiCache** | Valkey до 9.1, Redis OSS до 7.1, Memcached | Valkey дешевший: −20% для вузлів, −33% для Serverless. Redis OSS 4 і 5 з лютого 2026 року на платній Extended Support. З червня 2026 є опційна durability (Multi-AZ transaction log) для Valkey 9.0+ |
| **AWS MemoryDB** | Valkey і Redis OSS | Durable: запис підтверджується після потрапляння в Multi-AZ transaction log. Valkey на 30% дешевший |
| **Google Memorystore** | for Valkey (7.2, 8.0, 9.0, 9.1), for Redis і for Redis Cluster (до 7.2) | Memorystore for Memcached оголошено застарілим, вимкнення — у 2029 році |
| **Azure** | Azure Managed Redis (на стеку Redis Enterprise) | Azure Cache for Redis йде на пенсію: Enterprise-тири — 31.03.2027, Basic/Standard/Premium — 30.09.2028; створювати нові кеші вже обмежено з квітня 2026 |

Спільне для керованих сервісів:

- **Частина команд заблокована** (`CONFIG`, `DEBUG`, `MODULE`, `REPLICAOF`...). Параметри змінюються через parameter groups / API.
- **Failover через DNS.** Endpoint лишається тим самим, а IP за ним змінюється. Клієнт, який закешував DNS назавжди (класика JVM), після failover довго писатиме в старий master і отримуватиме `READONLY`.
- **Дефолтні параметри відрізняються від upstream.** Наприклад, у дефолтній parameter group ElastiCache стоїть `maxmemory-policy volatile-lru`, тому ключі без TTL не витісняються, і без TTL кеш упреться в OOM-помилки. Частина пам'яті вузла резервується під службові потреби (`reserved-memory-percent`, за замовчуванням 25%).
- **Вікна обслуговування** з failover'ом — регулярна подія, а не аварія. Клієнти мають уміти перепідключатися.

## 16. Redis vs Valkey vs Memcached та інші {#compare}

### 16.1 Redis vs Valkey

| | Redis | Valkey |
|---|---|---|
| Хто розвиває | Redis Ltd. (повернувся автор, antirez) | Linux Foundation; AWS, Google, Oracle, Ericsson, Snap та інші |
| Ліцензія | RSALv2 / SSPLv1 / **AGPLv3** (з 8.0); ≤ 7.2 — BSD | **BSD-3** |
| Остання стабільна (жовтень 2026) | 8.10.2 | 9.1.2 (9.2 у RC) |
| Що в комплекті | Query Engine, JSON, TimeSeries, Bloom/Cuckoo/CMS/Top-K/t-digest у бінарних дистрибутивах; Vector Sets і Array в ядрі | Ядро + окремі BSD-модулі `valkey-json`, `valkey-bloom`, `valkey-search`, `valkey-ldap` (образ `valkey/valkey-bundle`) |
| Унікальне | `allkeys-lrm` / `volatile-lrm`, Array, compact hashes, `BACKUP`, `HOTKEYS` та `INCREX` (у Valkey їх анонсовано в 9.2) | Кілька баз у Cluster, `CLUSTERSCAN`, ACL на рівні бази, `COMMANDLOG`, `DELIFEQ` |
| Дефолти, що відрізняються | `lazyfree-*` = no, `repl-backlog-size` 1 МБ | `lazyfree-*` = yes, `repl-backlog-size` 10 МБ |
| Формат RDB | 12 (7.4–8.4), 13 (8.6), 14 (8.8), 15 (8.10) | 11 (до 8.1), 80 з новою сигнатурою `VALKEY080` (9.x) |
| `INFO server` | `redis_version:8.10.2` | `redis_version:7.2.4` (завжди!), `valkey_version:9.1.2` |
| Хмари | Redis Cloud, Azure Managed Redis | ElastiCache, MemoryDB, Memorystore for Valkey |

Що з цього треба знати практично:

- **Valkey — drop-in заміна лише для Redis ≤ 7.2.** Офіційна позиція Valkey: дані Redis 7.4+ несумісні. RDB Redis 7.4+ Valkey за замовчуванням не завантажить (`Can't handle RDB format version 12`), реплікація з Redis 7.4+ у Valkey не працює, `DUMP` / `RESTORE` і `MIGRATE` між ними теж. У зворотний бік RDB Valkey 9 не завантажить жоден Redis. Мігрувати між сучасними версіями — логічно: RedisShake, RIOT, подвійний запис у застосунку.
- **Valkey завжди віддає `redis_version:7.2.4`**, щоб не ламати клієнтів. Інструменти, які вмикають фічі за `redis_version`, на Valkey 9 вважатимуть, що це Redis 7.2.
- **API зближується:** обидва мають TTL на полях хешу, `HGETDEL`, `MSETEX`, `SET ... IFEQ`, атомарну міграцію слотів і `CLUSTER SLOT-STATS`. А от `DELEX` (Redis) і `DELIFEQ` (Valkey) — різні команди для одного й того самого.
- **Ліцензія AGPLv3** не заважає просто користуватися Redis 8 у своїй інфраструктурі. Вимога відкрити код виникає, якщо ти змінюєш Redis і надаєш його як мережевий сервіс. Але в багатьох компаніях AGPL заборонений політикою, і це один із головних аргументів на користь Valkey.

### 16.2 Redis vs Memcached

| | Redis / Valkey | Memcached |
|---|---|---|
| Дані | Структури: рядки, хеші, списки, множини, ZSET, стріми... | Лише ключ → blob |
| Розмір значення | До 512 МБ | За замовчуванням до 1 МБ (`-I`) |
| Потоки | Виконання команд в одному потоці (+ I/O-потоки) | Справді багатопотоковий |
| Persistence | RDB, AOF | Немає (є extstore на flash, але це не persistence) |
| Реплікація і HA | Є (Sentinel, Cluster) | Немає в самому Memcached |
| Шардинг | Redis Cluster або на клієнті | На клієнті (consistent hashing) |
| Атомарні операції, скрипти, pub/sub | Так | Лише прості операції: `incr` / `decr`, `cas`, `append` |
| Пам'ять | Різні кодування, jemalloc, фрагментація | Slab allocator з фіксованими класами розмірів |
| Коли брати | Майже завжди | Дуже простий великий кеш рядків, де важливий багатопотоковий throughput на вузол |

### 16.3 Інші RESP-сумісні сховища

| Проєкт | Ліцензія | Що це | Статус |
|---|---|---|---|
| Dragonfly | BSL 1.1 | Багатопотоковий shared-nothing in-memory, сумісний з Redis API | Активний; BSL забороняє конкуруючі managed-сервіси |
| Microsoft Garnet | MIT | Кеш-сервер на C# / .NET з протоколом RESP | Активний |
| Apache Kvrocks | Apache 2.0 | Дані на диску (RocksDB), протокол Redis | Активний; для датасетів, які не влазять у RAM |
| KeyDB | BSD-3 | Багатопотоковий форк Redis від Snap | Фактично не розвивається з 2023 року |
| Redict | LGPL-3.0 | Форк Redis 7.2.4 | Затих після 2025 року |

### 16.4 Що обрати

- **Новий проєкт, своя інфраструктура або AWS / GCP** — Valkey: BSD-ліцензія, підтримка хмар, сумісність з усім, що вміло Redis 7.2.
- **Потрібні Query Engine, JSON-пошук, TimeSeries, Vector Sets** «з коробки» або підтримка Redis Ltd. — Redis 8.x (Redis Cloud, Redis Software, Azure Managed Redis).
- **Існуючий Redis ≤ 7.2** — Valkey оновлюється «на місці». **Redis 7.4+** — уже окрема гілка, і переїзд в будь-який бік стане проєктом міграції даних.
- Що б не обрав, **зафіксуй версію і двигун у документації** і перевіряй, які фічі використовує код: команди, яких немає в іншому двигуні, роблять міграцію дорожчою.

## 18. Траблшутінг: типові помилки й інциденти {#troubleshooting}

### 18.1 `OOM command not allowed when used memory > 'maxmemory'.`

Пам'ять дійшла до `maxmemory`, а витіснити нічого не можна: політика `noeviction` або `volatile-*` без ключів з TTL.

```bash
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|maxmemory_policy'
redis-cli INFO keyspace                     # expires=0 при volatile-* = витісняти нічого
redis-cli --memkeys                         # хто з'їв пам'ять
redis-cli CLIENT LIST | awk '{for(i=1;i<=NF;i++) if($i ~ /^omem=/) print $i, $0}' | sort -t= -k2 -rn | head   # великі output buffers
```

Що робити: для кешу — `allkeys-lru` / `allkeys-lfu`; знайти ключі без TTL і виправити код; знайти big keys і клієнтів з величезними буферами; збільшити `maxmemory` чи масштабуватися.

### 18.2 `MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk...`

`BGSAVE` впав, а `stop-writes-on-bgsave-error yes` заблокував запис. Причина — у лозі Redis:

```bash
grep -E 'Background saving error|Failed opening|Can.t save in background|fork' /var/log/redis/redis-server.log | tail
redis-cli INFO persistence | grep -E 'rdb_last_bgsave_status|rdb_last_bgsave_time_sec'
df -h /var/lib/redis; ls -ld /var/lib/redis  # місце і права
```

Типові причини: закінчилося місце на диску, немає прав на каталог (`Failed opening the temp RDB file ... Permission denied`), не вдався fork (`vm.overcommit_memory`, нестача RAM). Виправ причину і перевір `BGSAVE`. `CONFIG SET stop-writes-on-bgsave-error no` — лише як тимчасова милиця, бо далі Redis працюватиме без жодного снапшота.

### 18.3 `LOADING Redis is loading the dataset in memory`

Redis після старту (або репліка під час full sync) завантажує RDB / AOF. Великий датасет вантажиться хвилинами. Прогрес видно в `INFO persistence` (`loading:1`, `loading_loaded_perc`, `loading_eta_seconds`). Перезапуски master'а робити через failover на репліку, а не «по живому». У Kubernetes — `startupProbe` з запасом (розділ 15.2).

### 18.4 `BUSY Redis is busy running a script...`

Lua-скрипт чи функція працює довше за `busy-reply-threshold`. `SCRIPT KILL` (або `FUNCTION KILL`) допоможе, лише якщо скрипт ще нічого не записав. Інакше `UNKILLABLE`, і лишається чекати або `SHUTDOWN NOSAVE`. Потім — переписати скрипт: батчі, менше роботи за виклик.

### 18.5 `ERR max number of clients reached`, таймаути з'єднань

```bash
redis-cli INFO clients                       # connected_clients, maxclients, blocked_clients
redis-cli INFO stats | grep -E 'rejected_connections|total_connections_received'
redis-cli CLIENT LIST | awk '{print $2}' | cut -d= -f2 | cut -d: -f1 | sort | uniq -c | sort -rn | head   # з'єднання за IP
ss -Htn state established '( sport = :6379 )' | wc -l
```

Найчастіше це витік з'єднань у застосунку (немає пулу, пул без ліміту, не закриваються з'єднання) або шквал перепідключень після збою. `timeout 300` закриває неактивні з'єднання; `maxclients` піднімати разом з `LimitNOFILE`.

### 18.6 `CROSSSLOT Keys in request don't hash to the same slot`

Мультиключова команда, транзакція чи скрипт у Cluster з ключами з різних слотів. Рішення — hash tags (`{user:42}:a`, `{user:42}:b`) або розбити операцію на кілька (вона перестане бути атомарною).

### 18.7 `MOVED` / `ASK` у логах застосунку

Клієнт не cluster-aware або працює з кластером як зі standalone. Увімкнути cluster-режим у клієнтській бібліотеці. Поодинокі `MOVED` після решардингу чи failover — норма, постійні — ні.

### 18.8 `CLUSTERDOWN The cluster is down`

Частина слотів не обслуговується (master і всі його репліки недоступні) при `cluster-require-full-coverage yes`, або вузли не бачать більшості.

```bash
redis-cli CLUSTER INFO | grep -E 'cluster_state|cluster_slots_(ok|pfail|fail)|cluster_known_nodes'
redis-cli CLUSTER NODES | grep -E 'fail|disconnected'
redis-cli --cluster check 10.0.0.1:6379
```

Повернути вузли, а якщо вони втрачені безповоротно, призначити слоти іншим (`--cluster fix`) і відновити дані з бекапу. Надалі: репліки на різних хостах і зонах, `cluster-migration-barrier`.

### 18.9 `READONLY You can't write against a read only replica.`

Клієнт пише в репліку. Зазвичай після failover клієнт досі тримає з'єднання зі старим master (чи закешований DNS / IP). Рішення: Sentinel-aware / cluster-aware клієнт, перепідключення при `READONLY`, короткий DNS TTL і відсутність вічного кешу DNS у JVM.

### 18.10 `NOAUTH`, `WRONGPASS`, `NOPERM`

- `NOAUTH Authentication required.` — клієнт не передав пароль.
- `WRONGPASS invalid username-password pair or user is disabled.` — неправильна пара логін/пароль або користувач вимкнений (`off`).
- `NOPERM User ro has no permissions to run the 'set' command` — ACL не дозволяє команду, ключ чи канал.

`ACL LOG` покаже, хто, звідки і що саме намагався зробити.

### 18.11 `WRONGTYPE Operation against a key holding the wrong kind of value`

Команда для одного типу застосована до ключа іншого типу (`LPUSH` на рядок). Зазвичай це колізія імен ключів між сервісами або зміна формату даних без міграції. `TYPE key` і префікси в іменах ключів.

### 18.12 `NOSCRIPT No matching script`

`EVALSHA` після рестарту, failover або `SCRIPT FLUSH`: кеш скриптів порожній. Клієнт має повторити через `EVAL` (більшість бібліотек роблять це самі). Довгостроково — Functions (розділ 10.5).

### 18.13 `NOREPLICAS Not enough good replicas to write.`

Спрацював `min-replicas-to-write`: живих реплік з прийнятним лагом менше, ніж потрібно. Це захист від split-brain (розділ 8.4), а не баг. Перевір репліки (`INFO replication` на master).

### 18.14 Репліка безкінечно синхронізується

`sync_full` росте, у лозі master — `scheduled to be closed ASAP for overcoming of output buffer limits`. Див. розділ 7.3: збільшити `repl-backlog-size` і `client-output-buffer-limit replica`, перевірити мережу і розмір датасету.

### 18.15 Сплески latency за розкладом

Сплески кожні N хвилин майже завжди означають fork (`BGSAVE` за save-точками, AOF rewrite).

```bash
redis-cli INFO stats | grep latest_fork_usec
redis-cli INFO persistence | grep -E 'rdb_last_bgsave_time_sec|aof_last_rewrite_time_sec|rdb_last_cow_size'
redis-cli LATENCY LATEST
cat /sys/kernel/mm/transparent_hugepage/enabled
```

Рішення: THP не в режимі `always`, рідші снапшоти, persistence лише на репліці, менші інстанси (шардинг), швидші диски для AOF.

### 18.16 Пам'ять росте, а кількість ключів — ні

- Ростуть **output buffers** клієнтів (pub/sub-підписник, `MONITOR`, клієнт з великим запитом): `mem_clients_normal`, `omem` у `CLIENT LIST`.
- **Фрагментація** після масових видалень: `mem_fragmentation_ratio`, `MEMORY PURGE`, `activedefrag yes`.
- Ростуть **значення**: стріми без `MAXLEN`, списки без `LTRIM`, хеші без меж.
- **Протухлі, але ще не видалені ключі**: `expired_stale_perc`.
- **Lua**: динамічно згенеровані скрипти в кеші (`used_memory_scripts`, `number_of_cached_scripts`).

### 18.17 Redis убив OOM killer / под отримав OOMKilled

```bash
dmesg -T | grep -iE 'killed process|out of memory' | tail
journalctl -k | grep -i redis
kubectl describe pod redis-0 | grep -A5 'Last State'     # Reason: OOMKilled
```

Найчастіше не встановлено `maxmemory` або не залишено запасу на fork і буфери. Розділи 5.1 і 6.2.

### 18.18 Високий CPU

```bash
redis-cli INFO commandstats | sort -t= -k3 -rn | head   # де найбільше usec
redis-cli SLOWLOG GET 20
redis-cli INFO stats | grep -E 'expired_keys|evicted_keys|total_connections_received'
top -H -p $(pidof redis-server)                         # main thread чи I/O / bio потоки
```

Типові причини: `KEYS`, важкі O(N)-команди і Lua-скрипти; масове протухання чи витіснення; шквал нових з'єднань (особливо з TLS); `activedefrag`; просто впирання в одне ядро, коли час шардувати.

### 18.19 Алгоритм при будь-якому інциденті

```bash
redis-cli PING                                  # 1. чи живий і чи відповідає (LOADING? BUSY?)
redis-cli INFO server | grep -E 'version|uptime' # 2. чи не було рестарту (uptime_in_seconds)
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|policy|fragmentation_ratio'
redis-cli INFO stats | grep -E 'ops_per_sec|rejected|evicted|expired_keys|latest_fork'
redis-cli INFO clients                          # 3. з'єднання, блоковані клієнти
redis-cli INFO replication                      # 4. роль, лінк, лаг
redis-cli INFO persistence | grep -E 'status|in_progress'
redis-cli SLOWLOG GET 10                        # 5. повільні команди
redis-cli LATENCY DOCTOR
tail -100 /var/log/redis/redis-server.log       # 6. лог
dmesg -T | tail; free -h; df -h; vmstat 1 5     # 7. ОС: OOM, swap, диск, steal
```

Якщо `--latency` з хоста застосунку погана, а `--intrinsic-latency` і `--latency` на самому сервері нормальні, проблема в мережі чи клієнті, а не в Redis.

## 19. Каверзні питання на співбесіді — з відповідями {#interview}

### Як пояснити Redis за 30 секунд

> Redis — in-memory сервер структур даних. Команди виконуються одним потоком через event loop, тому кожна команда атомарна, а одна повільна блокує всіх. Дані живуть у RAM, на диск вони потрапляють опційно: RDB-снапшоти через fork і copy-on-write та/або AOF-журнал. Реплікація асинхронна, failover робить Sentinel, шардинг — Redis Cluster з 16384 слотами. Пам'ять обмежується `maxmemory` з політикою витіснення. Після зміни ліцензії у 2024 році з'явився BSD-форк Valkey, сумісний з Redis до 7.2 включно.

### Базовий рівень

**1. Що таке Redis і чим він відрізняється від звичайної бази даних?**
In-memory сервер структур даних: значення ключа — не лише рядок, а й хеш, список, множина, ZSET, стрім, і для кожного типу є атомарні серверні операції. Від реляційної бази відрізняється тим, що дані в RAM (мікросекунди замість мілісекунд), немає SQL, JOIN і довільних запитів, модель даних будується від шаблонів доступу, а durability за замовчуванням слабка: persistence і реплікація асинхронні.

**2. Redis однопотоковий? Чому тоді він такий швидкий?**
Однопотокове виконання команд, але не весь процес: є фонові потоки (`fsync`, lazy free, закриття файлів), I/O-потоки (6.0+) і дочірні процеси для RDB / AOF rewrite. Швидкий, бо дані в RAM, немає блокувань і перемикань контексту, структури даних ефективні, а один потік через `epoll` обслуговує тисячі з'єднань. Зворотний бік: інстанс упирається в одне ядро, а повільна команда блокує всіх.

**3. Які типи даних знаєш і для чого кожен?**
String (кеш, лічильники, бітмапи), Hash (об'єкти), List (черги, «останні N»), Set (унікальність, теги), Sorted Set (рейтинги, пріоритети, часові вікна), Stream (лог подій з consumer groups), HyperLogLog (кількість унікальних з похибкою ~0.81% за 12 КБ), Geo (на Sorted Set). У Redis 8 — ще JSON, TimeSeries, ймовірнісні структури, Vector Sets і Array.

**4. Що станеться, якщо виконати `KEYS *` на проді?**
O(N) по всіх ключах в одному потоці: на десятках мільйонів ключів це секунди повного блокування для всіх клієнтів, таймаути, а Sentinel може навіть почати failover. Замість нього — `SCAN` з `MATCH` і `COUNT` (або `redis-cli --scan`), який ітерує порціями. У нормально налаштованому ACL у застосунків команди `KEYS` немає взагалі (`-@dangerous`).

**5. Чим `DEL` відрізняється від `UNLINK`?**
`DEL` звільняє пам'ять синхронно в main thread: для колекції з мільйонами елементів це довге блокування. `UNLINK` миттєво прибирає ключ із простору ключів, а пам'ять звільняє фоновий потік. Аналогічно `FLUSHALL ASYNC`. У Valkey 8+ `lazyfree-lazy-user-del yes` за замовчуванням, тож там `DEL` поводиться як `UNLINK`.

**6. Що повертає `TTL` і як Redis протухає ключі?**
Секунди до протухання, `-1` — ключ без TTL, `-2` — ключа немає. Протухання — пасивне (при зверненні) і активне (`hz` разів на секунду вибірка ключів з TTL; якщо прострочених багато, цикл повторюється з лімітом CPU). Тому прострочений ключ може якийсь час займати пам'ять.

**7. Чи скидає `SET` TTL ключа?**
Так. `SET` без `KEEPTTL` перезаписує ключ разом з TTL, і він стає вічним. TTL скидають команди, що видаляють чи повністю перезаписують значення (`SET`, `GETSET`, `*STORE`), а ті, що змінюють значення на місці (`INCR`, `APPEND`, `HSET`, `LPUSH`), TTL не чіпають. `RENAME` переносить TTL на нове ім'я.

**8. Що буде, коли пам'ять закінчиться?**
Без `maxmemory` (дефолт — 0, тобто без ліміту) Redis росте, доки його не вб'є OOM killer чи cgroup. З `maxmemory` усе залежить від політики: `noeviction` (дефолт) — помилка `OOM command not allowed when used memory > 'maxmemory'` на запис, читання і `DEL` працюють; `*-lru` / `*-lfu` / `*-random` / `volatile-ttl` — витіснення.

**9. Які політики витіснення знаєш? LRU vs LFU?**
`noeviction`, `allkeys-lru`, `allkeys-lfu`, `allkeys-random`, `volatile-lru`, `volatile-lfu`, `volatile-random`, `volatile-ttl`, а з Redis 8.6 ще `allkeys-lrm` і `volatile-lrm` (least recently modified). LRU витісняє те, що найдовше не читали, LFU — те, що читають рідко, з «остиганням» лічильника. Обидва наближені: Redis бере вибірку з `maxmemory-samples` ключів і пул кандидатів, а не підтримує справжній список.

**10. RDB чи AOF?**
RDB — періодичний снапшот через fork: компактний, швидко завантажується, зручний для бекапів, але при падінні втрачається все після останнього снапшота. AOF — журнал записів з `fsync` раз на секунду (дефолт): втрата ~1 с, але файл більший і росте до rewrite. Для «сховища» вмикають обидва; для кешу часто вистачає RDB або нічого.

**11. Що таке pipelining і чи атомарний він?**
Відправка кількох команд без очікування відповіді на кожну: економить RTT і системні виклики. Не атомарний: між командами pipeline можуть виконатися команди інших клієнтів. Для атомарності — `MULTI` / `EXEC` або Lua.

**12. Чи є в Redis транзакції? А rollback?**
`MULTI` / `EXEC` виконує команди блоком без втручання інших клієнтів, але rollback немає: якщо команда впала під час виконання (`WRONGTYPE`), решта все одно виконаються. Лише помилки на етапі постановки в чергу (синтаксис, невідома команда) відміняють усю транзакцію з `EXECABORT`. Умовну логіку дають `WATCH` (оптимістичне блокування) або Lua.

**13. Pub/Sub, List чи Streams для черги?**
Pub/Sub — fire-and-forget: офлайн-підписник усе пропустить, повільного Redis відключить. List — проста черга, але повідомлення губиться, якщо воркер упав після `POP` (лікується `BLMOVE` у список «в обробці»). Streams — consumer groups, підтвердження `XACK`, повторна доставка завислих повідомлень через `XAUTOCLAIM`, можливість перечитати історію; це правильний вибір для черги з гарантіями.

**14. Як зробити розподілений лок?**
`SET lock:x <унікальний токен> NX PX 30000` — атомарно і з TTL. Відпускати лише свій лок: Lua «якщо значення = мій токен, то `DEL`», або `DELEX key IFEQ token` (Redis 8.4+) / `DELIFEQ` (Valkey 9.0+). `SETNX` + `EXPIRE` окремо — помилка: падіння між ними залишить вічний лок.

**15. Redis vs Memcached?**
Memcached — лише ключ → blob, багатопотоковий, без persistence і реплікації, значення до 1 МБ за замовчуванням. Redis — структури даних, persistence, реплікація, Cluster, скрипти, pub/sub, але виконання команд в одному потоці. Memcached має сенс для дуже простого великого кешу, Redis / Valkey — практично для всього іншого.

**16. Навіщо Sentinel?**
Моніторинг master і реплік, сповіщення, автоматичний failover і роль configuration provider: клієнт питає в Sentinel адресу поточного master. Sentinel не проксує трафік і не шардує дані. Потрібно щонайменше три Sentinel'и в незалежних зонах відмови.

**17. Що таке Redis Cluster і hash slots?**
Вбудований шардинг: простір ключів поділено на 16384 слоти (`CRC16(key) mod 16384`), слоти розподілені між master'ами, у кожного свої репліки, failover вбудований. Клієнт має бути cluster-aware: тримати карту слотів і обробляти `MOVED` / `ASK`. Мультиключові операції працюють лише в межах одного слота.

### Середній рівень

**18. Чому після масового протухання ключів пам'ять звільняється не одразу?**
Активне протухання — ймовірнісне: вибірка ключів з TTL `hz` разів на секунду з обмеженням по CPU. Якщо ключів, що протухли, багато, а до них ніхто не звертається, частина ще якийсь час лежить у пам'яті (`expired_stale_perc`). Плюс RSS не зменшується одразу через фрагментацію: алокатор тримає звільнені сторінки.

**19. Чому подія `expired` у keyspace notifications може запізнюватися?**
Вона генерується, коли ключ фізично видалили (при зверненні або в активному циклі), а не коли TTL дійшов до нуля. До того ж pub/sub не гарантує доставку. Будувати планувальник «виконай дію, коли ключ протухне» на цих подіях не можна: краще Sorted Set з часом як score або справжній планувальник.

**20. Що відбувається під час `BGSAVE` і чим це небезпечно?**
`fork()`: main thread стоїть, поки копіюються таблиці сторінок (близько 10–20 мс на ГБ, на старих віртуалках — сотні мс на ГБ). Далі copy-on-write: кожна сторінка, змінена під час снапшота, копіюється, і при інтенсивному записі пам'ять може подвоїтися. Ризики: сплески latency, OOM, невдалий fork і, як наслідок, `MISCONF`.

**21. Навіщо `vm.overcommit_memory = 1` і що не так із THP?**
З дефолтним overcommit ядро може відмовити у fork процесу на десятки гігабайтів, хоча через COW стільки пам'яті не знадобиться, і `BGSAVE` впаде з `Cannot allocate memory`. THP у режимі `always` змушує копіювати при COW 2-мегабайтні сторінки замість 4-кілобайтних, а це сплески latency і пам'яті. Redis сам попереджає про обидві речі при старті (для THP радить `madvise` або `never`), а з 6.2 параметр `disable-thp yes` вимикає THP для самого процесу.

**22. Що буде з `volatile-lru`, якщо ключів з TTL немає?**
Витісняти нічого, і Redis поводиться як із `noeviction`: запис отримує OOM-помилки. Типова ситуація в ElastiCache, де дефолтна політика — саме `volatile-lru`, а розробники не ставлять TTL.

**23. Як влаштована реплікація: full і partial resync?**
У master є replication ID і offset. Репліка надсилає `PSYNC <replid> <offset>`. Якщо ID збігається і пропущене ще є в replication backlog — partial resync, досилається лише пропущене. Інакше full sync: RDB через fork (з 7.0 diskless, одразу в сокет), завантаження на репліці, далі потік команд. PSYNC2 (4.0+) дозволяє partial resync після failover і рестарту репліки.

**24. Чому репліка може нескінченно робити full sync?**
Backlog малий (дефолт 1 МБ у Redis), тому після короткого розриву partial resync неможливий. А поки master робить і передає великий RDB, буфер для репліки перевищує `client-output-buffer-limit replica` (256 МБ / 64 МБ за 60 с), master рве з'єднання, і все починається спочатку. Лікування: збільшити backlog (швидкість потоку × час розриву × запас) і ліміт буфера, перевірити мережу. У Redis 8 потік змін під час full sync накопичується на репліці (rdb-channel), що частково знімає проблему.

**25. Чи гарантує `WAIT`, що запис не загубиться?**
Ні. `WAIT N timeout` чекає, доки N реплік підтвердять отримання запису в пам'ять. Це сильно зменшує ймовірність втрати, але Redis від цього не стає strongly consistent: failover все одно може обрати репліку без запису, а підтвердження не означає `fsync`. Для диска є `WAITAOF` (7.2+). Документація Redis прямо каже, що `WAIT` не робить Redis CP-системою.

**26. Як репліки обробляють TTL?**
Самі не протухають: чекають явного `DEL` від master, щоб дані не розійшлися. Але при читанні перевіряють TTL за своїм годинником і відповідають, що ключа немає (з 3.2). Наслідок: якщо master не встигає протухати ключі, пам'ять росте і на репліках. За `maxmemory` репліки теж самі не витісняють (`replica-ignore-maxmemory yes`).

**27. Quorum vs majority у Sentinel?**
Quorum — скільки Sentinel'ів мають погодитися, що master недоступний (ODOWN). Але щоб почати failover, Sentinel має отримати голоси більшості всіх Sentinel'ів. З п'ятьма Sentinel'ами і quorum 2 падіння визнають два, а failover можливий лише за наявності трьох доступних.

**28. Чому мінімум 3 Sentinel і 3 master у Cluster?**
І там, і там рішення приймає більшість: Sentinel'и голосують за лідера failover, master'и в кластері — за промоушн репліки. З двома учасниками падіння одного залишає 1 з 2, а це не більшість, і failover неможливий. Учасники мають стояти в незалежних зонах відмови.

**29. `MOVED` vs `ASK`?**
`MOVED` — слот постійно обслуговує інший вузол: повторити там і оновити карту слотів. `ASK` — слот зараз мігрує, і саме цього ключа на старому вузлі вже немає: одноразово відправити на новий вузол `ASKING` + команду, карту не оновлювати.

**30. Що таке hash tags і чим вони небезпечні?**
Якщо в ключі є `{...}`, хешується лише вміст дужок, тож `{user:42}:cart` і `{user:42}:profile` потрапляють в один слот, і з ними працюють мультиключові команди, транзакції і Lua. Небезпека — надмірне використання: якщо загнати під один тег дані великого клієнта, вийде гарячий перевантажений слот, і шардинг втрачає сенс.

**31. Що буде з кластером, якщо впаде master і всі його репліки?**
Частина слотів без власника. З дефолтним `cluster-require-full-coverage yes` весь кластер відповідатиме `CLUSTERDOWN The cluster is down`, навіть для слотів на живих вузлах. З `no` живі слоти працюють, а запити до осиротілих отримують помилку. `cluster-allow-reads-when-down yes` дозволяє читання.

**32. Чому в Redis Cluster саме 16384 слоти?**
Кожен heartbeat (ping / pong) між вузлами несе бітмап слотів: 16384 біти — це 2 КБ, а 65536 — уже 8 КБ на кожен пакет. Кластерів понад ~1000 master'ів не планувалося, тож 16384 слотів вистачає з запасом для рівномірного розподілу.

**33. Що буде, якщо в `MULTI` / `EXEC` одна команда впаде?**
Якщо під час виконання (наприклад, `WRONGTYPE`) — решта команд виконаються, rollback немає. Якщо ще на етапі черги (неправильний синтаксис) — `EXEC` поверне `EXECABORT`, і не виконається нічого. Пояснення Redis: runtime-помилки — це баги в коді, а rollback ускладнив би й сповільнив сервер.

**34. Як працює `WATCH` і коли він не підходить?**
`WATCH key` → читаємо → `MULTI` → пишемо → `EXEC`. Якщо ключ змінився (а з 6.0.9 і протух) до `EXEC`, транзакція не виконається, `EXEC` поверне nil, і застосунок повторює спробу. Це оптимістичне блокування. Не підходить при високій конкуренції за ключ: повтори йдуть по колу. Тоді краще Lua, де вся логіка виконується атомарно на сервері.

**35. Що треба знати про Lua-скрипти в Redis?**
Атомарні, тобто блокують сервер на час виконання. Після `busy-reply-threshold` (5 с) інші клієнти отримують `BUSY`, але скрипт працює далі. `SCRIPT KILL` спрацює лише для скрипта, який ще нічого не записав; інакше тільки `SHUTDOWN NOSAVE`. Якщо скрипт упав посередині, записи до помилки лишаються. Ключі передаються через `KEYS` (для Cluster і ACL). Кеш скриптів зникає після рестарту і failover, звідси `NOSCRIPT` у `EVALSHA`.

**36. Functions vs `EVAL`?**
Functions (7.0+) завантажуються бібліотекою один раз, зберігаються в RDB / AOF і реплікуються, тож переживають рестарт і failover. Їх можна позначити `no-writes` і викликати через `FCALL_RO` на репліках. `EVAL` / `EVALSHA` — тимчасовий кеш скриптів, з 7.4 ще й з витісненням.

**37. Big keys і hot keys: як знайти і що з ними робити?**
Big key — ключ з величезним значенням: блокуючі O(N)-операції, довгий `DEL`, перекіс пам'яті між шардами, проблеми з міграцією слотів. Шукати: `--bigkeys`, `--memkeys`, `--keystats`, `MEMORY USAGE`, аналіз RDB офлайн. Лікувати: розбивати, читати порціями, `UNLINK`. Hot key — ключ з непропорційним трафіком, який упирає одне ядро одного вузла. Шукати: `--hotkeys` (з LFU), `HOTKEYS` (8.6+), `CLUSTER SLOT-STATS`. Лікувати: локальний / client-side кеш, репліки, копії ключа.

**38. Як читати `mem_fragmentation_ratio` і чому RSS не падає після видалення ключів?**
Це `used_memory_rss / used_memory`. ~1.0–1.5 — норма; > 1.5 — фрагментація; < 1 — частина пам'яті у swap (гірше за все); величезне значення на майже порожньому інстансі — нормально. Після видалення ключів jemalloc тримає сторінки для майбутніх алокацій, тому RSS не падає. `MEMORY PURGE` і `activedefrag yes` допомагають, а радикальний спосіб — failover на свіжу репліку.

**39. Чому `SLOWLOG` порожній, а клієнти бачать 300 мс?**
`SLOWLOG` міряє лише виконання команди. Час у черзі за чужою повільною командою, мережа, fork, swap, THP, `fsync` і проблеми клієнта (вичерпаний пул, GC, DNS) туди не потрапляють. Дивитися треба `--latency` з боку клієнта і з сервера, `--intrinsic-latency`, `LATENCY LATEST`, `latest_fork_usec`, метрики хоста.

**40. Що таке cache stampede, penetration і avalanche?**
Stampede — протух гарячий ключ, і тисячі запитів одночасно перераховують його в БД: лок на перерахунок, stale-while-revalidate, ймовірнісне раннє оновлення. Penetration — запити до неіснуючих даних щоразу йдуть у БД: кешувати порожню відповідь, Bloom filter. Avalanche — масово протухли ключі з однаковим TTL або впав Redis: jitter у TTL, HA, circuit breaker, локальний кеш.

**41. Чому при оновленні даних ключ у кеші краще видалити, а не перезаписати?**
Паралельні оновлення можуть записати в БД в одному порядку, а в кеш в іншому, і в кеші залишиться старе значення. Видалення ідемпотентне, наступне читання візьме актуальне значення з бази. Гонка «читач поклав у кеш старе значення після інвалідації» все одно можлива, тому TTL ставиться завжди, а для критичних даних — відкладене повторне видалення або інвалідація через CDC.

**42. Чому відкритий у мережу Redis дорівнює зламаному серверу?**
Без пароля будь-хто може записати файл через `CONFIG SET dir` / `dbfilename` + `SAVE` (SSH-ключ, cron), підключити свій сервер як master і завантажити модуль, використати вразливість Lua (RediShell, CVSS 10.0 за оцінкою Redis). З 7.0 `CONFIG SET dir` і `MODULE` закриті за замовчуванням, але це не привід відкривати порт. Захист: приватна мережа і фаєрвол, ACL з мінімальними правами, TLS, свіжі патчі, не запускати від root. І пам'ятати, що офіційний Docker-образ має `protected-mode no`.

**43. Як видалити мільйони ключів за маскою на проді?**
`SCAN 0 MATCH 'session:*' COUNT 1000` у циклі + `UNLINK` пачками через pipeline, з паузами, якщо навантаження критичне. У Cluster — на кожному master окремо і з урахуванням слотів. Ніколи `KEYS` + `DEL`. Надалі такі ключі мають мати TTL або жити в окремому інстансі, який можна просто очистити.

### Senior-рівень

**44. Чи можна використовувати Redis як основну базу даних?**
Можна, якщо свідомо прийняти компроміси: AOF з `appendfsync always` або `everysec` (втрата до ~1 с), репліки, `WAIT` / `WAITAOF` для критичних записів, `min-replicas-to-write`, регулярні перевірені бекапи. Обмеження лишаються: датасет у RAM (дорого), немає довільних запитів і схеми, failover може втратити підтверджені записи. Для цього сценарію є AWS MemoryDB і опційна durability в ElastiCache для Valkey 9+ із синхронним журналом. Найчастіше правильна відповідь — БД як джерело правди і Redis як кеш чи допоміжне сховище.

**45. Чи безпечний Redlock? Що таке fencing tokens?**
Redlock бере лок на більшості з N незалежних master'ів. Критика Клеппманна: алгоритм спирається на припущення про час, і GC-пауза, затримка мережі чи стрибок годинника дозволяють двом клієнтам одночасно вважати лок своїм. Для коректності потрібні fencing tokens: монотонний номер від сервісу локів, а сховище відкидає записи з номером, меншим за вже бачений. Redis такого не дає. Висновок: локи на Redis — для ефективності (уникнути дублювання роботи); для коректності — etcd / ZooKeeper з fencing або обмеження в самій БД.

**46. Чим небезпечний master без persistence з автоперезапуском?**
Master падає, systemd чи Kubernetes одразу його перезапускає, він стартує порожнім, а репліки слухняно роблять з нього full sync і знищують свої дані. Sentinel може навіть не помітити падіння, якщо рестарт швидший за `down-after-milliseconds`. Правило з документації: або persistence на master, або без автоперезапуску.

**47. Як обмежити втрату даних при split-brain у Sentinel?**
`min-replicas-to-write 1` і `min-replicas-max-lag 10`: ізольований master перестає приймати записи через ~10 секунд без підтверджень від реплік, тож втрачається не більше цього вікна. Ціна — недоступність запису, коли репліки справді лежать. Плюс коректне розміщення Sentinel'ів і клієнти, які після failover перепідключаються до нового master.

**48. Чи можна втратити підтверджений запис у Redis Cluster?**
Так, двома способами. Асинхронна реплікація: master підтвердив запис і впав до того, як передав його репліці, яка стала новим master. Партиція: master у меншій частині кластера приймає записи, доки не мине `cluster-node-timeout`, а після об'єднання ці записи зникають. `WAIT` зменшує ризик, але не прибирає його.

**49. Що враховується в `maxmemory` і чому буфери реплік туди не входять?**
`maxmemory` порівнюється з `used_memory` мінус буфери реплік і AOF (`mem_not_counted_for_evict`). Якби буфери реплік враховувалися, вийшов би цикл: буфер росте → витіснення → кожне витіснення — це `DEL` у той самий буфер → ще більше витіснень, доки база не спорожніє. Тому RAM має бути більше за `maxmemory`: на буфери, COW і фрагментацію.

**50. Чим загрожує `FLUSHALL` і як відновитися?**
Реплікується на всі репліки. З налаштованими save-точками одразу синхронно перезаписує `dump.rdb` порожнім снапшотом. Якщо ввімкнено AOF і rewrite ще не відбувся: заборонити rewrite (`auto-aof-rewrite-percentage 0`), зупинити Redis, видалити `FLUSHALL` з останнього `*.incr.aof` і запустити знову. Інакше — бекап з іншого місця. Профілактика — ACL без `@dangerous` для застосунків.

**51. Як увімкнути AOF на працюючому інстансі без втрати даних?**
Не правкою конфігу з рестартом: Redis стартує з AOF, якого ще немає, і може піднятися порожнім. Правильно: `CONFIG SET appendonly yes`, дочекатися завершення rewrite (`aof_rewrite_in_progress:0`), потім `CONFIG REWRITE` або правка `redis.conf`.

**52. Як оновити Redis або переїхати на інший сервер без даунтайму?**
Підняти новий інстанс (нову версію) як репліку, дочекатися синхронізації, переключити клієнтів через failover (`FAILOVER`, `SENTINEL FAILOVER`, `CLUSTER FAILOVER` на репліці, керований failover у хмарі), потім оновити або прибрати старий вузол. Репліка може бути новішою за master, але не навпаки: новіший RDB старіша версія не прочитає. Між Redis 7.4+ і Valkey реплікація не працює взагалі, там потрібна логічна міграція.

**53. Інстанс упирається в CPU. Як масштабувати?**
Спершу з'ясувати, на що йде CPU: `INFO commandstats`, `SLOWLOG`, big keys, Lua, протухання, витіснення, шквал з'єднань, TLS. Якщо це мережа — `io-threads`. Якщо читання — репліки або client-side caching. Якщо запис і обсяг — шардинг: Redis Cluster або розділення за сервісами на кілька інстансів. Вертикальне масштабування «більше ядер» не допоможе: команди виконуються в одному потоці.

**54. Як працює client-side caching і коли він потрібен?**
Клієнт кешує значення у своїй пам'яті, а сервер через `CLIENT TRACKING` пам'ятає, хто що читав (або працює за префіксами в режимі `BCAST`), і шле push-повідомлення про інвалідацію при зміні ключа. Потрібен для гарячих ключів, які часто читають і рідко змінюють (конфіги, фіче-флаги): прибирає і мережу, і навантаження на сервер.

**55. Redis vs Valkey: різниця і як обрати? Чи можна мігрувати?**
Valkey — BSD-форк Redis 7.2.4 під Linux Foundation, основний двигун в AWS і GCP. Redis з 8.0 доступний під AGPLv3 (або RSALv2 / SSPLv1) і має в дистрибутиві Query Engine, JSON, TimeSeries, Vector Sets. З Redis ≤ 7.2 на Valkey — оновлення на місці. З Redis 7.4+ формати RDB розійшлися (Valkey не читає RDB 12+, Redis не читає RDB Valkey 9), реплікація між ними не працює, тож переїзд — логічна міграція. Вибір: ліцензійна політика компанії, потрібні модулі, хмара. Нюанс: Valkey завжди віддає `redis_version:7.2.4`.

**56. Чому Redis у Kubernetes отримує `OOMKilled`, хоча `maxmemory` налаштовано?**
Memory limit рахує RSS, а не `used_memory`: COW під час fork, буфери клієнтів і реплік, фрагментація. `maxmemory`, близький до ліміту, гарантує OOMKilled на першому ж `BGSAVE` під навантаженням. Рішення: `maxmemory` ~50–70% ліміту з persistence, THP на вузлах не в режимі `always`, моніторинг RSS, persistence на репліках.

**57. Як спроєктуєш кешування для сервісу на 100k RPS?**
Cache-aside з TTL і jitter; захист від stampede (лок на перерахунок або stale-while-revalidate); негативне кешування від penetration; локальний L1-кеш або client-side caching для найгарячіших ключів; pipelining і `MGET` замість циклів; пули з'єднань з таймаутами і backoff; Valkey / Redis з репліками (Sentinel або Cluster залежно від обсягу); `allkeys-lru` / `allkeys-lfu`; метрики hit ratio, latency, витіснень і пам'яті; і план деградації, якщо Redis недоступний: що робить сервіс і чи витримає БД.

**58. Що змінилося в Redis за останні роки, про що варто знати?**
Ліцензії (RSAL / SSPL у 7.4, AGPLv3 у 8.0) і форк Valkey; модулі Stack у дистрибутиві Redis 8; нові I/O-потоки; нова схема full sync; TTL на полях хешу; атомарна міграція слотів; compare-and-set для рядків (`SET IFEQ`, `DELEX` / `DELIFEQ`); нові політики `*-lrm` і `HOTKEYS` у 8.6; RediShell і хвиля security-патчів 2025–2026; зміни Bitnami; виведення Azure Cache for Redis з експлуатації.

### Сценарні питання: «Що ти робитимеш, якщо...»

**59. Latency стрибає кожні 15 хвилин.**
Періодичність вказує на fork: `BGSAVE` за save-точками або AOF rewrite. Перевірити `latest_fork_usec`, `LATENCY LATEST` (подія `fork`), час останніх `BGSAVE` у лозі, THP. Рішення: THP не в режимі `always`, рідші снапшоти чи persistence лише на репліці, менші інстанси (шардинг), `vm.overcommit_memory = 1`.

**60. На проді посипались `OOM command not allowed`.**
`INFO memory` (used vs maxmemory, policy), `INFO keyspace` (чи є ключі з TTL при `volatile-*`), `--memkeys` / `--bigkeys`, `CLIENT LIST` (великий `omem`). Швидко: збільшити `maxmemory`, якщо є запас RAM, або змінити політику на `allkeys-lru` для кешу. Потім знайти причину: ключі без TTL, big keys, стрім без `MAXLEN`, буфери клієнтів.

**61. Хтось виконав `FLUSHALL` на проді.**
Не перезапускати нічого бездумно. Якщо AOF: `CONFIG SET auto-aof-rewrite-percentage 0`, зупинити Redis, скопіювати `appendonlydir`, видалити `FLUSHALL` з останнього incr-файлу, запустити. Якщо лише RDB — локальний `dump.rdb` уже порожній, відновлювати з віддаленого бекапу (репліки теж порожні). Постмортем: ACL, `-@dangerous`, окремі користувачі для людей і застосунків.

**62. Після failover застосунок сиплеться помилками `READONLY`.**
Клієнт тримає з'єднання з колишнім master (тепер реплікою) або закешував його IP чи DNS. Рішення: Sentinel- / cluster-aware клієнт, перепідключення на `READONLY`, правильний endpoint (у хмарі — primary endpoint), обмежений кеш DNS у JVM. Тимчасово — перезапустити поди застосунку, щоб вони заново визначили master.

**63. CPU Redis 100%, а ops/s не виріс.**
Отже, команди стали «дорожчими». `INFO commandstats` (зростання `usec_per_call`), `SLOWLOG`, `CLIENT LIST` (`cmd=`), big keys, нові Lua-скрипти після деплою, масове протухання чи витіснення, шквал з'єднань (`total_connections_received`), `activedefrag`. Найчастіше причина — свіжий реліз застосунку з `KEYS`, `HGETALL` на великих хешах або `SMEMBERS`.

**64. Пам'ять росте, а кількість ключів — ні.**
Ростуть значення (стріми без `MAXLEN`, списки, хеші), буфери клієнтів (`mem_clients_normal`, `omem`: повільний pub/sub-підписник, `MONITOR`), фрагментація (`mem_fragmentation_ratio`), прострочені, але не видалені ключі, кеш Lua-скриптів. Розбирати за `INFO memory` і `MEMORY STATS`.

**65. Репліка постійно в full sync.**
У лозі master — `scheduled to be closed ASAP for overcoming of output buffer limits`, `sync_full` росте. Збільшити `repl-backlog-size` і `client-output-buffer-limit replica`, перевірити мережу між вузлами і час створення RDB, переконатися, що на репліці достатньо RAM. Якщо датасет величезний — шардувати.

**66. Застосунок отримує `MISCONF`.**
`BGSAVE` падає. Лог Redis: місце на диску, права на каталог, невдалий fork (`vm.overcommit_memory`, нестача RAM). Виправити причину і вручну перевірити `BGSAVE`. Вимкнути `stop-writes-on-bgsave-error` можна лише як тимчасову милицю, свідомо погоджуючись працювати без снапшотів.

**67. Один вузол Redis Cluster перевантажений, інші — ні.**
Hot key, big key або hash tag, що зігнав багато даних в один слот. `CLUSTER SLOT-STATS` (8.2+ / Valkey 8.0+), `HOTKEYS` (8.6+), `--hotkeys`, `--bigkeys` на цьому вузлі, `CLUSTER COUNTKEYSINSLOT`. Рішення: переглянути hash tags, розбити big key, локальний кеш для hot key, перенести гарячі слоти на окремий вузол.

**68. Після рестарту Redis кілька хвилин недоступний.**
Завантаження великого датасету: `LOADING`. RDB вантажиться швидше, ніж AOF без RDB-преамбули; швидкість упирається в диск і CPU. Плановий рестарт master'а робити через failover на репліку; у Kubernetes — `startupProbe` з запасом і не вбивати под liveness-перевіркою під час завантаження; зменшувати датасет на інстанс шардуванням.

## 20. Чек-лист: що треба знати про Redis {#checklist}

- [ ] Пояснити, чому Redis швидкий з одним потоком виконання і що «однопотоковий» — не зовсім правда (bio, I/O-потоки, fork)
- [ ] Наслідок одного потоку: одна повільна команда блокує всіх; складність основних команд
- [ ] Типи даних, їхні кодування (listpack, quicklist, intset, skiplist, hashtable) і чому кодування впливає на пам'ять
- [ ] Небезпечні команди (`KEYS`, `SMEMBERS`, `HGETALL`, `DEL` великих ключів, `FLUSHALL`, `MONITOR`) і їхні безпечні заміни (`SCAN`, `UNLINK`, `ASYNC`)
- [ ] TTL: пастки `SET` / `KEEPTTL`, `RENAME`, `EXPIRE 0`; пасивне й активне протухання; TTL на репліках; запізнення подій `expired`
- [ ] `maxmemory` і запас RAM; 8 класичних політик витіснення + `*-lrm` у Redis 8.6; пастка `volatile-*` без TTL; наближені LRU і LFU
- [ ] Що, крім даних, їсть пам'ять: буфери клієнтів і реплік, backlog, Lua, фрагментація; чому RSS не падає
- [ ] Big keys і hot keys: як знайти (`--bigkeys`, `--memkeys`, `--keystats`, `--hotkeys`, `HOTKEYS`, `CLUSTER SLOT-STATS`) і як лікувати
- [ ] RDB vs AOF, `appendfsync`, multi-part AOF, `MISCONF`, як безпечно ввімкнути AOF на живому інстансі
- [ ] fork і COW: `latest_fork_usec`, `vm.overcommit_memory = 1`, THP
- [ ] Бекапи RDB і AOF, `FLUSHALL` і відновлення з AOF; master без persistence + автоперезапуск
- [ ] Реплікація: replication ID, offset, backlog, full vs partial sync, PSYNC2, diskless, нескінченний full sync
- [ ] Асинхронність реплікації: `WAIT`, `WAITAOF`, `min-replicas-to-write`; stale reads з реплік
- [ ] Sentinel: SDOWN / ODOWN, quorum vs majority, вибір репліки, мінімум 3 Sentinel'и, split-brain, Sentinel-aware клієнти
- [ ] Cluster: 16384 слоти і чому саме стільки, hash tags, `CROSSSLOT`, `MOVED` vs `ASK`, failover, `cluster-require-full-coverage`, атомарна міграція слотів, обмеження
- [ ] Транзакції без rollback, `WATCH`, Lua (атомарність, `BUSY`, `SCRIPT KILL` vs `SHUTDOWN NOSAVE`, `NOSCRIPT`), Functions
- [ ] Cache-aside, інвалідація видаленням, гонки; stampede, penetration, avalanche
- [ ] Розподілені локи: `SET NX PX` + токен, безпечне звільнення, межі, Redlock і fencing tokens
- [ ] Rate limiting: fixed window (`MULTI` + `EXPIRE NX` або `INCREX`), sliding window на ZSET
- [ ] Pub/Sub vs List vs Streams; consumer groups, `XACK`, `XAUTOCLAIM`, `MAXLEN`
- [ ] Безпека: чому відкритий Redis = RCE, `protected-mode` (і Docker), ACL, TLS, захищені конфіги, RediShell і регулярні патчі
- [ ] Latency: джерела, `--latency`, `--intrinsic-latency`, `LATENCY DOCTOR`, межі `SLOWLOG`; I/O-потоки; налаштування ОС
- [ ] Моніторинг: ключові поля `INFO`, redis_exporter, алерти
- [ ] Kubernetes: memory limit vs `maxmemory`, sysctl на вузлах, probes і `LOADING`, мережеві ідентичності, Bitnami-зміни
- [ ] Керовані сервіси: ElastiCache / MemoryDB / Memorystore / Azure, failover через DNS, дефолти, що відрізняються від upstream
- [ ] Redis vs Valkey: ліцензії, сумісність лише до 7.2, формати RDB, `redis_version:7.2.4` у Valkey, різні дефолти
- [ ] Траблшутінг: `OOM`, `MISCONF`, `LOADING`, `BUSY`, `READONLY`, `CROSSSLOT`, `CLUSTERDOWN`, `NOREPLICAS`, `NOSCRIPT`, `NOAUTH` / `WRONGPASS` / `NOPERM`, OOM killer, сплески latency, високий CPU
